# 面试题:11 RAG 检索增强生成

> 每题讲透五件套:本质 / 机制 / 实例 / 边界 / 检验(追问预判)。答案分 30 秒版 + 深入版。
> 与 [02 上下文工程](02-context-engineering.md) Q4 衔接:那题讲**代码场景下 agentic search 与向量 RAG 怎么选**(数据形态决定检索范式);这一组讲 **RAG 系统本身怎么建、怎么调、怎么评**。

## Q1:讲讲 RAG 的完整工作流程?每个环节各有什么典型失败模式?

**考察点**:能否把 RAG 拆成**可归因的阶段流水线**,而不是"检索 + 生成"两个词;有没有"失败必须定位到某一级"的工程意识。

**30 秒版**:RAG 是两条流水线。**离线**:加载 → 解析 → 清洗 → 切块 → 嵌入 → 建索引 → 存元数据;**在线**:query 理解/改写 → 召回(向量 ‖ BM25)→ 融合 → rerank → 上下文装配 → 生成 → 引用与后校验。关键认知是它**是一个串行漏斗**:每一级的留存率相乘,上游丢掉的证据下游永远补不回来(rerank 救不了没召回的,prompt 救不了没送进去的)。所以必须**分级度量**,把"答错了"归因到具体某一级。典型失败按阶段:解析丢表格/丢版式 → 切块切碎语义 → 嵌入领域失配 → 召回被 top-k 截断 → rerank 排序错 → 上下文超预算被挤掉 → 生成时无视证据编造。

**深入版**:

**1. 每一级在优化什么、怎么坏、怎么观测**

| 阶段 | 职责 | 典型失败 | 观测指标 |
|---|---|---|---|
| 解析(parse) | PDF/HTML/表格 → 结构化文本 | 表格被拍平成乱序数字、多栏被串读、扫描件无 OCR、页眉页脚污染 | 人工抽检解析产物;每文档"可用字符比" |
| 切块(chunk) | 定义检索单元 | 答案跨块被切断;一块含多主题 | 答案跨块率、块内主题数抽检 |
| 嵌入(embed) | 语义 → 几何 | 领域/语言失配;query 与 doc 前缀不一致 | 自建标注集的 recall@k |
| 索引 + 召回 | 亿级候选可搜、出候选 | ANN 召回过低;过滤后返回空;top-k 截断;只用一路 | ANN recall、recall@N |
| 重排(rerank) | 排序 | 候选窗口不足、输入被截断 | NDCG@k、MRR |
| 装配(assemble) | 组上下文 | 重复内容占位、超预算被截、顺序不利 | context precision、上下文 token 数 |
| 生成(generate) | 出答案 | 无视证据编造、忠实于错误证据 | faithfulness、引用准确率 |

**2. 漏斗乘法:为什么"每级都还行"会变成"整体不行"**

端到端留存 = ∏ 各级留存率。四级各 0.90 ⇒ 0.66;各 0.95 ⇒ 0.81。这条乘法有两个直接推论:(a) **优化最弱的一级收益最大**,凭感觉调 prompt 往往在优化已经 0.95 的那级;(b) **必须先度量再优化**,否则你无法知道最弱的是哪一级。这也是 RAG 与单轮 LLM 调优在方法论上最大的差别。

**3. 最被低估的一级是解析,最被高估的一级是生成**

生产事故里"模型胡说"的根因绝大多数在上游:表格被解析成一串没有表头的数字、合同条款编号在切块时与正文分家、政策文档更新了但索引没更新。**把 hallucination 全部归给模型,是 RAG 面试里最典型的外行答案**。另一个常被忽略的下游失败是**上下文中毒**:检索回来两条互相矛盾的证据(旧版政策 + 新版政策),模型没有判据只能挑一条、且往往挑排在前面的——这不是生成级 bug,是**检索层缺时间/版本过滤**(对策见 Q5 装配级与 Q6 冲突上报)。

**实例**(一次可计算的归因):某问题的答案分布在 3 个 chunk 里。

```
解析:表格被拍平,1 个 chunk 失效                    → 2/3 可用
切块:1 个答案跨块边界被截断,单块不自足             → 1.5/3 有效
召回 top-50:命中 1 个                               → recall@50 = 0.33
rerank → top-5:该 chunk 排在第 7 位,被截掉         → 进上下文的证据 = 0
生成:上下文里没有依据 → 模型按世界知识编了一个答案
```
用户看到的现象是"模型幻觉",真实责任分布是解析 33%、切块 33%、rerank 33%,生成 0%。**没有分级指标,这个归因不可能做出来。**

**边界与误区**:
- 误区:"RAG = 向量数据库"。向量检索只是召回的一路,BM25、元数据过滤、结构化查询同样是 RAG 的合法组成;只看端到端准确率、不分级度量,等于蒙眼调参。
- 误区:把索引当一次性工程。语料在变,索引管道是**长期运维对象**,更新语义(增量、删除、重嵌入)必须一开始就设计。
- 边界:知识库很小的时候根本不该建 RAG。Anthropic 官方给过一条可用的分界线:知识库小于约 20 万 token(约 500 页)时,直接把全部内容放进 prompt + prompt caching 即可(as-of 2024-09;阈值随模型窗口与价格变化,需按自己场景重算)。

**追问预判**:
- 追问:"怎么快速判断是检索的锅还是生成的锅?" → 答:**oracle retrieval 反事实实验**——把标注好的 gold chunk 直接喂给模型。答对了 ⇒ 问题在检索;仍答错 ⇒ 问题在生成端(指令、模型能力、上下文顺序)。这是最便宜、最先该做的实验。
- 追问:"索引的增量更新怎么做?" → 答:文档级版本号 + 内容 hash 检测变更,chunk 级 upsert / tombstone;chunk id 用 `doc_id:section_path:content_hash` 而不是序号,否则中间插一段会让后面的 id 全部漂移、被迫全量重建。换嵌入模型必须全量重嵌入,所以索引里要带 `embed_model_version` 并支持双写灰度。

## Q2:文档切割(chunking)策略怎么选?chunk size 与 overlap 怎么定?有哪些高级切分法?

**考察点**:能否推导 chunk size 的取舍,而不是背 "512 tokens";知不知道 chunk 是**同时服务检索与生成**的双目标物。

**30 秒版**:chunk 的本质矛盾是**一个单位要同时当"检索单元"和"阅读单元"**。小块的嵌入语义纯、检索准,但上下文残缺、要更多块才凑得出答案;大块自足好读,但一个向量被迫代表多个主题,语义被"平均"掉,还浪费上下文预算。所以默认策略是**按结构切(标题/段落/代码块/表格),用 token 上限兜底**,而不是按字符数硬切;overlap 只是"防止答案被边界切断"的廉价保险,常取 10–20%。而真正的解法不是调参,是**解耦这两个目标**:小块用于检索、父块用于生成(small-to-big / 父子块)。

**深入版**:

**1. 为什么存在一个"内在最优区间"(从嵌入的数学推)**

一个 chunk 的 embedding 是它全部 token 表示的**池化**(mean/CLS/last-token),即一个**单点**。块内主题越多,这个点越靠近所有主题的重心,**离每个具体主题都更远** ⇒ 与任何具体 query 的相似度都被拉低。这就是"语义稀释":大块的检索损失不是玄学,是池化的必然结果。

反方向的约束同样硬:块太小 ⇒ 指代失去指涉("**它的**营收增长了 3%"——谁的?哪个季度?),单块不足以支撑回答,且块数暴增抬高索引与检索成本。两个方向的约束夹出一个区间——**区间的位置取决于文档结构与问题粒度,不是一个常数**。

**2. 结构 > 字符数**

markdown 标题层级、HTML/DOM、代码的 AST(函数/类边界)、PDF 的版式块,都是天然的语义边界。特别地:**表格必须整块保留**——被切开的表格是纯噪声(既没表头也没行对齐);代码必须按函数切(见 [02 Q4](02-context-engineering.md):切开函数与其类型定义会让单块基本不可用)。

**3. overlap 的真实作用与代价**

作用:让"跨边界的答案"至少在某一个块里完整出现。所以 **overlap 的正确定法是"≥ 典型答案片段长度",而不是固定 50 tokens**——如果你的答案通常是 2–3 句(约 80–120 tokens),50 的 overlap 就是无效保险。代价:存储与嵌入成本按 overlap 比例上涨,且同一段内容被多块覆盖 ⇒ **top-k 被重复内容占位**。所以有 overlap 就必须配去重(按 `doc_id` + 字符区间合并)。

**4. 高级切分法(讲机制,不列工具)**

- **递归结构切分**:优先在最强的语义边界断开(章节 → 段落 → 句子 → 词),超限才降级。工程默认值,便宜且稳。
- **语义切分**:逐句嵌入,在相邻句相似度的**低谷**处断开。代价是全量嵌入一遍 + 阈值敏感;在异构长文上收益才明显。**命题化 / 原子事实切分**更进一步——把段落改写成一句句自足的陈述再嵌入,检索精度最高,但需 LLM 改写,成本高且改写即有损。
- **上下文化切分(contextual chunking)**:保留原文块,但在嵌入与建 BM25 索引**之前**给每块前置一段由 LLM 生成的定位说明("本块出自 ACME 2023 Q2 财报,上一季度营收 3.14 亿")。Anthropic 的 Contextual Retrieval 走的正是这条路;工程关键点是用 **prompt caching 把"每块都要读一遍全文"的成本压下来**(官方给过一次性成本口径,as-of 2024-09,价格会变,面试里不建议报具体数)。官方自评效果:contextual embeddings 使检索失败率降 35%,叠加 contextual BM25 降 49%,再叠 rerank 降 67%(top-20 设置,**厂商自评口径**,不同语料不可直接套用)。
- **父子块 / small-to-big**:索引小块,命中后把它的**父块**(整节/整文档)送进上下文。这是"检索精度"与"生成上下文完整度"的解耦,工程最简单、收益最稳,**应该是默认起手式**。
- **层级摘要索引**:为每篇/每节生成摘要单独建索引,做粗筛的第一跳,再下钻到具体块。

**实例**(chunk size 与上下文成本的可计算取舍):设语料 1,000,000 tokens,overlap 15%。

| chunk size | 块数 ≈ 1.15M / size | 覆盖同等内容所需 top-k | 上下文 token |
|---|---|---|---|
| 1024 | ≈ 1,123 | top-5 | ≈ 5,120 |
| 512 | ≈ 2,246 | top-10 | ≈ 5,120 |
| 256 | ≈ 4,492 | top-20 | ≈ 5,120 |

**三行的上下文成本完全相同**——变的是:块越小,每个向量的主题越纯(检索更准),但候选越多、越依赖 rerank 把 20 个候选排对,索引条目也多 4 倍。这正是"小块召回 + rerank 收窄 + 父块回填"成为稳定组合的原因:用小块拿检索精度,用父块拿阅读完整度,用 rerank 消化变多的候选。

**边界与误区**:
- 误区:"chunk size 有业界最优值 512"。它依赖嵌入模型的有效长度、文档结构、问题粒度(点查 vs 综述)、以及有没有父块回填。**报一个数就输了,报一个取舍框架才对。**
- 误区:overlap 越大越好(冗余挤占 top-k、抬高成本,超过典型答案长度后收益迅速饱和);以及对代码/表格用固定长度硬切。
- 边界:图表、公式、版式化内容不适合纯文本切分——要么整块保留并额外生成一段文字描述用于嵌入,要么走多模态嵌入(见 Q7)。
- 边界:语料小到能整篇进上下文时,chunking 的最优解是**别切**。

**追问预判**:
- 追问:"怎么系统地调 chunk 参数?" → 答:固定一份标注集(query → gold 段落),在 `chunk_size × overlap` 网格上测 recall@k 与 context precision,**同时记录索引成本与 top-k 上下文 token**;取"召回饱和点"而非最高点——边际召回收益低于上下文成本时就停。
- 追问:"文档更新了 chunk 怎么增量更新?" → 答:以文档为单位重切,用内容 hash 判定哪些 chunk 未变以复用嵌入;id 用内容寻址(见 Q1 追问),避免序号漂移导致全量重建。

## Q3:Embedding 模型怎么选?向量检索的原理是什么?相似度度量怎么选?

**考察点**:能否讲清"嵌入把语义变成几何"这一步及其代价;度量选择能否从**训练目标**推出,而不是背"用 cosine"。

**30 秒版**:嵌入模型把文本映射成稠密向量,使"语义相近 → 几何相近";它靠**对比学习**(正样本拉近、负样本推远)获得这个性质。由此直接推出度量选择:**用什么目标训练的,推理时就必须用什么度量**——绝大多数检索型嵌入用归一化向量 + cosine/内积训练,所以用 cosine(此时与内积等价)。选型看五件事:领域与语言匹配、有效输入长度、维度与存储、是否需要**非对称检索**(query/passage 用不同指令前缀)、以及**迁移成本**——换模型 = 全量重嵌入 + 重建索引,这是选型里最贵的隐性成本。最终裁决永远用**自己语料上的标注集**,不用公开榜单排名。

**深入版**:

**1. 原理:双塔(bi-encoder)与它的代价**

query 与 doc **各自独立编码** ⇒ doc 向量可以离线算好 ⇒ 在线只需算一次 query 向量 + 一次 ANN 搜索。这就是"亿级候选、毫秒响应"的根本原因:**所有交互被推迟并压缩成向量空间里的一个标量**。

代价也正来自这里:编码 query 时看不见 doc,编码 doc 时看不见 query,两者之间的全部关系只剩一个数。这条机制**直接推出了 rerank(cross-encoder)存在的必要性**(见 Q5)——面试里能把这两题连起来讲,是明显的深度信号。

**2. 非对称性:最常见的静默掉点源**

query 短、是问句;doc 长、是陈述。许多模型因此要求给 query 和 passage 加**不同的指令前缀**(如 `query: ` / `passage: `)。忘了加、或两边加反了,**不会报任何错**,只会让召回率悄悄掉一大截;同一集合里混入两个模型产出的向量同理——灾难性但无报错。

**3. 相似度度量怎么选(可推导)**

- **cosine**:只看方向,忽略模长。检索模型主流。
- **内积(IP)**:同时受模长影响。若模型未做归一化训练,模长可能编码"信息量/流行度"——此时换成 cosine 会改变排序。
- **L2**:对**已归一化**向量,`‖a−b‖² = 2 − 2·cos(a,b)` ⇒ 与 cosine **单调等价**,排序完全一致。这是常考的小推导:归一化之后 cosine / IP / L2 三者排序同构,没归一化就各不相同。
- 判据一句话:**用模型卡指定的度量**;不确定就归一化 + cosine。

**4. 三条检索路线的谱系(能画出来是加分项)**

| 路线 | 表示 | 强项 | 代价 |
|---|---|---|---|
| 稀疏 / BM25 | 词频-IDF-长度归一化 | 罕见词、标识符、错误码、数字 | 不认同义词与改写 |
| 学习式稀疏(SPLADE 类) | 词表上的稀疏权重 | 语义扩展 + 仍可用倒排索引 | 训练与索引更重 |
| 稠密双塔 | 单向量 | 语义相近、跨表述 | 语义稀释、精确匹配弱 |
| late interaction(ColBERT 类) | **每 token 一个向量**,查询时 MaxSim | 精度接近 cross-encoder 且 doc 侧可预索引 | 存储放大一个量级以上 |

**5. 维度、量化与存储(可计算)**

存储 ≈ `N × d × bytes_per_dim`。**Matryoshka(MRL)** 训练让向量的**前缀可截断**——同一模型输出的高维向量截到一半仍保留大部分效果,这是"维度可调"的机制,而不是随便切一刀。

**实例**(1000 万 chunk,d = 1024):

```
float32 原始: 1e7 × 1024 × 4 B = 40.96 GB    MRL 截到 512: 20.48 GB
int8 标量量化: 1e7 × 1024 × 1 B = 10.24 GB
PQ(96 子空间 × 8 bit = 96 B/向量):1e7 × 96 B ≈ 0.96 GB  ← 约 42× 压缩
```
这组数直接决定了 Q4 的索引选型:**内存装不下就必须量化,而量化必然引入"用原始向量精排"的环节**。选嵌入维度时算这笔账,比看榜单分数有用得多。

**边界与误区**:
- 误区:"榜单第一就选它"。榜单是跨任务平均分,与你的语言、领域、问题分布都不同;还存在过拟合榜单与训练数据泄漏问题。MTEB / MMTEB 一类榜单只用来**筛候选**,最终必须用自己的标注集裁决(as-of 2026-08 该体系仍是主流参照,但榜单版本与排名变动很快,**具体名次需核实**)。
- 误区:"维度越高越好"。高维在存储、内存带宽与检索延迟上是线性成本,而质量收益边际递减。
- 误区:嵌入能表达否定与数值比较。"不含麸质""价格低于 100" 这类约束**必须落到元数据过滤**,语义相似度对否定几乎无感。
- 不确定项:具体模型的排名、维度、价格变化极快。面试里报"某模型 MTEB 多少分"风险大于收益;正确说法是"我们在自己的集合上做过 A/B,A 的 recall@20 高 X 个点"。

**追问预判**:
- 追问:"换 embedding 模型怎么平滑迁移?" → 答:双写双索引 + 影子流量(同一批线上 query 同时打两套索引,离线比 recall 并人工抽检),达标后切流;索引里必须有 `embed_model_version`,严禁同一集合混用两个模型的向量。
- 追问:"微调嵌入模型值得吗?" → 答:有领域黑话/内部缩写、且能拿到 query-doc 正样本对(点击日志、工单↔解决方案)时值得,**先做难负样本挖掘再训**通常比换一个更大的通用模型划算;但要把"全量重嵌入 + 长期维护 + 与基座模型解耦"的成本一起算进去。

## Q4:向量数据库怎么选?HNSW / IVF / 量化索引的原理与取舍?

**考察点**:能否讲清 ANN 的机制与"**召回率是运行时可调旋钮**"这一本质;能不能从工作负载推选型,而不是列产品名。

**30 秒版**:精确最近邻是 O(N·d) 的暴力扫描,规模一大就不可行,所以全部走 **ANN**——**用召回率换延迟**,而召回率是个**运行时可调的旋钮**。三条机制各治一件事:**HNSW** 是可导航小世界图 + 分层(与跳表同构):高层稀疏长边做"洲际大跳",低层稠密短边做局部精修,期望复杂度 ~O(log N),用 `ef_search` 调召回/延迟;**IVF** 用聚类分桶,只扫最近的 `nprobe` 个桶,用 `nprobe` 调召回;**量化(SQ/PQ/二值)** 解决的是**内存**而不是搜索路径,必然掉精度,所以必须配"用原始向量精排"。选型先问三件事:数据量与内存预算、写入模式(批量灌 vs 高频增删)、**是否需要带元数据过滤的检索**——最后一个才是生产里最容易翻车的点。

**深入版**:

**1. HNSW:为什么分层图能做到对数复杂度**

底座是 NSW(可导航小世界)上的**贪心搜索**:从入口点出发,不断跳到"离 query 更近的邻居",直到没有更近的为止。纯贪心的两个问题各由一个机制解决:

- **卡在局部最优 → 用 beam(`ef_search`)**:同时保留 `ef` 个最优候选,允许暂时走向"看起来更远"的邻居以跳出局部谷底。**ef 越大,召回率单调上升,延迟近似线性上升;ef 必须 ≥ k**。这就是"召回率是旋钮"的机制来源:**同一个索引、同一份数据,只调 ef 就能在召回 0.90 与 0.99 之间移动,不需要重建**。
- **起点太远 → 用分层**:第 l 层以概率 p^l 保留节点(几何分布),越高层节点越少、边越长。搜索从顶层单点开始贪心下降,每层把入口点精修一次再进入下一层。这与跳表同构:**高层每次把候选范围按常数因子缩小 ⇒ 期望层数 O(log N),每层常数步 ⇒ 总体 ~O(log N)**。

建图参数 `M`(每节点最大出边)与 `ef_construction` 决定图的质量与内存(邻接表 ≈ `M × 2 × 4 B` 每向量),**改它们要重建索引** ⇒ **能用 ef_search 调就别动 M**。弱点:图必须驻留内存;删除只能打墓碑,大量删除后图会退化需重建;建图慢。

**2. IVF:用聚类把搜索空间切开**

建索引对全量向量做 k-means 得 `nlist` 个质心,每个向量入最近质心的倒排列表;查询时算 query 到全部质心的距离,只扫最近的 `nprobe` 个列表,扫描量 ≈ `N × nprobe / nlist`。

**召回损失的来源是几何的**:真正的最近邻可能落在**桶边界另一侧**(query 恰好在两质心之间时最容易发生),`nprobe` 增大才可能覆盖到——又一个召回旋钮。

`nlist` 的经验值 ~√N 可以推出来:总成本 ≈ `nlist`(算质心距离)+ `N·nprobe/nlist`(扫桶),对 `nlist` 求导置零 ⇒ 最优在 `√(N·nprobe)` 附近。**能当场推这一步,比背"nlist 取 4√N"强得多。**

相对 HNSW:建索引快、内存省(尤其配 PQ),但同等召回下延迟通常更高;数据分布漂移后质心要重训。

**3. 量化:解决内存,不解决路径**

- **SQ(标量量化)**:每维 float32 → int8,4× 压缩,精度损失小,常作默认档。
- **PQ(乘积量化)**:把 d 维切成 m 个子空间,各自 k-means 出 256 个中心(8 bit),向量存成 m 字节的码。距离用 **ADC(非对称距离计算)**:query 不量化,预计算它到每个子空间 256 个中心的距离表,然后**查表求和** ⇒ 距离计算退化成 m 次查表加法,又快又省。代价是量化误差直接进入距离,近邻排序被打乱。
- **二值 / 汉明**:极致压缩,位运算算距离,只能做粗筛。
- 通用范式:**用压缩向量粗筛 top-K(K ≫ k)→ 用原始向量精算 top-k**。所以量化系统**必须保留一份原始向量**(可放磁盘/对象存储)。磁盘型 ANN(DiskANN 类)是同一思路的极端:图在磁盘、压缩向量在内存做粗筛,用 SSD 随机读换内存成本。

**4. 生产真正的坑:带过滤的检索**

需求形态是"只在 `tenant_id=42 且 status=active` 的文档里找最近邻"。两种朴素做法都会坏:

- **pre-filter**(先按元数据筛子集再搜):子集大时退化成暴力扫描;
- **post-filter**(先 ANN 取 top-k 再过滤):当过滤选择率很低时**可能返回空**——ANN 的 top-100 里一个符合条件的都没有,而系统"看起来正常"。

正确形态是 **filter-aware 的图/桶遍历**(遍历时就跳过不满足条件的节点,并相应放大 ef),或按高基数维度(如 tenant)做**物理分区**,一租户一索引。**多租户 RAG 的第一性设计决策是分区策略,不是选哪个数据库产品。**

**5. 选型判据(从负载推)**

| 问什么 | 推出什么 |
|---|---|
| 千万级以下,且已有成熟关系库/搜索引擎 | 优先用它的向量扩展——省掉整套数据同步与一致性问题 |
| 内存装不下原始向量 | 必须量化 + 精排(或磁盘型 ANN) |
| 每天全量重刷、无高频增删 / 低延迟高召回且内存充足 | 前者 IVF(-PQ)常更划算;后者 HNSW |
| 强多租户、过滤选择率很低 / 需要 hybrid | 前者分区优先其次 filter-aware;后者选倒排与向量同库的系统 |

**实例**(1000 万向量,d = 768 的内存账):

```
float32 原始 1e7×768×4B ≈ 30.7 GB  +  HNSW(M=32)图 1e7×32×2×4B ≈ 2.6 GB → 约 33 GB,需大内存机器
换 SQ int8:       7.7 GB + 2.6 GB ≈ 10.3 GB → 单机可行
换 IVF-PQ(m=96): 0.96 GB + 质心表 ≈ 1-2 GB → 很省,但需原始向量做精排(放磁盘)
```
旋钮的量级(**必须自测,不同实现差异很大**):`ef_search` 从 64 提到 256,召回率典型从 ~0.95 走到 ~0.99,延迟约 3–4×。**最后几个点的召回率是最贵的**——买不买要看它对**端到端答案正确率**的影响,而不是看召回率数字本身好不好看。

**边界与误区**:
- 误区:"HNSW 一定比 IVF 好"。HNSW 赢在同召回下的延迟,输在内存与重建成本。
- 误区:"ANN 召回 99% 就够了"。ANN 召回率是**相对于暴力搜索**的,它上面还叠着嵌入模型本身的语义召回率,两者相乘才是端到端。ANN 掉的 1% 常常无关紧要,嵌入选错掉的 20% 才是真问题——**别把工程精度当成质量**。另注:向量是**派生数据**,原文与元数据必须另有真相源,否则换模型时无法重建。
- 边界:百万级以下且内存装得下时,暴力(flat)扫描完全可行且召回 100%,**不要过早上 ANN**。

**追问预判**:
- 追问:"`ef_search` / `nprobe` 怎么定值?" → 答:用标注集画"召回率-延迟"曲线找拐点,再把召回率映射到端到端答案正确率上(常见结论是超过某点后端到端不再变好),取满足延迟 SLO 的**最小值**;线上可按查询价值分档(高价值查询给高 ef)。
- 追问:"高频增删怎么办?" → 答:HNSW 删除是墓碑,需周期性重建。工程做法是**双索引热切换**(后台重建 + 原子切换别名)或**分段索引**(新数据进小的实时段,后台合并进大段)——与 Lucene 的段合并同构。

## Q5:检索质量怎么优化?(混合检索 BM25+向量、rerank、query 改写/扩展、HyDE、父子块)

**考察点**:能否按"漏斗的哪一级"组织手段并排出优先级;有没有"每个手段都有延迟与成本代价"的账。

**30 秒版**:按漏斗分级下药。**召回级**:hybrid(BM25 + 向量,用 RRF 融合)——两者失败模式互补,BM25 挂在同义词与改写上,向量挂在标识符、专名、数字、罕见词上。**排序级**:cross-encoder rerank——把 query 与 doc **拼在一起**过一次模型做全交互打分,精度远高于双塔,但**不能预计算**,只能对召回的几十个候选做。**查询级**:改写(多轮里的指代消解)、分解(复合问题拆子查询)、多查询扩展、HyDE(先生成"假想答案"再检索,把 query-doc 的非对称匹配变成 doc-doc 的对称匹配)。**装配级**:父块回填、去重、时间/可信度排序、引用锚点、把最相关的放首尾。上手顺序:**先 hybrid + rerank(投入产出比最高),再动查询侧与切分**。

**深入版**:

**1. 混合检索:为什么必须两条腿**

BM25 的机制是词频饱和 + 逆文档频率 + 长度归一化,它的强项恰是嵌入的弱项:**罕见词的判别力**。错误码 `E_CONN_4032`、内部项目代号、法条编号,在嵌入空间里几乎没有可靠位置(训练时太罕见),但在倒排索引里 IDF 极高,一击即中。

融合用 **RRF(Reciprocal Rank Fusion)**:`score(d) = Σ_i 1/(k + rank_i(d))`,k 常取 60。它**只用名次不用分数**,因此不需要在两个不可比的尺度之间做归一化(BM25 分数无上界,cosine 在 [-1,1])——这是它在工程上流行的根本原因。代价是丢掉了分数携带的置信度信息。替代方案是分数归一化后加权求和(需按查询分布标定,较脆)或训练 learning-to-rank(需要标注)。

[02 Q4](02-context-engineering.md) 里"第一跳用 BM25 + 向量"的建议,机制根据就在这里。Anthropic 的 Contextual Retrieval 也是这个组合的一个具体实现(上下文化 chunk 同时喂 embedding 与 BM25,再叠 rerank;官方自评的失败率下降 35% → 49% → 67%,top-20 设置,as-of 2024-09 厂商口径)。

**2. Rerank:把交互还给模型**

机制对比是全题的核心:bi-encoder 把 query 与 doc 各压成一个向量,交互 = 一次内积;**cross-encoder 把 `[query; doc]` 一起送进模型**,每层注意力都能让 query 的 token 直接看 doc 的 token ⇒ 它能判断"这段是不是**真的回答了**这个问题",而不只是"主题相关"。

代价同样源于机制:doc 的表示依赖 query ⇒ **不能预计算** ⇒ 每个候选一次前向,延迟 ≈ 候选数 × 单次前向。这就是"只 rerank top-50~100"的由来。

**参数取舍是可计算的**:召回 top-N → rerank → 取 top-k 入上下文。N 决定**召回上限**(rerank 救不了没召回的),k 决定**上下文成本与噪声**。

```
方案 A:向量直接取 top-5           → 端到端 ≈ recall@5  = 0.72
方案 B:取 top-50 再 rerank 到 5   → 端到端 ≈ recall@50 × P(rerank 把 gold 排进前 5)
                                   ≈ 0.94 × 0.90 = 0.85   (+13 个点)
代价:50 次 cross-encoder 前向(批量下常在百毫秒级)
```
**这个乘法就是 rerank 价值的正确算法**——把它讲出来,比说"rerank 能提升效果"高一个档次。

变体:**late interaction(ColBERT 类)** 是折中(doc 侧可预索引、查询时 MaxSim,精度接近 cross-encoder、延迟接近双塔,代价是存储放大);**LLM-as-reranker**(直接让 LLM 做 listwise 排序)精度更高、成本更高,适合低 QPS 高价值场景。

**3. 查询侧四件事**

- **指代消解 / 改写**:多轮对话里"它的价格呢?"单独嵌入毫无意义,必须用历史补成自足问题。**这是多轮 RAG 里最常被漏掉、收益最大的一步。**
- **query 分解**:复合问题("A 和 B 哪个更便宜")拆成子查询分别检索——单个向量无法同时靠近两个主题(又是语义稀释)。
- **多查询扩展**:生成 3–5 个措辞不同的改写并行检索再 RRF 融合。收益是覆盖不同表述,代价是检索次数线性上涨,且**扩展过多会引入漂移**,把不相关文档拉进候选、稀释 rerank 的输入质量。
- **HyDE**:先让模型"编"一篇可能的答案文档,再用它的向量检索。原理是 query 与 doc 在**长度与文体上不对称**(问句 vs 陈述),嵌入空间里天然有 gap;而假想答案与真实答案**同分布**,doc-doc 匹配更稳。代价:多一次生成(延迟 + 成本);在模型完全不懂的专业领域会"编偏"反而带跑检索,**收益可能为负**。

判据:HyDE / 多查询适合**离线或低 QPS、且召回是瓶颈**的场景;在线高 QPS 优先 hybrid + rerank。

**4. 装配级(最容易被忽略的一级)**

父块回填(Q2)、按 `doc_id` + 区间**去重**(否则 overlap 与多查询会让 top-k 被同一段占满)、**顺序**(最相关的放首尾而非中间——U 型位置偏置,见 [02 Q1](02-context-engineering.md))、**元数据前置**(来源、时间、章节路径,既帮模型判断可信度也是引用的基础)、以及**允许模型说"证据不足"**(见 Q6)。

**实例**(一条完整在线链路与延迟预算):

```
用户提问 → 指代消解/改写(小模型)~150 ms
  → 并行召回:向量 top-50(HNSW ef=128)~15 ms ‖ BM25 top-50 ~10 ms
  → RRF 融合 + 去重 → 约 60 候选 ~2 ms
  → cross-encoder rerank 60 → top-8(批量前向)~120 ms
  → 父块回填 + 元数据拼装 → 约 6K tokens 上下文 ~5 ms
  → 生成(要求逐句带 chunk_id 引用)秒级
```
检索侧总计约 300 ms,在端到端里是小头(生成才是大头)。**先把召回做厚、再用 rerank 收窄**,是这份延迟预算里最划算的分配方式。

**边界与误区**:
- 误区:"rerank 能救烂召回"。rerank 只能重排**已召回的候选**,`recall@N` 是硬天花板 ⇒ 优化顺序永远是**先 recall 后 precision**。
- 误区:"上了 hybrid 一定更好"。若语料几乎没有专名/代码/数字,BM25 增量可能很小却要背一套倒排索引的运维成本。同理,把所有技巧一次全上也是错的——每个手段都有延迟与成本,且互有交互效应(强 rerank 会稀释多查询扩展的收益)。**逐个消融,别默认开。**
- 边界:强时效场景(新闻、监控、告警)里,时间衰减与硬过滤的收益常常大于所有语义技巧。

**追问预判**:
- 追问:"hybrid 的权重 / RRF 的 k 怎么调?" → 答:RRF 的 k 控制"头部名次的权重集中度"——k 小则第 1 名主导,k 大则更平滑;用标注集扫 k 与两路相对权重,并**按查询类型分档**(含罕见标识符的 query 加大 BM25 权重,可用 query 的最高 IDF 作为路由特征)。
- 追问:"rerank 模型怎么选型?" → 答:按四个维度——语言覆盖、最大输入长度(**截断会直接丢掉证据**)、延迟(候选数 × 前向)、许可与部署形态(托管 API vs 自托管开源权重);最终仍以自己语料上的 NDCG@k / recall@k 提升裁决。as-of 2026-08 托管与开源两条路线都有多个可用选项(托管侧如 Cohere、Voyage;开源权重侧如 BGE、Qwen3、Jina 系列),**具体版本与排名变化很快,面试里报选型维度胜过报型号**。

## Q6:RAG 系统怎么评估?幻觉怎么度量与抑制?

**考察点**:能否把评估拆成检索级 / 生成级 / 端到端三层并各给指标;能否把"幻觉"拆成**可度量的子概念**而不是一个感觉词。

**30 秒版**:分三层评,否则无法归因。**检索级**(需标注):recall@k、MRR/NDCG@k、context precision(送进去的块里有多少真有用)。**生成级**(可无标注,因此可对线上流量全量跑):**faithfulness / groundedness**——答案的每个断言能否在给定上下文里找到支持;以及 answer relevance——是不是答非所问。**端到端**(需标准答案):answer correctness、拒答率与拒答正确率、引用准确率。幻觉要拆成三类分治:**无依据编造**(上下文里没有)、**误读依据**(有但读错)、**过时/冲突**(召回了互相矛盾的证据)。核心抑制手段是**可验证的引用**:要求每个断言标注来源 chunk_id,再用程序或第二个模型**逐句核对**——把幻觉从"感觉"变成一个可自动判定的布尔值。

**深入版**:

**1. 三层指标与它们之间的因果链**

| 层 | 指标 | 需要什么 | 诊断什么 |
|---|---|---|---|
| 检索 | recall@k | query → gold chunk 标注 | 证据**进没进来**(唯一的硬天花板) |
| 检索 | context precision / 噪声率 | 同上 | 进来的东西值不值得占上下文 |
| 生成 | faithfulness / answer relevance | (上下文, 答案) — **无需标准答案** | 有没有编 / 有没有答非所问 |
| 端到端 | correctness | 标准答案 | 最终裁决 |
| 端到端 | 拒答率 / 该拒不拒率 | "库里无答案"样本 | 不知道时会不会硬编 |

因果链是这题的核心:**recall@k 低 ⇒ 怎么调 prompt 都救不回来**;recall 高但 faithfulness 低 ⇒ 生成端问题(指令、模型、上下文顺序);两者都高但 correctness 低 ⇒ 标准答案或问题本身有歧义。能顺着这条链讲归因,比背指标名有用得多。

**2. 怎么低成本造评测集(实操高频题)**

- **合成 + 人工过滤**:从每个 chunk 反向生成问题(让模型读 chunk 写"这段能回答什么"),该 chunk 即 gold。零标注成本、覆盖全库;但**合成问题与 chunk 措辞高度重合 ⇒ 系统性高估召回**,必须人工抽检并改写成口语化问法。
- **真实流量挖掘**:线上 query 日志 + 人工标注候选,最贵但最真。**难例定向**:必须专门构造三类——答案跨多块、需要否定/数值比较、以及**库里根本没有答案(应当拒答)**。**第三类不能少**,否则系统在"不知道"时全部编造,而评测集完全看不出来。
- 规模:**50–100 条高质量样本跑起来,胜过 1000 条噪声标注**。

**3. LLM-as-judge 用在 RAG 上的特殊陷阱**

通用偏差(位置、长度、自我偏好)见 [06 Q2](06-evals-observability.md)。RAG 特有的一条是:**judge 会用自己的世界知识去"补"上下文里没有的东西**,从而把幻觉判成 faithful。对策有两条:judge 的提示必须写死"**仅依据给定上下文判定,禁止使用外部知识**";并把判定拆到**断言级**——粒度越小,越不容易被世界知识带跑。任何 judge 上线前都要用一小份人工标注做一致性体检(如 Cohen's κ),不合格就换提示/换模型,而不是直接信它的分数。

**4. 幻觉抑制手段(按性价比排序)**

1. **强制引用 + 程序化核对**:输出带 `[chunk_id]` 锚点;后处理检查每个断言是否有锚点、锚点是否真实存在、断言与该 chunk 是否构成蕴含。无锚点的断言直接标红或剔除。
2. **允许并奖励拒答**:提示里明确"上下文不足以回答时,说明缺什么,不要推测";评测集里放"无答案"样本,把**错误拒答率**与**该拒不拒率**都当正式指标。**只测正确率不测拒答,系统必然学会编。**
3. **降噪 + 先证据后结论**:提高 context precision(rerank、去重、时间过滤)减少矛盾证据同时入场;要求模型先摘录支持句再作答,而不是先下结论再补引用(后者的引用往往是事后合理化)。
4. **原生 citations 能力**:把引用变成结构化输出而不是模型自由文本,可显著减少"引用了不存在的编号"这类错误(as-of 2026-08 主流 API 有相关能力;注意与结构化输出可能互斥,见 [02 Q5](02-context-engineering.md),**具体兼容性需核实**)。
5. **线上监控**:对真实流量抽样跑 faithfulness 当 SLI;同时盯检索侧的**先行指标**(候选相似度分布、rerank 分数分布、拒答率漂移)——它们先于用户投诉发生变化。

**实例**(断言级 faithfulness 的判定骨架):

```
输入:context(送进模型的 chunk 列表,带 id)、answer
1. 拆解:把 answer 拆成原子断言
   ["A 型号的保修期是 24 个月", "延长保修需额外付费"]
2. 逐条判定(judge 提示写死"仅依据下列上下文,禁止使用外部知识"):
   输出 supported / contradicted / not_mentioned + 支持句的 chunk_id
3. faithfulness = supported 条数 / 总断言数
4. 任何一条 contradicted ⇒ 该样本判为幻觉,进人工复核队列
```
配套三档看板:`recall@50`(证据进没进来)· `faithfulness`(有没有编)· `correctness`(答没答对)。**三个数一起看才能定位问题在哪一级**;只看其中任何一个都会得出错误结论。

**边界与误区**:
- 误区:"faithfulness 高 = 答案对"。忠实于**错误的检索结果**同样是错的——必须与 recall / correctness 并列看。
- 误区:只做离线评测。RAG 质量随**语料**漂移(新文档进来、旧文档过期),线上抽样监控是必需品不是加分项。也别把幻觉当模型的锅——生产幻觉的主因通常在检索:没召回、召回了矛盾的、召回了过期的。
- 边界:开放式/综述式问题没有唯一标准答案,`correctness` 不适用,只能用 rubric 评分 + 人工;别硬套 exact match。
- 不确定项:各类 RAG 评测框架(RAGAS 一类)的指标**定义在不同版本间有差异**,引用分数必须说明框架与版本(as-of 需核实)。

**追问预判**:
- 追问:"该投检索还是该换模型?" → 答:两个便宜的反事实实验——① oracle retrieval(直接喂 gold chunk),正确率大涨 ⇒ 投检索;② 同样上下文换更强的模型,大涨 ⇒ 投生成端。两个实验能省掉几周瞎调。
- 追问:"线上没有 ground truth 怎么监控?" → 答:用不需标注的代理指标:faithfulness(全量可跑)、拒答率、引用覆盖率、检索分数分布漂移,加上用户行为信号(重问率、复制率、点踩);再对采样流量做人工/judge 标注来校准这些代理指标。

## Q7:2026 年了,长上下文与 agentic search 会取代 RAG 吗?三者怎么选?

**考察点**:能否跳出站队、给出**可计算的判据**;能否说清三者是**互补的架构层**而非同层竞品。

**30 秒版**:不会取代,但**"朴素 RAG"(固定切块 + 单次 top-k + 无 rerank + 无评测)确实在退场**。三者优化的根本不是同一件事:**长上下文**是"全塞进去",上限是语料规模、成本与注意力退化;**RAG** 本质是一个**成本/延迟压缩器**,顺带是**权限过滤、新鲜度与引用锚点的天然落点**;**agentic search** 是"模型自己多轮查、看结果再改查询",用**轮次与上下文**换取检索策略的自适应。判据三问:① 语料**塞得下且塞得起**吗(能 ⇒ 长上下文最简单);② 有没有**精确的字面键或结构键**(有 ⇒ 关键词/结构检索或 agentic search);③ 是否需要**低延迟单跳 / 强权限过滤 / 可审计引用 / 超大或高频更新的语料 / 多模态**(是 ⇒ RAG 不可替代)。生产上的成熟形态是三层叠用。

**深入版**:

**1. 三者在优化什么(先拆开再谈选型)**

| | 长上下文 | RAG 管线 | Agentic search |
|---|---|---|---|
| 谁决定看什么 | 全都看 | 检索器:离线索引 + 单次召回 | 模型:运行时多轮迭代 |
| 成本随语料规模 | **线性且每次请求都付** | 近似常数(只付 top-k) | 随轮次增长,不随语料 |
| 新鲜度 / 权限多租户 | 取决于拼装;权限难做 | 取决于索引管道;权限的**天然落点**(元数据 + 分区) | 永远是当前状态;取决于工具权限 |
| 引用可审计 | 弱(难定位出处) | **强**(chunk_id 即锚点) | 强(路径与命令可复现) |
| 失败恢复 | 无(没看到就是没看到) | 弱(召回错了下游无从察觉) | **强**(0 结果就换关键词) |
| 主要瓶颈 | 注意力退化 + 成本 + 延迟 | 第一跳召回质量 + 索引维护 | 上下文与轮次预算 |

**2. 为什么长上下文吃不掉 RAG(三条硬理由)**

- **经济学**。设语料 P tokens、请求 N 次、top-k 上下文 k tokens:长上下文 ≈ `N·P`(命中 prompt cache 也只降到 ~`0.1·N·P`,且有 TTL,且语料一变缓存全失效),RAG ≈ `一次性索引成本 + N·k`。**P 与 N 越大,差距越悬殊**。LightOn 2026 的博客给出的量级是"典型负载下 RAG 比长上下文便宜 8–82×"(**厂商博客口径,当量级参考、不当精确值**)。反过来推同样成立:P 小、N 小的场景(内部小手册、一次性分析)本就该直接塞——Anthropic 官方给的分界线是知识库小于约 20 万 token(约 500 页)时全量入 prompt + caching 即可(as-of 2024-09,阈值随模型与价格变化)。
- **注意力**。标称窗口 ≠ 有效窗口,干扰项越多质量越差(机制见 [02 Q1](02-context-engineering.md))。**"塞得进"和"用得好"是两条曲线**;即使成本不是问题,把 100 万 token 全塞进去也常常不如给 6K 精选证据。
- **权限、新鲜度、审计**。企业里每个用户可见的文档不同 ⇒ 过滤**必须发生在检索层**;文档每天在变 ⇒ 索引管道是变更的落点;答案要能追到具体段落 ⇒ 需要 chunk 粒度的锚点。这三件事在"全塞进去"的架构里**没有自然的位置**。

**3. 为什么 agentic search 也吃不掉 RAG**

agentic search 的前提是**存在一个便宜、精确、可迭代的检索原语**——grep 之于代码、SQL 之于结构化数据、API 之于系统状态。当检索对象是**非结构化、无精确字面键**的自然语言文档(合同、工单、论文、客服知识),没有可 grep 的锚点,第一跳仍然必须是语义召回。**多模态是更硬的边界**:图表、扫描件、版式化 PDF——"你没法 grep 一张图"(LightOn 2026 的说法),这里需要多模态嵌入或视觉 rerank,shell 工具无从下手。成本结构上,agentic search 把成本从离线索引搬到**在线上下文与轮次**(见 [02 Q4](02-context-engineering.md)),高 QPS、紧延迟 SLO 的产品(搜索框、客服机器人)承受不了几轮工具调用。

但它确实**取代了朴素 RAG 的"单次 top-k 定生死"**。现代形态是 **agentic RAG**:把检索做成 agent 的工具,模型自己决定要不要检索、检索什么、结果不够就换个查询再来一次——正好补上 Q1 里"漏斗每级只有一次机会"的结构缺陷。

**4. 什么场景 RAG 仍不可替代(可直接背的七条判据)**

1. **语料远大于窗口且持续增长**(企业文档库、法规库、全量工单)——塞不进,只能检索。
2. **强权限 / 多租户**:答案只能基于当前用户有权看的文档 ⇒ 过滤必须在检索层(Q4 的分区设计)。
3. **可审计的引用**:金融、法务、医疗要求每句话可追溯到出处段落 ⇒ chunk_id 天然是锚点。
4. **高频更新 + 强时效**:今天改的政策今天生效 ⇒ 索引管道是唯一有确定更新语义的地方。
5. **高 QPS / 低延迟**:单跳向量检索是毫秒级,agent 多轮是秒级。
6. **多模态语料**:图表与版式化文档没有可 grep 的字面键。
7. **成本敏感的大规模服务**:每请求只付几千 token,而不是几十万。

反向清单(**该放弃 RAG** 的判据):语料只占窗口一小部分、请求量低、问题需要全局综述而非定点取证、或检索对象是代码/结构化数据这类有精确键的东西。

**5. 收敛形态:三层叠加**

- 第一层 **RAG 做候选缩减**:把 10⁷ 个 chunk 压到几十个候选(便宜、可过滤、可审计);
- 第二层 **agent 做取证与迭代**:在候选域内决定读哪些父块、要不要改写查询再来一轮、发现矛盾时去查权威源;
- 第三层 **长上下文承接整合**:把最终几千到几万 token 的证据一次性给模型做综合与写作。

一句话:**检索层输出候选与指针,agent 负责取证,长上下文负责整合**——这与 [02 Q4](02-context-engineering.md) 在代码场景得出的结论同构,只是把 grep 换成了向量 + BM25。

**实例**(同一判据、不同参数 ⇒ 相反结论):

```
场景 A:P = 2,000,000 tokens,N = 10,000 请求/天,top-k 上下文 = 6,000
  长上下文:超窗口不可行;即便分批也是 ~2e10 tokens/天 量级
  RAG:     离线嵌入一次 + 每次 6K → 6e7 tokens/天             ← 相差三个数量级
  agentic: 每次 4 轮 × ~3K = 1.2e4/次 → 1.2e8/天,延迟从毫秒变秒级
场景 B:P = 150,000 tokens,N = 50 请求/天
  长上下文:7.5e6 tokens/天,命中 prompt cache 后更低,工程量近乎为零  ← 选它
  RAG:     索引 + 切块 + 评测 + 运维的固定成本明显不划算
```
**同一个公式,P 和 N 一换,结论就反过来——这才是"怎么选"的正确答法。**

**边界与误区**:
- 误区:"RAG 已死"。死的是**朴素 RAG**;检索本身是任何"知识超出窗口"的系统的必需件。
- 误区:"长上下文更简单所以更好"。它把复杂度从索引管道转移到了成本、延迟与注意力质量上,并且丢掉了权限过滤与引用锚点这两个企业刚需。
- 误区:"agentic RAG 就是把检索包成一个工具"。真正的差别是**模型能否观察到检索失败并据此改写查询**——如果工具只返回 top-k 文本、不返回"命中数少 / 最高分低 / 结果为空"这类质量信号,agent 就没有自愈的依据,退化回朴素 RAG 加了一层壳。
- 不确定项:各类"RAG 比长上下文便宜 N 倍"的数字来自不同厂商与负载假设,**当量级用、不当精确值用**;正确做法是用自己的 P/N/k 算一遍。

**追问预判**:
- 追问:"新需求来了,你怎么做第一次架构决策?" → 答:先量三个数——语料总量 P、请求量 N、延迟 SLO;再问三个是否——要不要权限隔离、要不要可审计引用、语料多久更新一次。P 小 N 小无权限要求 ⇒ 长上下文;有精确键且是内部工具形态 ⇒ agentic search;其余默认 hybrid RAG + rerank,并把检索做成 agent 工具支持多轮迭代。
- 追问:"把检索做成 agent 工具,接口怎么设计?" → 答:入参暴露 `query`、`filter`(元数据/时间)、`top_k`;返回必须带 **chunk_id、来源路径、时间戳、匹配分数**,并显式给出"命中数 / 最高分"等**质量信号**,让模型能判断"这次是不是没找着";description 里写清"什么时候该检索、什么时候直接答"(description 即 API 文档,见 [01 Q3](01-agent-fundamentals.md))。
