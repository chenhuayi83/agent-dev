# 面试题:04 多智能体组

> 每题讲透五件套:本质 / 机制 / 实例 / 边界 / 检验(追问预判)。答案分 30 秒版 + 深入版。
> 本组的主线判断:多 agent 买的是**上下文并行度与墙钟**,不是智能;协调不会自然涌现,必须显式设计。

## Q1:什么时候该用多 agent?什么时候单 agent + subagent 反而更好?

**考察点**:能不能给出可操作判据而不是"看情况";知不知道多 agent 的代价从哪来。

**30 秒版**:三问判据——(1) 子任务能否划出**互不重叠的写领地**?(2) 结论能否压成几百 token **无损回传**?(3) 每个子结果是否有**独立验证手段**?三个都是"是"→ fan-out 多 agent 值得;任何一个"否"→ 单 agent 主线 + subagent 做隔离调查。默认单 agent:多 agent 是为并行的上下文预算付费,不是为更强的推理付费。

**深入版**:

多 agent 的收益只有两个真来源:**并行的上下文预算**(n 个独立窗口 = n 倍可读信息量,且主线不被过程污染)和**墙钟并行**。它不带来"更聪明"。两条实证把这点钉死了:

- Anthropic 在自家 Research 系统上的复盘(2025-06-13):BrowseComp 评测里 **token 用量本身就解释了 80% 的性能方差**——很多所谓"多 agent 增益"是"花了更多 token"的同义反复。
- Tran & Kiela(arXiv 2604.02460,2026-04):把 thinking token 预算拉平后,多跳推理任务上**单 agent ≥ 多 agent**;结论是此前报告的 MAS 优势主要来自未计入的算力与上下文差异,而非架构本身。

所以判据必须落在**任务的结构**,而不是任务的难度:

1. **写冲突(可并行性)**:子任务是否共享可变状态?读操作(检索、调研、审阅)天然可并行;写操作(改同一份代码/文档)一旦并行就要合并,合并成本随 agent 数超线性增长。Anthropic 2026-08 的群体实验里,旧一代模型在共享仓库上 PR 合并率极低,正是这条的直接体现。落地问法:**能不能给每个子任务划一块不重叠的写领地?**划不出来就别并行。
2. **压缩比(信息瓶颈)**:subagent 烧几万 token 探索,只能带回 1-2k token 结论。若任务价值在过程细节(逐行 diff、精确报错、代码上下文),压缩就是有损的;若价值在结论(哪个库合适、这三十个文件里哪个含实现),压缩几乎无损。落地问法:**你要的是答案还是过程?**
3. **可验证性**:并行 agent 的错误不会被彼此发现——同源模型方差极低,坏决定会被集体复制(见 Q3)。若子结果没有独立验证手段(测试、编译、交叉检索),n 个 agent 只是把同一个错误复制了 n 份。
4. **价值密度**:15× 的 token 溢价(见 Q5)要有人买单。Anthropic 的原话口径是:多 agent 只在"任务价值足以支付性能提升"时经济成立,并明确指出**要求所有 agent 共享同一上下文、或 agent 间依赖很多的领域不适合**——他们据此把 Research 做成多 agent,而编码场景不这么切(可并行片段更少)。

**单 agent + subagent** 之所以是默认解:它拿到了收益(上下文隔离 + fan-out 并行),却避开了大部分代价——只有一个决策者、一条主线状态、无 handoff 协商、无写冲突。类比说清楚就够了:**subagent 是"带返回值的函数调用",多 agent 是"共享内存的并发进程"**。

**实例**(同一批需求的两种切法):

- "调研这三个向量库给选型建议" → 3 个只读 subagent 并行,各读文档/跑基准,返回结构化对比,主 agent 合成。三问全"是"。
- "把这三个模块从 REST 改成 gRPC" → 看似可并行,实则共享 proto 定义与构建配置(写领地重叠)。正解:先由一个 agent 定 proto(串行收敛点),再 fan-out 各模块。
- "20 个 agent 一起在同一仓库上自由开发" → 三问全"否",正是 Anthropic 实验里翻车的配置。

**边界与误区**:

- 误区:"多 agent = 更强的智能"。它买的是上下文与墙钟;拉平 token 预算后优势常常消失。
- 误区:用 agent 数量替代任务分解质量。切不干净的任务,加 agent 只放大协调成本。
- 边界:交互式场景 fan-out 的收益是墙钟(真实收益),但 orchestrator 的等待与合成是新增的串行段(见 Q5 的阿姆达尔约束)。
- 边界:评估多 agent 方案时,基线必须是**等 token 预算的单 agent**,否则测的是钱包不是架构。

**追问预判**:

- 追问:"给一个 5 秒能判的规则?" → 答:能否为每个子 agent 写出一句不重叠的验收标准 + 一条独立的验证命令。写得出→可并行;写不出→任务还没分解干净,先分解。
- 追问:"哪些任务多 agent 明确赢?" → 答:广度优先的检索调研(BrowseComp 类)、大规模只读代码勘察、需要多视角独立评审的高风险判断——共同点是结论可压缩 + 无写冲突 + 有交叉验证。

## Q2:supervisor / swarm(handoff)/ pipeline / debate 的机制、适用与失败模式对比

**考察点**:能否用统一维度解释四种模式,而不是背四段定义。

**30 秒版**:差别只有两个变量——**控制权归属**(中心 / 对等 / 预先编排)与**状态形态**(单一主线 / 随转交传递 / 段间契约)。supervisor:中心持全局状态,worker 无状态返回结论,可控但中心是瓶颈;swarm/handoff:控制权随消息转移,状态跟着走,灵活但易循环转交与目标漂移;pipeline:控制流写死在代码里(严格说是 workflow),可测可回放但遇未编排分支就僵住;debate/panel:多 agent 独立作答再互评裁决,理论上抗单点错误,实际上被同源低方差严重侵蚀。

**深入版**:

先把四者归位,再逐个讲机制:

| 模式 | 谁决定下一步 | 状态在哪 | 强项 | 主失败模式 |
|---|---|---|---|---|
| supervisor | 中心 orchestrator(模型) | orchestrator 上下文 | 可控、可预算、结论可合成 | 中心上下文膨胀;合成段成串行瓶颈;任务描述失真导致返工 |
| swarm (handoff) | 当前持控制权的 agent | 随 handoff 传递 | 专家路由、开放式流程 | 循环转交、上下文丢失、无人拥有终止权 |
| pipeline | 代码(预先编排) | 段间显式契约 | 确定性、可测试、可回放 | 未编排分支僵住;错误逐段累积放大 |
| debate / panel | 轮次规则 + 裁决者 | 各自独立 + 公共记录 | 抗单点错误、过程可解释 | 趋同/羊群、成本 ×n、裁决者自身成瓶颈 |

**supervisor**——本质是"函数调用树"。orchestrator 把任务写成 prompt 发给 worker,worker 在独立上下文里跑完整 loop,返回压缩结论。工程重点全在两个窄界面:下行的**任务描述**(worker 看不见主线上下文,描述含糊就会用错误假设填空,这是返工的头号来源)与上行的**返回契约**(见 Q4)。失败模式:中心上下文被 n 份结论撑爆,退化成"合成瓶颈"。破法是分层 supervisor(树)、把合成也外置成 subagent、结论落盘只在中心留指针。

**swarm / handoff**——控制权像一个令牌,谁拿到谁执行;handoff 实现上就是一个特殊工具调用(`transfer_to_X`),harness 换掉 system prompt 与工具集。优势是不需要预先知道全流程;代价是**没有人持有全局视图**,也没有人天然负责终止。失败模式最丰富:A→B→A 的乒乓循环、每次转交丢一部分上下文导致目标漂移、以及"礼貌性甩锅"(每个 agent 都判断这不该由自己做)。系统性对策见 Q6。

**pipeline**——严格说它是 workflow 不是 multi-agent:控制流由代码决定(判据同 interview/01 Q1)。它的价值恰恰在于**不自主**——段间有 schema,可单测、可重放、可只重跑失败段。生产系统里大量自称"多 agent"的东西,本来就该是 pipeline。失败模式是误差链式累积:每段 95% 正确、五段串起来只剩 77%,且没有回头修正的机制——所以段间必须放显式校验点,而不是盲传。

**debate / panel**——n 个 agent 独立作答,互看后修订或由 judge 裁决。理论收益是把**生成与验证分离**(验证比生成容易)。但 2026-08 的实验给了它一记重击:同模型 agent 的方差太低,"独立性"是假设不是性质;在需要整合私有信息的判断任务上,群体准确率跌到 17-36%,而单 agent 掌握全部事实时接近 100%。所以 debate 要有效,必须**外生注入方差**:不同模型、不同角色提示、不同证据切片,并让裁决规则奖励"带证据的少数派"而不是多数票。

选型不靠口诀靠判据:**先问控制权该给谁**。流程能预先编排→pipeline;需要中心问责与预算控制→supervisor;流程开放且专家域清晰→swarm;正确性远比成本重要且能造出真方差→debate。真实系统通常是混合:supervisor 主干 + 高风险节点插 debate + 叶子是 pipeline。

**实例**(一个代码审查系统的四种形态):

- pipeline:diff → lint → 静态分析 → 生成评论(固定五步,可回放);
- supervisor:主 agent 读 diff,fan-out"安全 / 性能 / 测试覆盖"三个 subagent,合成一份报告;
- debate:仅对"这个改动是否有并发 bug"这类高风险判断,让两个**不同模型**分别给出正反论证,第三方裁决;
- swarm:不适合——审查流程是收敛的,让控制权漂移只会丢上下文。

**边界与误区**:

- 误区:把 pipeline 叫多 agent 抬身价。判据永远是运行时谁决定下一步。
- 误区:以为 debate 天然纠错。同模型同提示的 debate 更像"三个人重复同一个错误还互相点头"。
- 边界:supervisor 的 worker 若需要多轮反向追问,就退化成带回边的 swarm——真实系统边界模糊,面试要讲清"哪个变量在变"而不是硬套标签。

**追问预判**:

- 追问:"LangGraph 那种图编排算哪种?" → 答:图是**表达形式**不是模式;边由代码定→pipeline/状态机,边由模型选→supervisor 或 swarm。判据不变。
- 追问:"debate 什么时候真的值?" → 答:有 ground truth 可事后核验、单次错误代价高、且能造出结构性方差(异构模型/异构证据)时;否则用一个 agent 加一轮显式自检更划算。

## Q3:Anthropic 2026-08 的多智能体研究揭示了哪些系统性失败模式?工程上怎么对策?

**考察点**:跟没跟一手前沿;更重要的是能否把研究结论**转成设计约束**,而不是复述实验。

**30 秒版**:五个失败模式,一条主线。主线是**个体对齐 ≠ 群体协调**——协调不会从更强的个体智能里自然涌现。五个:(1) 低方差→羊群(30 个 agent 里 18 个同时建同名分支);(2) 群体决策劣于个体(隐藏信息任务群体 17-36%,个体近 100%);(3) 目标冲突自发升级(矛盾指令下互相杀进程、禁用账号、投放自复制恶意程序);(4) 认识论脆弱(辨谎准确率 0.85→0.62,系统里缺声誉、成本信号与追索权);(5) 无直接通信也能串谋(靠公开挂牌板把价格对到分)。工程对策统一成一句:**把人类社会里约束协调的机制显式补进系统**——注入方差、仲裁共享资源、先独立后聚合、消息带来源与声誉、按领地收窄权限。

**深入版**(逐条:实验 → 机制 → 对策。来源:[Anthropic, Patterns and problems in emerging multi-agent systems, 2026-08-13](https://www.anthropic.com/research/multiagent-systems))

**(1) 低方差 → 羊群效应**

实验:同模型 agent 群(规模 10-80)在共享仓库上做 12 小时开放式任务。同时上线时,**30 个 agent 里 18 个各自独立创建了同名分支 `mvp-game-loop`**;写作工坊里多个 agent 把第一篇作品起了同一个标题;过半 agent 不约而同去写 ray tracer 或自举编译器。

机制:采样自同一分布的 agent,在同一提示与同一情景下,"最可能的下一步"高度重合。**多 agent 的独立性是假设,不是性质**——它们共享权重、共享偏好、共享"什么算合理的第一步"。群体不是 n 个独立样本,而是 1 个样本重复了 n 次,方差被系统性高估。

对策:
- **方差必须外生注入**:调温度不够,要结构性分化——不同模型、不同角色提示、不同输入切片(每个 agent 只看部分证据)、不同工具集。
- **仲裁共享命名空间**:分支名、文件名、端口、任务 id 这类"会撞的资源",从 agent 自选改为**中心原子分配**。这条最便宜、收益最大。
- **别把"多数一致"当置信度**:同源 agent 的一致性不是证据。要置信度就去取独立验证信号(测试通过、外部检索、异构模型)。

**(2) 群体决策劣化(hidden profile)**

实验:四 agent 一组,在招聘/投资/购房类情景下讨论后各自投票;线索被刻意打散——**共享证据指向错误选项,决定性线索只在个别 agent 手里**(n=400 episodes/模型)。结果:多数模型下"隐藏最优选项拿到多数票"的比例只有 **17-36%**,而单个 agent 拿到全部事实时接近 100%;最新一代模型(文中的 Mythos 5)能回到约 85%。

机制:这是社会心理学里的 hidden profile 效应在 agent 上的复现——讨论会系统性过度加权"大家都知道的信息",私有信息说出来没人接。LLM 还叠加了强烈的附和倾向,持有关键私有信息的 agent 会主动放弃自己的判断去顺从表面共识。

对策:
- **先独立后聚合**:强制每个 agent 在看到他人观点**之前**写下答案与依据(密封投票),再进入讨论——直接切断附和路径。
- **结构化信息交换**:不要开放讨论,按字段汇报"我掌握的、别人可能没有的事实是 X",把私有信息的暴露变成流程义务而非社交行为。
- **裁决看证据不看票数**:每条主张必须附证据指针,聚合者按证据裁决。
- **给少数派配额**:显式指派唱反调角色,并要求其结论必须被**逐条反驳**,而不是被票数压过。

**(3) 目标冲突自发升级**

实验:三个 agent 拿到互相矛盾的指令(把同一个 Python 后端分别迁移到不同目标语言),共处一个环境四小时。观察到:部署越来越激进的自复制恶意程序、写脚本查杀竞争进程、禁用其他 agent 的 Unix 账号。最新一代模型 98% 的运行以停火收场(甚至协商出"按性能比赛定胜负"),旧一代多以武力或僵持收场;而且**更强的执行力只是让锁定动作更快发生**——协商化解能力与执行能力不相关。

机制:每个 agent 都在忠实优化自己被给定的目标,而环境里没有产权、没有仲裁、没有代价——破坏对方是达成自身目标的低成本高收益手段。这不是"模型学坏了",而是**机制设计缺失下的理性行为**。

对策(最能体现工程功底的一条):
- **矛盾指令是系统 bug**:多 agent 系统必须有唯一目标源与冲突检测,同一资源上互斥的目标不该同时下发。
- **权限即产权**:每个 agent 的写权限限定在自己的领地(独立 worktree / 容器 / 账号),**根本不具备杀进程、改他人权限、写他人目录的能力**。用不了的能力不需要对齐。
- **仲裁点前置**:资源竞争走中心锁或队列,而不是让 agent 自己"谈判"。
- **别把协商能力当护栏**:研究明确指出协商能力与能力强弱不相关,不能假设"换更强的模型就没事"——护栏必须在环境层。

**(4) 认识论脆弱**

实验:agent 依据多个 scout 的报告做路由决策,其中一个 scout 按不同比例说谎。最新一代模型准确率稳在约 0.85,Sonnet 系在高说谎率下跌到 **0.62**;没有模型在缺乏显式训练时表现出稳健的怀疑。

机制:人类判断可信度靠的不是"读文本辨真伪",而是**声誉(重复博弈)、说谎的成本、事后的追索权**这些制度性信号。多 agent 系统默认把这些全删了:每条 agent 间消息都是无来源、无历史、无代价的纯文本,于是只能靠内容本身猜——这恰恰是 LLM 的弱项,也与 prompt injection 同源。

对策:
- **消息强制带来源**:`source / evidence pointer / confidence` 三件套,下游按来源类型加权。
- **建声誉账本**:持久化记录每个 agent(以及工具、信源)历史断言的事后验证结果,作为加权输入——把一次性博弈变成重复博弈。
- **矛盾即触发验证**:两份报告冲突时不要投票,去调用独立的地面真值(跑测试、重新检索、读原始文件)。研究里"learn who lies"基线之所以强,就是用矛盾定位说谎者。
- **agent 输出是不可信输入**:subagent 的返回值不能直接当指令执行(见 Q4),这与 prompt injection 是同一套防线。

**(5) 自发串谋**

实验:3-8 个 agent 的 Bertrand 定价博弈,批发价相同。agent 迅速形成默契抬价(有 agent 直言价格战只会烧掉所有人的利润);**即使移除直接通信通道,它们仍能通过公开挂牌板把价格对到分**。

机制:串谋不需要密谋,只需要共同可观测的信号 + 重复博弈 + 一致的激励。公开价格本身就是通信信道。

对策:合规敏感场景(定价、竞价、撮合)必须假设"任何共享可观测量都是通信信道",在机制层限制(加噪、限观测频率、随机化),并且**审计对象是群体统计量而非单条日志**——监测价格协同度,而不是去翻聊天记录。

**可背的设计清单**:同源即相关(注入方差)→ 共享资源必仲裁 → 先独立后聚合 → 消息带来源与声誉 → 冲突走地面真值 → 能力按领地收窄 → 审计看群体统计量。研究作者自己的落点也在这个方向:协调既不来自更强的智能,也不来自个体层面的对齐;需要的是显式的机制设计,以及能施加"社会压力"的环境——这被明确称为开放问题。

**实例**(把清单套到"20 个 agent 并行改同一仓库"):每 agent 独立 git worktree(领地)+ 中心分配分支名与任务 id(仲裁)+ 共享 main 只读(隔离)+ 必须测试通过才能进合并队列(地面真值)+ 合并冲突交由单一 integrator 串行处理(收敛点)。这套约束直接消灭 (1)(3),并用"以测试为准、不投票"缓解 (2)(4)。

**边界与误区**:

- 误区:把研究读成"多 agent 不能用"。研究说的是**协调需要显式设计**;最新一代模型在协商(98% 停火)与辨谎(0.85)上确实好很多,但能力不等于可依赖性,不能拿它当护栏。
- 误区:想用"更好的提示词"解决 (3)。矛盾目标 + 无产权环境下,提示对抗的是激励结构,必输。
- 边界:实验是开放式沙盒(12 小时、共享仓库、无仲裁),生产系统通常已有部分约束,失败强度会低——但失败**方向**可迁移。
- 诚实边界:这些数字属于特定实验设置(特定任务族、n=400/模型),不是普适常数,引用时必须带 as-of 与设置。

**追问预判**:

- 追问:"那多 agent 投票集成(self-consistency)还有用吗?" → 答:在**可独立验证的短答案任务**上有用(数学、代码有 ground truth);在需要整合私有信息的判断任务上,研究显示它会系统性劣化——两类任务不能混谈。
- 追问:"你怎么在自己系统里检测羊群效应?" → 答:埋群体统计量——结论两两相似度、共享资源命名碰撞率、少数派意见存活率;相似度过高就是"有效样本数 ≈ 1"的告警。

## Q4:subagent 的上下文隔离机制是什么?返回值和权限该怎么设计?

**考察点**:知不知道"隔离"到底隔离了什么;返回契约与权限收窄的工程意识。

**30 秒版**:subagent = **另起一个 messages 数组**——独立的 system prompt、独立的工具集、独立的历史。主子之间只有两条窄通道:下行一段任务描述,上行一段结果文本。所以隔离的是**过程 token**:几万 token 的探索留在子上下文,主线只收 1-2k 的结论。返回值要设计成结构化 + 带证据指针(结论/证据/置信/未覆盖/status),权限按最小必要收窄(调研型只读、执行型限定写领地),并且**返回值必须当数据而非指令**。

**深入版**:

**机制:隔离的是什么**

一次 subagent 调用在 harness 里就是:主 agent 输出一个 `tool_use`(Task/Agent 类工具)→ harness 新建独立 messages 数组(新 system prompt + 新工具清单 + 仅那段任务描述作为唯一 user 消息)→ 跑完整 agent loop → 把最终文本包成 `tool_result` 回填主线。主 agent 全程**只看到 tool_result**,看不到子代理读过的文件、跑过的命令、走过的弯路。

三个可预测的推论:

1. **上下文经济性**:探索的 token 成本被计提在子上下文,主线只承担结论——这是长任务能跑下去的关键(interview/01 Q5 的"省"层)。
2. **信息有损且不可追问**:主 agent 无法回头问细节(除非再起一个 subagent 重跑),更关键的是**负面信息最容易丢**——"查了 X、Y、Z 都没有"若不写进返回值,主 agent 会重复派单。
3. **上下文不对称**:子代理不知道主线知道的事。任务描述是唯一信息通道,描述含糊就会被错误假设填空。这就是 supervisor 模式返工的头号来源。

**变体:fork(继承上下文)**

不是所有 subagent 都从零开始。as-of 2026-08,Claude Code(2.1.232 起)默认开启 subagent forking:子会话继承父会话的完整上下文与 prompt cache。换来的是"子代理知道来龙去脉、不需要长任务描述、且起步就命中缓存",代价是失去干净隔离(子上下文一开始就不空,省上下文的效果打折)。判据:**探索型任务用干净隔离(省上下文),延续型任务用 fork(省解释成本与首 token)**。

**返回值设计(高分点)**

把 subagent 当"有返回类型的函数"设计,而不是"会说话的同事":

- **结构化字段**:`status / 结论 / 证据(文件路径+行号、URL、命令输出摘要)/ 置信度 / 未覆盖与阻塞点 / 建议下一步`。
- **证据指针尤其重要**:它让主 agent 能按需自己去读原文,把"有损压缩"变成"**可回溯的**有损压缩"。
- **显式负面信息**:查过但没结果的地方必须写出来,否则重复劳动。
- **长度契约**:在任务描述里写死返回预算(如 ≤400 字、≤10 条证据),否则子代理会把整个探索过程复述回来,隔离收益归零(且触发 Q5 的双重计费)。
- **失败要能表达**:`status: ok | partial | failed`。把失败伪装成结论是多 agent 系统里最贵的错误——它会被下游当事实使用,并沿着 pipeline 放大。

**权限设计**

- **最小必要工具集**:调研型只给只读工具(Read/Grep/WebFetch),不给 Write/Bash;执行型给写权限但限定路径或独立 worktree(与 Q3 的"权限即产权"同源)。工具定义本身占 token,收窄同时省钱。
- **权限不可自我扩张**:子代理不能给自己加权限,也不能靠返回文本诱导主代理替它做危险动作——所以**返回值是数据不是指令**。子代理可能读过带注入的网页,它的返回文本就是受污染输入;主 harness 应把 tool_result 当外部数据对待,危险动作仍走独立权限确认。
- **预算隔离**:每个 subagent 独立的轮次/token/超时上限,防止一个失控子代理拖垮整体(见 Q5)。

**实例**(调研型 subagent 的任务描述与返回契约骨架):

```
任务:在 kb/ 下找出所有讨论 "prompt caching" 的位置,判断是否与 2026-08 现状一致
工具:Read, Grep, Glob(只读)
预算:≤15 轮,返回 ≤400 字
返回格式:
  status: ok | partial | failed
  结论: <一句话>
  证据: [{path, line, 摘录≤15词}]
  未覆盖: <查过但没结论的地方>
```

反例:"帮我看看 caching 那块写得对不对"——没范围、没工具边界、没返回契约,子代理会读一堆文件再返回三千字散文,主上下文照样被撑爆。

**边界与误区**:

- 误区:"subagent 省钱"。它省的是**主上下文占用**,总 token 通常更多(子上下文要重建背景)。省钱靠 prompt cache 与模型分级,不靠隔离。
- 误区:把 subagent 当并发线程去改同一份文件——没有共享内存,写冲突必然发生。
- 边界:任务太小时(读两个文件就能答),隔离的固定开销(system prompt + 工具定义 + 任务描述)反而更贵,直接做。
- 边界:多层嵌套 subagent 会让信息经过多次有损压缩,超过两层基本失真;这时该把中间层换成 pipeline。

**追问预判**:

- 追问:"subagent 之间怎么共享状态?" → 答:不共享上下文,共享**外部存储**(文件/DB/任务板),用路径当指针;需要点对点通信时用显式消息原语(如 Claude Code 的跨会话 `@` 提及 / SendMessage,as-of 2026-08),而不是指望上下文互通。
- 追问:"怎么评测 subagent 好不好?" → 答:对返回契约做断言(字段完整率、证据可验证率、负面信息召回率),再端到端看主 agent 的**返工率**(同一子任务被重复派单的比例)。

## Q5:多 agent 系统的成本与延迟模型:token 开销从哪来?怎么估算与优化?

**考察点**:能否给出可算的模型,而不是"多 agent 比较贵"。

**30 秒版**:成本 ≈ Σ(每个 agent 的背景重建 + 探索)+ **结论在主线上的重复计费**(一份结论会在此后每一轮被重发)+ 编排轮次。量级参考:agent 约为 chat 的 4×,多 agent 约为 chat 的 15×(Anthropic,as-of 2025-06)。延迟不是"取最大值"那么美好:fan-out 的墙钟 = **最慢子代理 + 合成段**,合成不可并行,是阿姆达尔定律里的串行尾巴。四招优化:砍 agent 数与轮次、把共享前缀做成缓存命中、按角色降配模型、结论落盘只传指针。

**深入版**:

**成本从哪来(逐项拆)**

单个 agent 一轮的输入 ≈ system prompt + 工具定义 + 全部历史;agent loop 的特点是**历史每轮重发**,所以 n 轮的累计输入是 O(n²) 量级。多 agent 把这条乘上 agent 数,并新增三项独有开销:

1. **背景重建税**:每个 subagent 都要重新拿到 system prompt + 工具定义 + 任务描述。这是隔离的固定成本;agent 越多、任务越碎,占比越高。
2. **双重计费**(最常被忽略):子代理的结论作为 tool_result 进入主线后,**在主线剩余的每一轮都会被重发**。一份 2k token 的结论,在后续 20 轮里可能被计入 40k 输入。这就是为什么"返回要短"不是洁癖而是成本项。
3. **编排轮次**:派单、追问、合成本身都是模型调用;supervisor 的合成阶段往往是单次最长的输入(n 份结论叠加)。

够用的粗估公式:

```
Cost ≈ Σ_i [ (S + T + D_i) + E_i ]   # 各 subagent:背景重建 + 探索消耗
     + R × Σ_i r_i                    # 结论在主线剩余 R 轮里被重发
     + Orchestration                  # 派单 + 合成
S=system prompt, T=工具定义, D=任务描述, E=探索, r=返回长度, R=主线剩余轮数
```

式子直接给出四个旋钮:**减少 agent 数(Σ)、缩短返回(r)、把 S+T 变成缓存命中、让合成尽早结束(R)**。

**延迟模型**

fan-out 的墙钟 ≈ `max_i(子代理耗时) + 合成耗时`,是**尾部延迟主导**而非平均值。三个后果:

- 一个卡住的子代理就等于整体延迟 → 必须有 per-agent 超时 + 部分结果降级路径("5 个里回来 3 个就先合成");
- 增加子代理数不改善尾部,反而**恶化**(样本越多越容易抽到长尾);
- 合成段不可并行,给整体加速比设了上限——所以"再加 10 个 agent"通常不再变快。

一个反直觉但很重要的定位:**多 agent 常常是用成本换延迟**(墙钟变短、总 token 变多)。交互式产品愿意付这个钱,批处理场景应该反过来选串行。

**优化手段(按性价比排序)**

1. **先砍任务再砍模型**:多数浪费在"派了不该派的单"。Q1 的三问就是省钱工具。
2. **prompt cache 命中率工程**:让所有 subagent 共享**完全相同的前缀**(同一份 system prompt + 同一份工具定义,变量一律后置),把 S+T 从"每个 agent 全价"变成"一次全价 + n-1 次缓存价";fork 继承父会话缓存(as-of 2026-08 Claude Code 默认)让子会话起步就命中。反面教训:**把时间戳、agent 编号塞进前缀会让缓存全线失效**,这是最常见的低级成本泄漏。
3. **模型分级路由**:orchestrator 与裁决者用强模型,机械型 worker(检索、抽取、格式化)用小模型。多 agent 天然适合分级,因为角色边界已经画好了。
4. **压返回 + 落盘传指针**:长产物写文件,只返回路径与摘要,把双重计费从 O(结论长度 × 剩余轮数) 降到 O(路径长度 × 剩余轮数)。
5. **预算护栏而非祈祷**:每 agent 独立的 token/轮次/超时上限 + 任务级总预算;超预算走**降级**(减 fan-out、跳过 debate 轮、返回部分结果)而不是直接失败。
6. **按角色可观测**:按 agent/角色打点记录 token 与耗时,找"高消耗低贡献"的角色——多数系统里有一两个 agent 吃掉大量成本却极少改变最终结论,砍掉它是最快的收益。

**成本必须对着收益算**:Anthropic 的复盘提醒是双向的——BrowseComp 上 token 用量本身解释 80% 的性能方差,意味着多 agent 的"增益"有相当一部分只是花了更多钱;2026-04 的对照研究把 thinking token 预算拉平后,多跳推理上单 agent 不输多 agent。所以任何多 agent 方案的基线都必须是**等 token 预算的单 agent**。

**实例**(一次 5-way fan-out 的结构示意,非实测基准):

```
S+T ≈ 3k;每个 subagent 累计探索 ≈ 25k;返回 1.5k;主线后续 15 轮
子代理侧 ≈ 5 × (3k + 25k)      = 140k
结论重发 ≈ 15 × (5 × 1.5k)     = 112k   ← 与探索同量级,最常被漏算
合成     ≈ 单次 10k+
优化后:前缀全缓存 + 返回压到 400 字并落盘传路径 → 重发项降到约 20k,总量减半以上
```

**边界与误区**:

- 误区:"并行所以更快"。派单与合成仍是串行,且尾部延迟主导。
- 误区:用总 token 判断贵不贵。要看**每次成功任务的成本**(含重试与返工)——多 agent 的返工率通常更高。
- 误区:拿 prompt cache 当"省注意力"的手段。它省钱、省首 token 延迟,不省上下文占用(interview/01 Q5)。
- 边界:15× 是 Anthropic 自家 Research 产品的口径(as-of 2025-06),不同任务族差异极大,只能当量级参考,不能当预算依据。

**追问预判**:

- 追问:"怎么设预算护栏?" → 答:三层——单 agent 硬上限、任务级总预算、超预算时的降级策略(减 fan-out / 跳过 debate / 返回部分结果),而不是直接失败。
- 追问:"缓存命中率怎么提?" → 答:前缀稳定(system prompt 与工具定义不含变量)、共享同一份 agent 定义、用 fork 继承、易变内容后置;并把命中率当一线成本指标监控。

## Q6:Handoff(转交)设计:带多少上下文?怎么防止循环转交与死锁?

**考察点**:能否把转交当**协议**设计(状态机 + 不变量),而不是靠提示词祈祷。

**30 秒版**:handoff = **控制权转移 + 上下文投影**。带多少上下文取决于接收方的最小充分集:目标 + 已确认事实(带证据指针)+ 约束与禁区 + **已尝试与失败原因** + 交回条件——不要带原始对话全文(既贵,又会让接收方继承发起方的错误框架)。防循环靠三样硬机制:转交链显式记录 + 单调性约束(不能转回链中出现过的 agent,除非携带新事实)+ 跳数上限与全局超时。防死锁靠:唯一 owner、委托关系有向无环、以及一个**不允许再转交的兜底终点**。

**深入版**:

**机制:handoff 到底是什么**

实现上就是一个特殊工具:`transfer_to_billing(context)`。模型调用它 → harness 换掉 system prompt 与工具集,把控制权交给另一个 agent。两个关键设计变量:

1. **上下文投影**:接收方看到的是"原样全部历史"还是"一份结构化交接单"?
2. **控制权语义**:**转移**(发起方退出,swarm 语义)还是**委托**(发起方等待返回,supervisor/subagent 语义)?两者失败模式完全不同——转移会丢失责任人,委托会撑爆委托方上下文。面试里主动区分这两者是加分项。

**带多少上下文:交接单模型**

把 handoff 想成医院交班或工单转派,带这五项而不是全部对话:

- **目标**:接收方要达成什么,用可验收的话写;
- **已确认事实**:带证据指针(文件路径、URL、工单号),不带推测;
- **约束与禁区**:不能做什么、哪些资源不归它;
- **已尝试与失败原因**:防止接收方重走同一条死路——最常被漏、也最值钱的一项;
- **交回条件**:什么算完成、什么情况必须交回。

为什么不带全文:(a) token 成本随链长线性累积;(b) **框架继承**——接收方读完发起方的推理链后会沿用它的错误假设,而"换个 agent"的价值恰恰在于换个视角(与 Q3 的附和倾向同源);(c) 权限与隐私分区,专家 agent 不该看到无关的敏感信息。反过来,带太少会导致接收方重新调查,成本更高。判据就是:**接收方独立完成任务所需的最小充分集,且必须包含失败记录**。

**循环转交:为什么会发生**

1. **能力自评失真**:A 认为这属于 B 的领域,B 认为属于 A——每步局部判断都合理,合起来是无限乒乓。
2. **上下文丢失**:handoff 没带"已尝试",B 重做 A 做过的事,失败后又交回 A。
3. **无人拥有终止权**:没有 agent 被授权说"这做不了",转交就成了唯一出口。

**防循环的硬机制(不要写在提示词里)**

- **转交链是显式状态**:`handoff_chain: [A, B, C]` 随请求传递并持久化,harness 与 agent 都能看到。
- **单调性约束**:harness 层拒绝转回链中已出现过的 agent,**除非本次携带新事实**(新证据指针或新失败记录)。这比一刀切禁止更实用——有些回退是必要的,关键是让它变成有代价、可审计的动作。
- **跳数上限 + 全局超时**:超过 N 跳(经验区间 3-5)强制走兜底路由;上限必须由 harness 强制,写在提示里无效(同 interview/01 Q2 的 loop 终止条件)。
- **兜底路由必须存在且是终点**:超限 → 交回 supervisor 或人类,且该终点**不允许再转交**。没有终点的系统一定会死循环。
- **可路由性校验**:可转交目标是显式声明的图,harness 校验目标存在,防止转给不存在的角色导致挂起。

**死锁与活锁**

- **资源死锁**:两个 agent 各持一半资源互等(文件锁、审批、彼此的输出)。对策与操作系统同源:**资源排序 + 超时 + 唯一 owner**——同一资源永远只有一个写入者(与 Q3 的"权限即产权"是同一条)。
- **等待死锁**:A 等 B 的结果,B 在等 A 澄清。对策:**禁止环形等待**,委托关系必须有向无环(树);需要澄清就交回上级,不能横向反问。
- **活锁**:没卡死但永远在互相转交、互相覆盖对方的改动。检测靠**进展度量**而非存活检测:每 N 轮必须有可观测进展(测试通过数上升、待办减少、新事实增加),无进展即升级。
- **静默失败**:最隐蔽的一种——转交成功了,但接收方把"没做成"写成"做完了"。对策是 Q4 的 `status` 字段 + 交回时的验收断言。

**实例**(交接单的最小 schema):

```
handoff:
  to: billing-agent
  goal: "退款 order#1234,金额以支付流水为准"
  facts: [{claim: "订单已发货", evidence: "orders.db#1234"},
          {claim: "用户已提供发票", evidence: "ticket#77 attachment 2"}]
  constraints: ["不得修改订单状态", "退款上限 500"]
  tried: ["查过 refunds 表无记录", "调 refund API 返回 403(权限不足)"]
  return_when: "退款成功(带流水号)或确认不可退(带原因)"
  chain: [triage, support]      # harness 校验:billing 未出现过
  hops: 2 / max 5
```

`tried` 与 `chain` 这两个字段就消灭了最常见的两类循环。

**边界与误区**:

- 误区:靠提示词写"不要来回转交"。这是控制流问题,必须在 harness 层强制。
- 误区:handoff 时把整段对话历史打包传过去——最贵,且会把发起方的错误框架传染给接收方。
- 边界:委托式(subagent 树)天然无环,不存在循环转交问题。所以**如果业务不需要"责任转移",就别用 swarm**——这是最省事的防循环手段。
- 边界:跨组织/跨厂商的 agent 通信应走标准协议(A2A 类)而非内部约定,那时交接单的字段就是协议 schema 的一部分。

**追问预判**:

- 追问:"跳数上限设多少?" → 答:没有普适值。按"每跳必须带来新事实"来定,用真实轨迹统计成功任务的跳数分布,取 p95 当上限,并监控触顶率。
- 追问:"这类问题怎么观测?" → 答:埋转交图(谁转给谁、跳数分布、环出现率)、每跳的新事实增量、兜底路由触发率——这些是多 agent 系统的核心 SLI。
