# 面试题:02 上下文工程

> 每题讲透五件套:本质 / 机制 / 实例 / 边界 / 检验(追问预判)。答案分 30 秒版 + 深入版。
> 与 [01 Agent 基础](01-agent-fundamentals.md) Q5(省/压/存/续四层方案)衔接:那题讲**方案分层**,这一组讲**每层的机制**。

## Q1:上下文窗口为什么会"性能先于容量耗尽"?讲讲注意力退化的机制与工程含义

**考察点**:能否从 transformer 机制推导出退化,而不是复述 "context rot" 这个词;能否把机制翻译成可执行的工程规则。

**30 秒版**:窗口容量是硬约束,但**有效上下文远小于标称容量**。三层原因:(1) softmax 注意力是**竞争性归一化**,候选越多、干扰项与目标越像,选中正确 token 的稳定性越差——退化的本质是"选不准"而非"记不住";(2) 长上下文能力是训练分布的产物,标称 1M 不等于在 1M 处保持 4K 处的质量;(3) agent 特有的**信噪比劣化**:工具输出、失败尝试、被推翻的计划持续堆积。工程含义:上下文预算是**质量预算**,必须做准入控制(admission control),而不是等窗口满了再救。

**深入版**:

**1. 注意力层面:为什么长 = 差(第一性原理)**

注意力权重是 `softmax(QKᵀ/√d)`,softmax 在**全部候选 key 上归一化**。序列变长意味着两件事同时发生:分母里的竞争者变多,且相似度分布变平。于是正确信息拿到的相对权重下降——这不是"遗忘",是**信号被稀释**。由此可以推出三个非平凡的结论:

- **退化主要由干扰项的语义相似度驱动,不只由长度驱动**。Chroma 的 Context Rot 报告(2025,覆盖 18 个模型)与 NoLiMa(2025)都指向同一现象:当"针"与"草堆"语义接近、或需要一次隐式推理跳转时,准确率在远未到窗口上限时就开始掉;而字面匹配式的 NIAH(needle-in-a-haystack)几乎满分。**"NIAH 满分" 因此不能作为长上下文可用的证据**。
- **位置有偏**。"Lost in the Middle"(Liu et al., 2023)给出 U 型曲线:开头与结尾的信息被更好利用,中段最容易被忽略。直接推论:**必须被遵守的规则要么放最前(系统提示 / CLAUDE.md),要么放最近一条消息,不要埋在中段**。
- **反直觉的一条**:结构连贯的长文本比打乱顺序的同等长度文本更拖累注意力质量(Chroma 报告的观察之一,as-of 2025)。原因与上面同源——连贯文本提供了更多"看起来相关"的竞争者。

**2. 训练与评测层面:标称长度 ≠ 有效长度**

RULER(2024)一类合成基准反复显示,模型的"有效长度"显著小于标称长度,且随任务复杂度进一步缩短。as-of 2026-08,主流旗舰 API 模型标称已到 1M 级(Anthropic 当前一代模型的上下文窗口为 1M),但**没有一个跨模型通用的"有效长度"常数**——必须按自己的任务分布实测。任何"我们上了大窗口所以不用管上下文"的说法都要打折。

**3. agent 特有的第三层退化(harness 层,最容易被面试者漏掉)**

agent 的上下文里塞的不是散文,而是:工具定义、文件全文、命令输出、失败的尝试、被推翻的方案。其中**"过时的正确信息"最毒**——三轮前读到的旧版文件内容、已被否决的实现路径,它们与当前任务**语义高度相关**(所以会在注意力竞争里胜出),但事实上已经错了。这正好解释了官方 best practices 的两条建议:"纠正两次仍不对就 `/clear` 重开"(上下文已被失败路径污染,继续叠加纠正只会加剧竞争),以及"无关任务之间 `/clear`"。官方原文把这条约束写在了全篇最前面:上下文窗口是**最需要管理的资源**,性能随其填充而退化。

**4. 从机制到规则(每条都能推导,不是口诀)**

| 工程规则 | 由哪条机制推出 |
|---|---|
| 相关性优先于完整性,宁少勿全 | 干扰项相似度是退化主因 |
| 硬约束放头部(CLAUDE.md)与尾部(最近消息) | U 型位置偏置 |
| 无关任务之间 `/clear`,而不是接着聊 | 信噪比 |
| 大规模探索交给 subagent,只回传结论 | 只让结论参与注意力竞争(见 Q6) |
| 上下文占用必须**可观测**(`/context`、statusline) | 不可观测就不可管理 |

**实例**(Claude Code 官方"上下文窗口走查"给出的启动占用,as-of 2026-08,为示意量级):

```
system prompt 4,200 + project CLAUDE.md 1,800 + auto memory 680
+ skill descriptions 450 + ~/.claude/CLAUDE.md 320 + env info 280
+ MCP 工具名(schema 延迟加载)120  ≈ 7.8K —— 一行代码都还没读
```

随后:读一个文件 1,100–2,400 tokens,一次 grep 约 600,一次 `npm test` 输出约 1,200。"调查一下这个模块"读 30 个文件就是几万 token——**而质量曲线在到达窗口上限之前就已经开始下弯**。

**边界与误区**:
- 误区:"退化 = 超出窗口被截断"。截断是**硬失败**(可见、会报错);退化是**软失败**(不可见,表现为悄悄变笨)——后者才危险。同理"NIAH 100% 说明长上下文没问题"也站不住:字面检索 ≠ 跨段聚合 + 隐式推理的真实任务。
- 边界:确实存在"该让上下文长起来"的场景——深陷单一复杂问题时,历史本身就是有效信号,强行 `/clear` 会丢关键前提。官方 best practices 明确保留了这个例外。
- 不确定项:各家"有效长度"的具体数值随模型与任务变化很大,坊间流传的百分比多来自二手博客,**面试里不要当硬数据引用**。

**追问预判**:
- 追问:"那给我 10M 窗口是不是就解决了?" → 答:容量与质量是两条曲线。更大窗口解决**截断**,不解决**竞争性稀释**与信噪比;而且延迟、成本、缓存命中率都随长度恶化。窗口增大改变的是策略的参数(阈值往后挪),不是策略本身。
- 追问:"怎么量化你系统里的有效上下文?" → 答:构造**带干扰项的任务级探针**(不是 NIAH),在 4K/32K/128K 分档测准确率与指令遵循率,取拐点作为工程预算上限;线上则监控退化的行为学信号——compaction 触发频率、重复读同一文件的次数、同一错误被纠正的轮数。

## Q2:Compaction(上下文压缩)的机制是什么?保留策略怎么设计?

**考察点**:能否讲清"压缩是有损**再生成**"这一本质;能否把保留清单从判据推导出来,而不是背一份清单。

**30 秒版**:compaction = 逼近窗口上限时,把旧历史交给模型**再生成为一段摘要**,用摘要替换原文,在同一个任务里继续。它是**有损、不可逆、且由模型执行**的操作,所以三件事必须设计:何时触发、先做什么(通常先清最没信息密度的旧工具输出,不够再摘要)、保什么。保留策略的唯一判据是:**摘要之后,agent 能不能只靠"摘要 + 外置文件"重建现场并继续干活**。

**深入版**:

**1. 先把四种操作分开(高分区分点)**

| 操作 | 做什么 | 有损性 | 典型触发 |
|---|---|---|---|
| clear / 新会话 | 丢弃整段历史 | 全损,但**可控** | 任务切换 |
| context editing(裁剪) | **删除**旧 tool_result / thinking 块 | 有损但**确定性**(规则决定删什么) | 工具输出堆积 |
| compaction(摘要) | 把历史**再生成**成摘要 | 有损且**非确定性**(模型改写) | 逼近窗口上限 |
| memory / 外置 | 写到上下文之外 | 无损(只要真写下来) | 跨压缩、跨会话 |

顺序有硬道理:**先删后压**。删除旧 tool_result 是 O(1)、不花模型调用、不引入幻觉;摘要要多一次推理、有改写风险。Claude Code 的官方描述正是这个顺序——"先清理较旧的工具输出,必要时再摘要对话"(as-of 2026-08)。API 层也把两者做成**互相独立的特性**:context editing 的 `clear_tool_uses` / `clear_thinking` 策略,与 compaction 的服务端摘要块,是两个 beta,不要混称(as-of 2026-08)。

**2. 为什么 compaction 天然危险:它是"模型总结模型自己的历史"**

三类系统性丢失,按代价排序:

- **约束丢失(最贵)**:早期的否定式约束("不要改 migrations""必须用 pnpm")最容易被当作已消化的背景抹掉。官方表述很直白:压缩保留你的请求和关键代码片段,但**早期的细致指令可能丢失**——所以持久规则应放 CLAUDE.md,而不是指望它在对话历史里活下来。
- **失败记忆丢失**:"这条路试过、不行"没被保留 ⇒ 压缩后原地重蹈覆辙。这是最典型的"压缩后突然变笨"。
- **精确值丢失**:行号、commit hash、命令的确切写法被摘成散文,后续要重新取证。

**3. 保留策略怎么推导(而不是抄清单)**

判据一句话:**保留"重建当前工作现场所必需的最小状态",而不是"看起来重要的内容"**。按"丢了会发生什么"分三类:

- **丢了会做错 → 必保**:硬约束与禁止项、验收标准、当前分支与已改文件清单、验证命令、下一步待办。
- **丢了会重做 → 必保**:已排除的方案 + 原因。**负面知识信息密度最高、最省未来 token**,却最常被摘掉。
- **丢了可再取 → 只保指针**:文件全文、长命令输出、已 commit 的 diff 都不保。摘要里写 `src/auth/token.ts:120-180 是刷新逻辑` 远胜于贴 60 行代码——文件还在硬盘上,而 token 不会回来。

落地形态(as-of 2026-08):在 CLAUDE.md 写 `Compact Instructions` 段做**常驻定制**;`/compact <focus>` 做**一次性定制**;`Esc+Esc` / `/rewind` 选中某条消息后 "Summarize from here / up to here" 做**分段压缩**(前者压缩该点之后、保留更早的完整上下文,后者反之)。更强的做法是让 agent 在压缩前主动把状态**写进文件**,摘要里只留"去读这些文件"。

**4. 分层摘要的两个失败模式**

- **递归漂移**:摘要的摘要逐代累积并放大错误,且不可回溯。缓解:让摘要保留**可校验的锚点**(commit hash、文件路径、测试名)使下一代能自我核对;优先按 checkpoint 分段压缩而非整体重摘。
- **压缩抖动(thrashing)**:若单个文件或工具输出大到"压完立刻又填满",系统会陷入压缩循环。Claude Code 的处理是几次尝试后**停止自动压缩并报错**,而不是无限重试(as-of 2026-08)。根因在**准入控制缺失**——不该让那么大的东西整块进来;压缩层救不了准入层的错。

**实例**(可直接抄的保留清单骨架 + 两种触发方式):

```markdown
<!-- CLAUDE.md -->  ## Compact Instructions
压缩时必须逐字保留:
1. 硬约束:不改 db/migrations/*;必须用 pnpm;禁止引入新依赖
2. 已改文件清单(路径 + 一句话说明改了什么)
3. 验证命令:pnpm test -- auth;pnpm build
4. 已排除的方案 + 排除原因(防止重复试错)
5. 未完成待办(编号,注明当前卡在哪一步)
不必保留:文件全文、通过的测试日志、已 commit 的 diff(保 commit hash 即可)
```
一次性定制则是:`/compact 只保留 API 契约变更与未完成的迁移步骤`。

**边界与误区**:
- 误区:"compaction 是压缩算法"。它是**再生成**不是无损编码;把它当 gzip 想会系统性低估风险。
- 误区:"有自动压缩兜底就够了"。自动压缩的目标是**别崩**,不是**别丢**。真正重要的状态必须走外置层(见 [01 Q5](01-agent-fundamentals.md) 的"存")。
- 误区:压缩越早越好。过早压缩会毁掉正在被使用的细节;压缩点应尽量落在**任务的自然边界**(一个子任务收尾、刚 commit 完),此时"现场"最容易被少量文字重建。
- 边界:单轮问答、短任务不需要 compaction——直接开新会话更便宜也更干净。

**追问预判**:
- 追问:"compaction 对 prompt cache 有什么影响?" → 答:毁灭性的。压缩重写了历史 ⇒ 前缀改变 ⇒ 该点之后的缓存全部失效。所以压缩的真实成本 = 摘要生成的一次调用 + 后续请求的缓存重建,不能只按"省了多少 token"算收益(见 Q3)。
- 追问:"怎么评估压缩质量?" → 答:做成回归测试——取真实长会话,在压缩前后分别让 agent 回答一组"现场问题"(改了哪些文件 / 硬约束是什么 / 下一步是什么),比对通过率;或在会话中注入 canary 事实,测其压缩后存活率。

## Q3:Prompt caching 的原理、命中条件与成本收益模型?它和上下文管理是什么关系?

**考察点**:能否说出"前缀匹配"这一唯一不变量并由它推导全部规则;能否算清经济账;能否讲清缓存与上下文管理既正交又冲突。

**30 秒版**:prompt caching 缓存的是**已经算好的前缀 KV 状态**,key 是渲染后字节的**精确前缀**。一个不变量决定一切:**任意位置改一个字节,该位置之后的缓存全部失效**。渲染顺序是 `tools → system → messages`,所以稳定内容必须物理排在前、易变内容排在后。经济上:命中读约 0.1× 输入价,写入约 1.25×(5 分钟 TTL)/ 2×(1 小时 TTL),5 分钟档两次请求即回本。它与上下文管理**正交**:缓存省的是重复计算的钱和延迟,**不省窗口占用,也不省注意力**。

**深入版**:

**1. 原理:为什么缓存粒度必然是前缀**

自回归 transformer 处理 prompt 时做 prefill:逐层算出每个 token 的 K/V。位置 i 的 KV 依赖**全部 < i 的 token**(因果注意力)。所以前缀相同 ⇒ KV 相同 ⇒ 可复用;而"缓存一个片段"或"缓存一个集合"在数学上不成立。由此直接推出三条,而不是靠记:

中间插入一个 token ⇒ 其后所有位置 KV 全变 ⇒ 全失效;换模型 ⇒ 权重不同 ⇒ 缓存**不可跨模型**(所以"主循环里临时换个便宜模型跑子任务"会毁掉整条缓存,正确做法是开 subagent);有 TTL,因为 KV 占存储、不可能永久驻留。

**2. 命中条件(Anthropic Messages API,as-of 2026-08)**

- 显式断点 `cache_control: {type:"ephemeral"}`,**每请求最多 4 个**;默认 TTL 5 分钟,可设 `ttl: "1h"`。打在最后一个 system 块上的断点会把 `tools + system` 一起缓存。
- **最小可缓存前缀是模型相关的**,不足则**静默不缓存**——没有报错,只有 `cache_creation_input_tokens: 0`。官方口径(as-of 2026-06):Opus 5 / Fable 5 为 512 tokens;Opus 4.8 / Sonnet 5 / Sonnet 4.6 为 1024;Opus 4.7 为 2048;Opus 4.6 / Haiku 4.5 为 4096。**注意它不随代次单调**,迁移模型时要重新核对。
- **失效是分层的**,不是全或无:改工具定义或换模型 ⇒ tools/system/messages 全失效;改 system ⇒ system 与 messages 失效但 tools 仍命中;改 `tool_choice`、切 thinking 开关 ⇒ 只影响 messages 层。含义:真正的红线只有**工具集**和**模型**,其余参数变化不必恐慌。
- **20 块回看窗口**:每个断点最多向前回看 20 个 content block 去找旧条目。agentic loop 一轮就可能产生几十个 tool_use/tool_result 块,超过就**静默 miss**。补救:长回合里每 ~15 块补一个中间断点。这是 agent 场景独有、也是最常被漏的坑。
- **并发时序**:缓存条目要等第一个响应**开始流式返回**后才可读。N 个同前缀请求并发发出会**全部 miss**。fan-out 的正确姿势:先发 1 个、等到首 token,再发其余 N−1。

**3. 静默失效清单(可以直接 grep 的反模式)**

`datetime.now()` / `Date.now()` 出现在 system prompt;UUID 或 request id 排在内容前部;`json.dumps` 没有 `sort_keys=True`(或直接迭代 `set`);把 session/user id 插进 system prompt;条件式拼接 system 段落(`if flag: system += ...`,每种组合都是一个新前缀);`tools=build_tools(user)` 让工具集随用户变化。诊断只有一条:看 `usage.cache_read_input_tokens`,长期为 0 就一定有静默失效源,diff 两次渲染后的字节找它。

**4. 成本收益模型(能算才叫懂)**

设共享前缀 P tokens、请求 N 次、基础输入单价为 1:

- 不缓存:`N·P`
- 5 分钟档:`1.25·P + (N−1)·0.1·P` ⇒ N=2 时 `1.35P < 2P`,**两次即回本**
- 1 小时档:`2·P + (N−1)·0.2·P` ⇒ 需 `N ≥ 3`(`2.2P < 3P`)

1h TTL 的价值不在单价,而在**跨越流量空档**(bursty 场景)。另外缓存还砍 TTFT(跳过 prefill),交互式产品里这个收益常常大于省钱本身——于是有"预热"打法:启动时发一次 `max_tokens: 0` 的请求把缓存写好。但预热只在三个条件同时成立时划算:首请求延迟对用户可见、共享前缀足够大、且存在流量到达前的时机(启动 / 部署后 / 定时窗口开始)。流量本身就连续时,预热是纯粹的多付一次写入。

**5. 与上下文管理的关系(面试真正想听的部分)**

- **正交**:被缓存的 token 仍然**完整占用窗口、完整参与注意力竞争**,缓存治不了 Q1 的退化——**省钱不省注意力**。
- **冲突**:上下文管理的动作会破坏缓存。compaction 重写历史 ⇒ 前缀改变 ⇒ 缓存全废;动态增删工具 ⇒ tools 在位置 0 ⇒ 全废。工程解法统一是把变化**后移到缓存前缀之后**:用 `{"role":"system"}` 中途系统消息代替修改顶层 system(as-of 2026-08 在 Opus 5 / Opus 4.8 / Fable 5 / Mythos 5 上可用、无需 beta header,Sonnet 5 不支持,需 catch 400 回退);用 tool search **追加** schema 而不是替换工具集;子任务用 subagent 而不是换模型。
- 所以正确的心智顺序是:**先设计上下文结构(什么进、进哪一层、放什么位置),再谈缓存**。缓存是良好结构的奖励,不是烂结构的补救。

**实例**(agent 的分层排布与断点位置):

```
[tools:  排序确定的稳定工具集]                     ← 位置 0,绝不动态增删
[system: 角色 + 硬规则(冻结,不插日期/用户名)]     ← breakpoint #1(缓存 tools+system)
[messages: ……历史……]                              ← breakpoint #2(滚动,打在最近一轮末尾)
[user:   本轮问题 / 动态注入的上下文]               ← 断点之后,每轮都变
```

回归测试思路:连发两次相同前缀的请求,断言第二次 `usage.cache_read_input_tokens > 0`,把它放进 CI——防止有人某天往 system prompt 里加了个时间戳,而线上只表现为账单缓慢上涨。

**边界与误区**:
- 误区:"缓存 = 记忆"。缓存只是**计算复用**,模型不会因为命中缓存而"记得"更多;跨会话记忆要走文件 / memory 层。也别因为"能缓存了"就放心堆上下文:堆得越多注意力越差,缓存读虽便宜但不免费,延迟仍随长度上升。
- 误区:把断点打在整个 prompt 的末尾。"共享前缀 + 变化尾部"的场景必须打在**共享段末尾**,否则每次都写一个新条目、永远读不到。
- 边界:每次请求前 1K token 就不同的场景根本不该开缓存——只会白付写入溢价。

**追问预判**:
- 追问:"fan-out / 多 agent 场景怎么最大化缓存?" → 答:让所有分支复用父级**逐字节一致**的 `system` / `tools` / `model`,差异只追加在尾部;并且先发一个请求把缓存写热、等首 token 之后再并发其余,避免并发全 miss。
- 追问:"缓存和 compaction 冲突时怎么权衡?" → 答:看"还要跑多少轮"。离收尾还远,压缩换来的注意力收益 > 缓存损失;接近收尾时,宁可外置状态后换新会话,也别在一条很长的前缀上做一次全量重写。

## Q4:Agentic search(grep/glob 式主动检索)vs 向量 RAG:代码场景怎么选?

**考察点**:能否从"代码这种数据形态的特性"推导选择,而不是站队喊"RAG 已死"。

**30 秒版**:代码场景默认选 **agentic search**(glob/grep/read + 多轮迭代收敛):代码有**精确标识符**和**可计算的结构**,字面与结构检索的信噪比远高于语义相似;而且它零索引、零陈旧、天然跟随当前工作区与 git 状态。向量 RAG 的主场是"用自然语言描述找不知道名字的东西"和超大规模的第一跳召回。成熟做法是**混合**:检索层出候选**指针**,agent 用 grep + read 做精定位与取证。Claude Code 官方的工具分类里,Search 就是"按 pattern 找文件 + 按正则搜内容",不含向量索引(as-of 2026-08)。

**深入版**:

**1. 先看数据形态——这是推导的起点**

- 标识符是**精确且近乎唯一**的:`refreshToken` 在仓库里就是那几处,正则一击即中;而嵌入会把它和 `renewSession`、`rotateCredential` 拉到一起——**语义相似恰恰是代码检索的噪声源**(与 Q1"相似干扰项最伤"同源)。
- 代码有**可计算的结构**:定义 / 引用 / 继承 / 调用关系可以由编译器或 LSP 精确给出,不需要近似。
- 代码**变化频繁**:每次 commit 都让索引局部陈旧,而 agent 关心的恰恰是工作区的当前状态(包括未提交的改动)。
- **chunk 边界即语义边界**:把函数与其类型定义、调用点切开,单块可用性大幅下降——这是 RAG 在代码上最难解的一环。

**2. 两种范式的机制对比**

| 维度 | Agentic search | 向量 RAG |
|---|---|---|
| 谁决定检索 | 模型,运行时多轮 | 检索器,单次(或固定几次) |
| 查询形态 | 正则 / 文件名 / 结构,可**迭代改写** | 一个向量,近似最近邻 |
| 失败恢复 | 0 结果就换关键词——**自愈** | 召回错了下游无从察觉 |
| 新鲜度 | 永远是工作区当前状态 | 取决于索引更新管道 |
| 基础设施 | 无(有 shell 就行) | 嵌入模型 + 向量库 + 分块 + 重排 + 更新 |
| 主要成本 | **上下文与轮次**(每次搜索/读文件都吃 token 与延迟) | 索引构建 / 存储 / 维护 + 首跳召回质量 |
| 弱项 | 不知道该搜什么词时会盲目扩散 | 精确标识符、结构关系、跨版本 |

**3. 关键权衡:agentic search 把成本从"离线索引"搬到了"在线上下文"**

这是它唯一的真代价,并且直接连回 Q1 与 Q6:一句没有边界的"调查一下 X"能读几十个文件、吃掉几万 token——这正是官方五大失败模式里的**"无边界探索"**。所以 agentic search 必须配上纪律:先 glob 缩小范围 → grep 定位行号 → **只读命中行段而非整文件** → 大规模探索交给 subagent 只回传结论。**没有上下文纪律的 agentic search 会自己把自己搞垮**。

**4. 什么时候仍然该上向量 / 混合**

仓库极大且问题是"我不知道它叫什么"(自然语言描述 → 候选文件),grep 无从下手;检索对象不是代码而是**文档 / 工单 / 设计讨论 / 历史决策**——那本来就是语义检索的主场;需要**低延迟单跳**(IDE 内联补全、在线服务),承受不了多轮工具调用;需要跨仓库、跨版本的模糊关联。

混合架构的常见形态:第一跳用 **BM25 + 向量**做候选召回(别只用向量——BM25 对标识符和错误信息往往更强),把候选的**文件路径**(不是 chunk 全文)交给 agent,由 agent 用 grep/read 精确验证。要点是:**检索层输出指针,agent 负责取证**——这同时解决了"chunk 割裂"和"上下文膨胀"两个问题。

还有第三条腿值得提:**结构化索引**(LSP / ctags / 代码图)——比向量准、比 grep 懂结构。Claude Code 侧对应的是 code intelligence 插件提供的跳转定义 / 查引用(as-of 2026-08)。面试里能主动把它列出来,说明你没有把问题简化成二选一。

**5. as-of 与不确定性(诚实边界)**

编码 agent 侧确实出现了"去向量化"的转向,可核实的一手证据是:Claude Code 官方文档的工具分类中,Search 只有"按 pattern 找文件 / 按正则搜内容",不包含向量索引(as-of 2026-08)。但坊间流传的"某公司某月删掉了 RAG 管线""agentic search 比 RAG 高 X 个点"这类具体说法,我没有找到可靠一手来源,**不建议在面试里当事实引用**。可靠的表述是:在代码这种数据形态上,精确 + 结构检索的信噪比优势可以从第一性原理推出;具体幅度必须按自己的仓库实测。

**实例**(一次真实定位的收敛过程,以及它的 token 账):

```bash
rg -l "refreshToken" --type ts           # 缩范围:6 个文件路径        ≈  200 tokens
rg -n "refreshToken" src/auth/token.ts   # 定位:行号 120-180          ≈  150 tokens
# 只读命中区间 Read(token.ts, offset=110, limit=90) ≈ 900;整文件读入 ≈ 2,400 tokens
```

同一问题若走向量 RAG:要先嵌入整库、按函数分块、维护更新;返回的 top-k chunk 可能命中 `renewSession`(语义近但不是要找的),而且**不给行号**——agent 仍要再读一次文件确认。

**边界与误区**:
- 误区:"agentic search 是免费的"。它不建索引,但每次搜索与读文件都在花上下文和延迟——成本被**转移**,不是被消灭。
- 误区:"RAG 过时了""向量一定优于关键词"。判据是**检索目标是否存在精确可写的字面键或结构键**;文档、工单、跨仓知识仍是语义检索的主场,而代码检索里 BM25 / 正则常常更强(尤其针对标识符与报错文本)。
- 边界:大规模离线批处理(几千个文件的机械迁移)反而适合索引 + 脚本分发(`for file in $(cat files.txt); do claude -p ...`),而不是让一个 agent 逐个探索。

**追问预判**:
- 追问:"仓库 10 万文件,grep 又慢又吵怎么办?" → 答:分层收敛——先用目录结构 / 代码所有权 / 构建依赖图缩小域(这些是**结构信息**,比语义可靠),再 ripgrep;必要时加一层轻量倒排或代码图做第一跳,agent 只在候选域内精定位;同时把探索放进 subagent 并限制轮次与读文件数。
- 追问:"怎么评测检索质量?" → 答:构造"问题 → 应命中文件/行段"的标注集,测 recall@k 与**定位到行**的精度;agent 侧额外测"平均工具轮次"与"消耗 token"——agentic search 的质量必须和成本一起看,否则会优化出一个又准又烧钱的方案。

## Q5:结构化输出(JSON Schema / strict mode / constrained decoding)的底层机制与失败模式?

**考察点**:能否区分"提示约束 / 校验重试 / 解码期约束"三层;能否说清 constrained decoding 到底约束了什么、代价在哪。

**30 秒版**:三层实现,强度递增:(1) **提示 + 后校验**——让模型写 JSON,解析失败就重试,纯靠概率;(2) **schema 传入 + 服务端校验/重试**;(3) **constrained decoding(strict mode)**——把 JSON Schema 编译成状态机(FSM / 下推自动机),解码每一步对 logits 做**掩码**,只允许能延续合法结构的 token。第三层把"大概率合法"变成"结构上必然合法"。代价:schema 表达力受限(不支持递归、数值/长度约束)、新 schema 有一次性编译延迟、**结构合法 ≠ 语义正确**,而且约束过强会挤压模型的推理空间。

**深入版**:

**1. 机制:从生成到掩码**

解码每一步是在词表上采样。约束解码在采样前插入一个掩码:根据已生成的部分 JSON,自动机计算"哪些 token 能让这个串仍**可能**扩展成合法实例",把其余 token 的 logit 置为 −∞。

为什么必须是自动机、而不是事后校验?因为 JSON 的合法性是**上下文相关的前缀性质**:已经写了 `{"age":` 就必须接数字;开了引号就必须闭合。要在生成期约束,就得把 schema 编译成能对任意前缀回答"下一步还能接什么"的结构——正则与枚举 → 有限状态机,嵌套对象与数组 → 需要栈(下推自动机)。**限制的来源也在这里**:递归 schema 会让自动机无界,所以普遍不被支持,这是原理性限制而非产品偷懒。

实现上还有一个难点:自动机以**字符**为单位,采样以 **token** 为单位,一个 token 可能跨越语法边界,因此要预计算"token → 自动机转移"的映射。这就是"新 schema 第一次使用有编译开销、之后走缓存"的原因(Anthropic 侧口径:新 schema 有一次性编译成本,相同 schema 在 24 小时内命中缓存,as-of 2026-08)。

**2. 两种用法要分清(Anthropic API,as-of 2026-08)**

- **工具参数 strict**:在**工具定义的顶层**设 `strict: true`(不是设在 `tool_choice` 上),schema 需 `additionalProperties: false` + 完整 `required`,保证 `tool_use.input` 精确符合 schema。**响应格式**则用 `output_config.format` 约束最终回答的 JSON 形态,SDK 侧推荐 `client.messages.parse()` 直接拿到已校验对象(顶层 `output_format` 参数已弃用)。
- **支持**:object/array/基础类型、`enum`、`const`、`anyOf`、`allOf`、`$ref`/`$def`、常见 string format(`date-time`/`email`/`uuid`)。**不支持**:递归 schema、数值约束(`minimum`/`maximum`/`multipleOf`)、字符串长度约束、复杂数组约束;`additionalProperties` 只能是 `false`。Python / TS SDK 会把不支持的约束从发给 API 的 schema 里**剥离、改在客户端校验**——所以"我写了 `minimum` 模型就不会越界"是**错觉**:保证发生在客户端,不在解码期。

**3. 失败模式(得分区)**

- **结构对、语义错**:约束保证形状,不保证内容。`{"date": "2026-13-45"}` 可以完全合法通过。语义校验必须留在应用层。
- **截断与拒答(都靠 stop_reason 才能发现)**:`max_tokens` 时输出可能是**合法前缀但不完整**的 JSON——严格模式下尤其隐蔽,因为你以为"有保证";`refusal` 时输出可能根本不符合 schema。所以必须先判 stop_reason 再读 content,而不是只 try/except 解析。
- **约束伤推理**:强制模型从第一个 token 就进入 JSON,等于剥夺它"先想再答"的空间,在需要推理的抽取/判断任务上会掉点。解法:让 schema 自带 `reasoning` 字段(先写依据再写结论),或开 thinking 让推理发生在受约束输出之外。
- **schema 过度设计**:深嵌套 + 巨型 enum + 长 description 既吃 token 又提高出错率;`type` / `value` 这类歧义字段名会让模型填错。解法:拍扁、命名自解释、每个字段一句话说明。
- **兼容性坑**:结构化输出与 citations 互斥(返回 400)、与 assistant prefill 互斥;strict 工具参数与程序化工具调用等特性也不兼容。改造前查兼容矩阵,别猜。

**4. 工程判据:什么时候用哪一层**

下游是**程序**、解析失败代价高(写库、触发动作)→ 用 strict / constrained;下游是**人**或任务需要自由推理 → 别硬套 schema,markdown 更好。但**无论哪层都要留兜底**:stop_reason 检查 + 语义校验 + 有限次重试,并把校验错误**作为消息回传让模型自己修**——这是"错误即数据"(见 [01 Q3](01-agent-fundamentals.md))在结构化输出上的应用。

**实例**(工具定义骨架 + 三层兜底):

```json
{
  "name": "create_ticket",
  "description": "创建工单。仅在用户明确要求创建时调用;只是询问状态时不要调用。",
  "strict": true,
  "input_schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["reasoning", "title", "severity"],
    "properties": {
      "reasoning": {"type": "string", "description": "先写判断依据,再填其余字段"},
      "title":     {"type": "string", "description": "一句话概括问题现象"},
      "severity":  {"type": "string", "enum": ["p0", "p1", "p2"]}
    }
  }
}
```

```python
resp = client.messages.create(...)
if   resp.stop_reason == "refusal":    handle_refusal(resp)        # 1) 拒答:可能完全不合 schema
elif resp.stop_reason == "max_tokens": retry_with_more_tokens()    # 2) 截断:合法前缀 ≠ 完整对象
else:                                  validate_semantics(parse(resp))  # 3) 结构合法后仍需语义校验
```

**边界与误区**:
- 误区:"strict mode 保证输出正确"。它保证**形状**,不保证**事实**;同理"schema 里写了 `minimum` 就有硬保证"也不成立——当前不支持数值约束,SDK 剥离后在客户端校验,保证的位置变了。
- 误区:"约束越强越好"。完全禁止自由文本常常降低质量;给模型留一个 reasoning 字段,往往比反复调 prompt 更有效。
- 边界:弱模型 / 本地模型上,若运行时没有约束解码能力,只能退回"提示 + 校验重试",此时必须显著简化 schema(拍平、少枚举、少嵌套)。

**追问预判**:
- 追问:"constrained decoding 会不会改变输出分布、从而降低质量?" → 答:会。掩码等于在受限集合上重新归一化——模型本来想走的路径若被掩掉,只能在次优分支里挑;表现为推理型任务掉点,以及"被迫填字段"式的编造。缓解办法是让 schema 允许推理位、允许 `null` / `"unknown"`,而不是逼它必须给出答案。
- 追问:"多个可选形态怎么表达?" → 答:用 `anyOf` + 判别字段(discriminator),而不是把所有字段都设成可选。满屏可选字段会让模型难以判断该填哪些,也让下游代码到处判空。

## Q6:上下文隔离(subagent)的收益与代价怎么权衡?什么时候不该隔离?

**考察点**:能否把隔离当作一个有明确成本函数的工程手段,而不是"多 agent 更强"的信仰;能否给出**不该隔离**的清单。

**30 秒版**:subagent 的收益只有一条但很大:**过程不进主上下文,只回传结论**——探索读的几十个文件由子上下文承担,主上下文只付"派发 + 摘要"的钱,同时避开 Q1 的注意力稀释。代价有四类:通信有损(细节永久留在子上下文)、冷启动(子 agent 要重建背景,**总 token 常常更高**)、规格化成本(任务必须写清楚,否则白跑一轮)、无法中途纠偏。判据:**当"要读的量" ≫ "结论的量",且结论能被压成一段可验证的文字时才隔离**;反之不该隔离。

**深入版**:

**1. 收益的机制**

主上下文的成本 = 派发提示 + 回传摘要,**与子任务实际读了多少无关**。官方走查给出的量级(as-of 2026-08,示意值):主会话"派发一个研究 subagent"只增加约 **80 tokens**,子 agent 在自己的窗口里读完若干文件后回传约 **420 tokens** 的摘要——主上下文净增约 0.5K;同样的探索若直接在主线做,轻松是 5–10K 起(见 Q1 的单文件读取成本)。

省容量只是表层。更重要的是**省注意力**:主上下文里不会残留几十段与最终决策无关的文件内容去和硬约束抢注意力。还有一个常被忽视的收益:**结论比过程更抗压缩**——一段 400 token 的结论在后续 compaction 中的存活率,远高于同样信息分散在几十条 tool_result 里的形态(见 Q2)。

**2. 代价的机制(四类,按重要性排序)**

- **通信有损**:隔离的另一面是主上下文**永远拿不到**子上下文里的细节。若后续需要"当时那个文件第 137 行长什么样",只能重读。所以子 agent 的返回必须包含**指针**(文件路径、行号区间、执行过的命令),而不只是结论——这是让隔离**可逆**的关键设计。
- **冷启动成本**:子 agent 默认从空上下文开始(fork 型变体除外——fork 会带一份主会话历史的副本,as-of 2026-08 Claude Code 支持),它要重新加载系统提示、CLAUDE.md、工具定义,再从任务描述里理解背景。**总 token 常常不降反升**,降的是主上下文的占用。**把"省钱"当成隔离的理由通常是错的**;理由应该是"保护主上下文"。
- **规格化成本**:你必须把目标、范围、返回格式写清楚。人类下意识依赖的共享上下文在这里全部消失——这也是 subagent 最常见的失败原因:描述含糊 ⇒ 返回没用 ⇒ 再跑一轮,双倍延迟。
- **无法交互式纠偏**:主 agent 看不到子 agent 中途走偏。子任务越长、越开放,风险越高。所以隔离适合**有明确终止条件**的调查,不适合"边做边商量"的实现。

补一个缓存维度:子 agent 若复用父级**逐字节一致**的 `system` / `tools` / `model`,还能命中父级缓存;若重建了不同前缀,就是一次完整的冷 prefill(见 Q3)。

**3. 什么时候不该隔离(反向清单,每条都可推导)**

- **信息压缩比低**:要读 3 个文件、而结论就是这 3 个文件的内容本身 ⇒ 隔离只加了一层转述损耗。经验量级:**读入量 / 结论量 < ~5 就别隔离**(量级判断,非硬阈值)。
- **需要写操作与连续状态**:实现型任务要连续编辑 → 跑测试 → 看反馈,隔离会切断闭环;隔离适合**只读调查**。
- **任务定义还不清楚**:先在主会话里想清楚再派发,否则是为含糊付双倍代价。**子任务很小**同理:派发 + 冷启动的固定成本可能超过直接做。
- **要求可审计的完整轨迹**:合规场景需要主线保留全部证据链,摘要不够。
- **协调收益不明**:多个子 agent 并行做**同一个**判断再投票,不必然更好——Anthropic 2026-08 的多智能体研究提示群体决策可能劣于个体(见 [01 Q5](01-agent-fundamentals.md) 追问),范围要克制。

**4. 正确的隔离设计(把代价压到最低)**

- **合同化派发**:写清"目标 / 边界(哪些目录、最多读多少)/ 返回格式(结论 + 证据指针 + 不确定项)";**返回指针而非全文**(`path:line-range` + 可复跑命令,主 agent 需要时自取);**只读优先**——调查、审查、验证类任务隔离收益最高,且没有并发写冲突。
- **对抗性复核**:让 reviewer 子 agent 在**干净上下文**里只看 diff 与验收标准——它看不到产生这段代码的推理,所以不会被自己的思路绑架。这是隔离的**第二种收益(去偏)**,与省上下文正交。官方也提示了副作用:被要求"找问题"的 reviewer 总能找出点什么,要明确告诉它只报影响正确性或需求的缺口,否则会诱发过度工程。

**实例**(同一个任务的两种派发写法):

```
✗ "用 subagent 调查一下认证模块"
   → 范围无界、返回格式未定;可能读了 40 个文件,回来一段泛泛而谈
✓ "用 subagent 调查:token 刷新在哪里实现、是否已有可复用的 OAuth 工具。
   范围限于 src/auth/ 与 src/lib/;返回格式:1) 结论(≤10 行)
   2) 证据:文件路径 + 行号区间 3) 没找到或不确定的点(必填,没有就写'无')"
```

判据自查表:

| 情况 | 隔离? | 理由 |
|---|:---:|---|
| "这套鉴权怎么工作的"(要读 20+ 文件) | ✔ | 压缩比高,且只读 |
| "评审这个 diff" | ✔ | 需要不带偏见的干净上下文 |
| "改这 3 个文件并让测试通过" | ✘ | 需要连续的反馈闭环 |
| "看一眼 config.ts 里超时设成多少" | ✘ | 固定成本 > 收益 |
| "并行 5 个 agent 投票选架构" | ⚠ | 协调成本高,收益存疑 |

**边界与误区**:
- 误区:"subagent 省 token"。省的是**主上下文占用**;总 token 常常更多。能主动说清这一点是面试里的强信号。
- 误区:"隔离越多越好"——每次隔离都是一次有损通信,链路越长衰减越严重;以及把隔离等同于并行——隔离解决**上下文污染**,并行解决**墙钟时间**,两者常一起用但动机不同,别混着讲。
- 边界:fork 型子代理(带主会话历史副本启动)是折中——省掉背景重建,但也把主上下文的噪声一起带过去,只在"复核需要完整背景"时才值得。

**追问预判**:
- 追问:"子 agent 返回的摘要不可信怎么办?" → 答:强制返回**可验证的证据指针**(路径 + 行号 + 可复跑命令),主 agent 抽查关键结论;并把"不确定项"设为返回格式的必填字段,逼它显式声明边界,而不是自信地编。
- 追问:"什么时候该升级成多 agent 团队,而不是单 agent + subagent?" → 答:当子任务**真正独立**、可并行、且各自有清晰验收标准时(例如 2000 个文件的机械迁移,可以直接 `claude -p` 扇出);一旦需要频繁共享中间状态或互相等待,协调成本会吃掉全部收益,不如单 agent 串行 + 状态外置。

## Q7:Prompt 工程在 2026 年还剩什么?system prompt 该怎么写?few-shot、CoT 这些技巧哪些已经过时?

**考察点**:能否说清 prompt 工程与上下文工程的从属关系与重心迁移;能否用**机制**而非口味判断哪些技巧还活着;有没有可复现的调优方法论。

**30 秒版**:prompt 工程是上下文工程的**子集**——它管你**静态撰写**的那部分,上下文工程管推理时窗口里的**全部**内容(提示 + 历史 + tool_result + 检索 + 记忆)及其**顺序、分层、准入、淘汰**。单轮问答时代两者重合,所以"话术"就是全部;agent 时代你写的 system prompt 可能只占第 30 轮上下文的百分之几,重心因此从**措辞**转向**信息架构**。system prompt 要结构化写:角色与边界 → 硬约束 → 工具选择策略 → 输出契约 → 少量范例,并且**越长越稀释**(Q1 的注意力竞争),它是**预算**不是文档。过时的多是"从模型里骗出它已有能力"的咒语(强行 CoT、身份加持、情绪勒索);活着的是"给模型它不可能知道的信息"的手段(范例定义形状与边界、明确的负向约束、可检验的判据)。调优靠评估集 + 单变量 + 看分布,不是玄学试错。

**深入版**:

**1. 从属关系与重心迁移(先把概念摆正)**

区分尺度是**这段内容由谁写、何时进上下文**:prompt 工程管你**离线撰写、每次请求原样出现**的部分(system prompt、工具 description、few-shot 范例、输出契约);上下文工程 = 这些 **+ 运行时动态进来的一切** + 它们的结构。所以 prompt ⊂ context,而且是其中**最不动的那一层**。

重心为什么迁移,有一个可量化的说法:单轮问答里你写的 prompt 是上下文的 **100%**;一个跑了 30 轮工具调用的 agent,你写的部分可能只剩百分之几,其余全是运行时产物。**你能通过措辞控制的比例在系统性下降,能通过准入/结构/压缩控制的比例在上升**——这才是 "prompt engineering → context engineering" 的实质,不是换个词赶时髦。

一个直接推论,也是很好的面试回答:**今天绝大多数"prompt 不好使"的报告,根因不在措辞**。诊断法:把当次请求**渲染后的完整上下文 dump 出来自己读一遍**——如果一个熟悉任务的人拿着这份上下文也做不对,那就不是 prompt 问题,是信息问题(该给的没给、给了但埋在中段、或被前面的失败轨迹污染)。改措辞治不了信息缺失。

**2. system prompt 怎么写(结构 + 代价)**

顺序本身有意义,越靠前越抗稀释:

1. **角色与任务边界**:你是什么、为谁服务、**不做什么**。注意要写**信息**而非加持——"读者熟悉 C++ 但没写过 Rust"是信息(限定了术语层级与解释深度),"你是世界顶级专家"不含信息。
2. **硬约束**:少而绝对、可执行。只放"违反即失败"的(不改哪些目录、必须用哪个包管理器、禁止新增依赖)。
3. **工具选择策略**:什么时候用哪个、什么时候**不要**用。单个工具的用法属于它自己的 description(见 [01 Q3](01-agent-fundamentals.md)),别把 schema 在 system prompt 里重抄一遍。
4. **输出契约**:程序消费时这一段应当**上升成 schema**(见 Q5),而不是用散文描述——同样的目的,一个是概率保证,一个是结构保证。
5. **少量范例**:见第 4 节。

最实用的一个概念是 **altitude(高度)**:Anthropic 的工程指南把 system prompt 写作描述为在两种失败之间找 Goldilocks 区间——一端是把复杂脆弱的 if-else 逻辑硬编码进提示(脆、难维护),另一端是含糊的高层指导(不给模型具体信号);正确高度是"足够具体以指导行为,又足够灵活以留出启发式空间"(as-of 2026-08)。

**代价必须写进设计**:每个 token 都是 (a) 每次请求的固定成本与延迟——prompt caching 能免掉重复计算的钱,但**免不掉窗口占用与注意力竞争**(见 Q3),(b) Q1 意义上的干扰项。而且**system prompt 内部也有 U 型**:把 10 条规则塞进 3000 token,第 5 条正落在中段。由此推出两条规则:规则数量控制在**能被逐条检验**的量级;真正的红线可以在**最近一条消息里复述**一次(利用尾部位置优势),而不是指望它在中段被看见。

**3. 哪些过时、哪些还活着**(过时判断是**我的判断**,非硬事实;每条附机制理由)

统一判据只有一条:**这个技巧是在"骗出模型已有的能力",还是在"给模型它不可能知道的信息"?** 前者随训练进步而贬值,后者永不贬值。

**已贬值的**:
- **"请一步步思考"/强行 CoT 提示**:2022 年有效,是因为推理当时是"提示可诱导但默认不发生"的行为。今天推理是训练进权重、有独立解码预算的原生能力(见 [01 Q4](01-agent-fundamentals.md)),诱导对象已默认在场;在 reasoning 模型上强行要求"把思考写进输出"甚至有反作用——它把推理挤进受格式约束的最终输出,与原生 thinking 争预算(与 Q5"约束伤推理"同源)。
- **身份加持与情绪/贿赂话术**("你是世界顶级的…""答错会被解雇""给你 200 美元"):原理上它们是对**基座模型输出分布**的引导——补全式模型上,"专家"语境确实能把生成拉向预训练语料中质量更高的区域。经过后训练对齐的助手模型默认已在这个模式里,边际引导趋近于零;而贿赂/威胁类从来没有稳固机制,是把分布扰动当成了规律。
- **用散文描述输出格式**(在有结构化输出 API 时):被 Q5 的第三层 constrained decoding 取代。
- **繁琐的分隔符仪式**:用 `###` 还是 XML 标签本身不重要;**分节这件事仍然重要**(可寻址、可增删、便于缓存分层)。贬值的是格式迷信,不是结构。

**仍有效且有机制解释的**:
- **少样本范例定义输出形状与边界**——见第 4 节,这是最该讲透的一条。
- **明确的负向约束**:"不要 X"在 X 是模型**默认吸引子**时有效(它本来大概率那样做,你在决策点加了判别信号)。两条工程细节:`不要 X,改用 Y` 远好于只写 `不要 X`(给了替代吸引子,否则模型知道往哪不走却不知道往哪走);负向约束是 compaction 里**最先丢的**(见 Q2),所以它属于 CLAUDE.md / system 层,不属于对话历史。
- **把判据写成可检验条件**:"写出高质量代码"没有梯度,模型无从判断何时算完成;"`pnpm test` 通过、不新增依赖、改动不超过 3 个文件"能被模型在生成中自查、被 harness 在生成后核验。这条同时是 prompt 技巧和 eval 设计——**凡是你写不成可检验条件的要求,你也没法评测它**。
- **位置安排**:硬约束放头部与最近消息(Q1 的 U 型)。这是机制直接推出的,与模型代次无关。

**4. 为什么"范例定义格式"强于"描述格式"(机制,不是经验)**

模型做的是在给定上下文下预测下一个 token。**范例是分布内的强约束**:上下文里已经存在一段与目标同构的文本,模型只需**延续同一个模式**——这是它在预训练里做过无数次的操作,几乎零翻译损耗。**描述是分布外的弱约束**:模型必须先把自然语言规范翻译成生成策略再执行,这步翻译有损;而且**描述的表达力天然不足**——"日期用 ISO 格式"没有回答:年份未知怎么办?区间怎么写?"上世纪 90 年代"映射成什么?你得再写十条规则去堵,每条又引入新歧义;而三五个精选范例把这些**用示范直接定死**,零歧义、零翻译。

由此推出的是**选取原则而非数量原则**:范例要**典型且多样**,落在你真正在意的判定边界上。Anthropic 的工程指南也是这个口径:精选一组多样的、典型的范例来刻画期望行为,而**不是**把每一条边界规则堆成清单塞进提示(as-of 2026-08)。所以两种坏做法对称存在:给 20 个雷同的常见样例(全在分布内,什么都没教),和把边界情况写成 30 条散文规则(退回弱约束)。

三个必须知道的代价:范例是**永久上下文税**(每轮都在,且参与注意力竞争,agent 场景里 5 个长范例可能比它们解决的问题更贵);**过度锚定**(模型会连范例的**内容**一起模仿——领域词汇、句长、甚至具体数值,缓解办法是让范例内容与真实任务保持距离或显式声明"仅示范格式");有结构化输出时**形式已由解码保证**,范例的价值应转移到 schema 表达不了的**语义边界**(什么情况填 `unknown`、什么情况该拒绝)。

**5. prompt 调优方法论(把玄学变成实验)**

1. **先有评估集,再改 prompt**。20–50 个真实用例,必须同时包含**触发这次改动的失败样本**和**当前已通过的样本**(回归护栏)。没有评估集的调优 = 没有测量的优化。
2. **定义打分函数,测出基线并记录**。能自动判的自动判(精确匹配/schema 校验/断言);判不了的写 rubric 交给 LLM judge,但 rubric 必须先在人工标注上**校准**过,否则你是在优化一个未经检验的裁判。
3. **单变量修改**。一次改一处;同时改三处再看总分,你无法归因,而且大概率其中一处是负向、被另两处掩盖。
4. **看分布,不看单例**。同一用例在生产温度下跑 n 次(n≥5),报**通过率**而非"我试了一下好了";并且**必看回归**——逐案例对比前后。vibes 式调优最典型的失败就是修好第 7 例、悄悄弄坏第 1–6 例。
5. **读失败样本并分类**。这步决定前面所有工作是否有用:把失败分成"措辞歧义 / 信息缺失 / 工具或 schema 不合适 / 模型能力不足 / 评估集本身错了"。**只有第一类才该用改 prompt 来修**;把信息缺失当措辞问题改,就会养出一个越来越长、越来越不像话的 system prompt——这正是 kitchen sink 的常见成因。

两条工程纪律:prompt 与评估集**进仓库、进 code review、随 commit 走**,评估当回归测试挂 CI(与 Q3"把缓存命中断言进 CI"同构:都是防止一次无心编辑在线上悄悄劣化)。以及**知道何时停手**——当改动带来的提升落进跑批的噪声范围内,继续调 prompt 就是在拟合噪声,该去改上下文结构、工具或模型了。至于自动优化(prompt 优化器、让模型改自己的提示):它自动化的是第 3 步,前提仍是你有第 1、2 步。**真正的资产是评估集,不是那段 prompt——评估集能迁移到下一代模型,prompt 不能。**

**实例**(同一需求的前后对比):

```text
✗ 旧写法(咒语 + 散文格式 + 无判据)
   你是世界顶级的资深工程师,拥有 20 年经验。请一步步仔细思考。
   请尽力写出高质量的代码。输出请用 JSON,包含风险等级等字段,格式要规范。

✓ 重写(信息 / 硬约束 / 可检验判据 / 契约上升为 schema)
   [角色] 你在一个 TypeScript 单体仓里做代码审查,读者是本仓的提交者。
   [硬约束] 不修改 db/migrations/**;不新增依赖;命令一律用 pnpm。
   [判据] "通过"= `pnpm test -- <相关用例>` 通过 且 未新增依赖 且 改动 ≤3 个文件。
   [工具] 定位用 rg 而非全文件读;只读命中行段。不确定就说不确定,不要猜路径。
   [输出] 由 strict schema 约束(见工具定义),schema 里带 reasoning 字段先写依据。
```

范例强于描述的一个具体切面——同样是"日期规范化",描述堵不住的歧义由范例一次定死。注意下面三条都是**边界样例**而非常见样例:常见样例本来就在分布内,教不了模型任何东西。

```text
描述式(弱约束,留下一堆未定义行为):
  "把日期统一成 ISO 8601 格式。"
范例式(强约束,边界情况被直接定义):
  "2026年3月"      → {"date": "2026-03", "precision": "month"}
  "上世纪90年代"    → {"date": "1990/1999", "precision": "decade"}
  "去年年底"        → {"date": null, "precision": "unresolved", "note": "需要参照日期"}
```

**边界与误区**:
- 误区:"prompt 工程已死"。死的是**话术层**;信息架构层的活变多了。而且在**没有 agent loop 的单轮任务**(分类、抽取、改写)上,prompt 仍然几乎等于全部工程。
- 误区:"prompt 越详细越好"。Q1 的机制直接反驳:每条追加规则都是新的注意力竞争者,并把先前规则往中段挤。规则集要**定期删**,不只是加。
- 误区:"这个提示词在 A 模型上很灵,搬过去也灵"。提示是对**特定模型后训练行为**的适配,换模型必须重跑评估集——尤其那些"绕过某个默认行为"的技巧,换代后常常无效甚至有害。
- 诚实边界:"哪些技巧过时"是**判断**,依据是机制推理(能力位置从提示迁移到权重与解码预算)与官方指南口径,**不是**我做过的对照实验;各家模型差异真实存在。坊间"某话术提升 X%"这类数字多为轶事,面试里不要当数据引用。

**追问预判**:
- 追问:"CLAUDE.md 和 system prompt 是什么关系?" → 答:同一层的不同来源——CLAUDE.md 是项目提供、拼进请求头部的持久指令,享有 Q1 的头部位置优势,也承担同样的稀释代价。所以它应放**跨会话恒定的硬约束与项目事实**(命令、目录禁区、约定),不放一次性任务描述;并且需要像代码一样定期精简,否则会长成一份没人读、模型也遵守不了的清单。
- 追问:"给你一个线上表现不稳的 agent,你从哪下手?" → 答:**先分层定位再动手**——dump 完整上下文看信息是否齐备(信息层)→ 看工具 description 与 schema 是否让它选错工具(接口层)→ 看是否只在长会话/压缩后才劣化(上下文管理层)→ 最后才是措辞。同时先建评估集,把"不稳"量化成通过率分布,否则你无法证明任何修改有效。
