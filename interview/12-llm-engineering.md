# 面试题:12 大模型工程

> 每题讲透五件套:本质 / 机制 / 实例 / 边界 / 检验(追问预判)。答案分 30 秒版 + 深入版。
> 本组是**推理引擎层**,与 [08 生产化](08-production.md) 的**应用层**成本优化衔接而不重复:08 讲"缓存怎么回本、模型怎么路由",本组讲"缓存背后的 KV 显存是怎么算的、batching 为什么能提吞吐、量化省的到底是哪一块"。
> 主线判据:**大模型推理几乎处处是内存带宽瓶颈,不是算力瓶颈**——本组八题里有五题的第一性解释都落在这一句上。

## Q1:讲一下 Transformer 架构。self-attention 的计算过程与复杂度是什么?

**考察点**:是不是只会背"QKV 三件套"。区分点在**维度变换讲不讲得清**、**复杂度的两个项分别在什么时候占主导**、**为什么要除以 √d_k**。

**30 秒版**:decoder-only Transformer 是 N 个相同 block 的堆叠,每个 block = causal self-attention + FFN,两者都带残差与归一化。attention 的计算是:输入 `[B, L, d]` 经三个投影得到 Q/K/V,拆成 h 个头变成 `[B, h, L, d_h]`;`QKᵀ/√d_h` 得到 `[B, h, L, L]` 的分数矩阵,加 causal mask 后 softmax,再乘 V 回到 `[B, h, L, d_h]`,拼头后过输出投影。复杂度两项:投影与 FFN 是 **O(L·d²)**,注意力分数与加权是 **O(L²·d)**——**只有当 L 与 d 同量级时二次项才占主导**,常规上下文长度下 FLOPs 大头其实还在线性投影上。

**深入版**:

**一、一个 block 的维度流水**(B=batch,L=seq,d=d_model,h=heads,d_h=d/h):

```
x                 [B, L, d]
├─ RMSNorm                                (pre-norm:先归一化再进子层)
├─ Q = xW_Q       [B, L, d]  → reshape → [B, h, L, d_h]     W_Q ∈ R^{d×d}
│  K = xW_K, V = xW_V  同上(GQA 下 K/V 的头数更少,见 Q2)
├─ RoPE 作用在 Q/K 上(位置信息乘进去,不是加在 embedding 上)
├─ S = QKᵀ/√d_h   [B, h, L, L]           ← 唯一一个 L² 的张量
├─ S += causal_mask(上三角 −inf)
├─ P = softmax(S, dim=-1)                 [B, h, L, L]
├─ O = PV         [B, h, L, d_h] → 拼头 → [B, L, d]
└─ out = O·W_O    [B, L, d]  + 残差
─ RMSNorm → FFN(SwiGLU:三个矩阵 gate/up/down,d ↔ d_ff)+ 残差
```

**二、为什么除以 √d_h**。q·k 是 d_h 个乘积之和;若各分量近似独立同分布且方差为 1,则点积方差为 d_h、标准差 √d_h。d_h=128 时分数量级约 ±11,softmax 会被推到近似 one-hot 的饱和区,梯度趋零、训练不动。除以 √d_h 把方差拉回 1,这是**数值稳定性**要求,不是美学选择。

**三、复杂度的两项,以及它们的交叉点**(每层每 token,乘加算 2 FLOPs):

| 部分 | FLOPs | 随 L 的阶 |
|---|---|---|
| Q/K/V/O 四个投影 | 2·4d² = 8d² per token → **8Ld²** | 线性 |
| FFN(SwiGLU 三矩阵,d_ff≈2.7d) | ≈16d² per token → **16Ld²** | 线性 |
| QKᵀ 与 PV | **4L²d** | 二次 |

令 `4L²d = 24Ld²` 得交叉点 **L ≈ 6d**;考虑 causal mask 只需算下三角,实际再翻一倍,约 **L ≈ 12d**。d=4096 时约 5 万 token。**结论:在 32K 以内的常规上下文里,attention 的二次项还不是 FLOPs 大头,真正先爆的是 `[B,h,L,L]` 这个中间张量的显存与显存带宽**——这正是 Flash Attention 的切入点(Q3)。

**四、参数量怎么估**。每层 ≈ attention 4d² + FFN 3·d·d_ff。d=4096、d_ff=11008、32 层:`(4×4096² + 3×4096×11008) × 32 = (67.1M + 135.3M) × 32 ≈ 6.48B`,加 embedding(32000×4096≈131M,若输入输出不共享则 ×2)≈ **6.7B**——这就是"7B"的来历。反过来也能用:面试官报一个 d 和层数,你要能当场估出参数量。

**实例**(用维度反推显存里的中间张量):B=1、h=32、L=32768、FP16,分数矩阵 `[1,32,32768,32768] × 2 B = 64 GiB`——一张 80GB 卡放不下一个 batch=1 的注意力中间结果。这一个数字就解释了为什么长上下文必须用 Flash Attention 这类**不物化 L×L 矩阵**的实现。

**边界与误区**:
- 误区:"attention 是 O(L²) 所以它是瓶颈"。是显存与带宽的瓶颈,FLOPs 上要到 L≈12d 才反超线性项。答题时把两个瓶颈分开说。
- 误区:把 encoder-decoder 结构当默认。当代 LLM 基本是 decoder-only + causal mask,面试里讲 cross-attention 会显得知识陈旧。
- 演进要点(不背版本号,只记方向):post-norm→pre-norm(训练稳定)、LayerNorm→RMSNorm(省一次均值)、绝对位置编码→RoPE(外推与相对性更好)、ReLU→SwiGLU、dense FFN→MoE(激活参数远小于总参数)。
- 与 agent 的关系:模型对上下文中位置的敏感性(lost-in-the-middle)根子在注意力分布上,这是 [02 上下文工程](02-context-engineering.md)"注意力退化"的物理层解释——不是玄学,是 softmax 在长序列上的分布性质。

**追问预判**:
- 追问:"MoE 改变了上面哪个数?" → 答:改变的是"每 token 激活的 FFN 参数量",FLOPs 随激活专家数走,而**显存仍按总参数量算**;所以 MoE 是"用显存换算力"的交易,推理部署的痛点从算力转向显存与专家路由的负载均衡。
- 追问:"causal mask 在实现上是加 −inf 吗?" → 答:数学上是,工程上分块实现里对完全被 mask 的块直接跳过计算(Flash Attention 的 causal 优化),这也是它 causal 场景近乎省一半的来源。

**关联**:**本组 Q2 KV Cache** · [kb/10-landscape/model-capabilities.md](../kb/10-landscape/model-capabilities.md) · [interview/02-context-engineering.md](02-context-engineering.md)

## Q2:KV Cache 是什么?为什么需要?显存怎么算?MQA / GQA / MLA 各优化了什么?

**考察点**:**必考题,而且必须能当场算显存**。答不出公式基本等于没准备。深一层考的是:知不知道 KV Cache 是"用显存换算力"、知不知道 MQA/GQA/MLA 三者优化的是同一个量的不同维度。

**30 秒版**:自回归解码时,第 t 步只新增一个 token,但注意力要看前面所有位置的 K/V。这些 K/V 只依赖已生成的 token、**不随后续步骤变化**,所以缓存起来,每步只算新 token 的 K/V 追加进去——把每步 O(L²) 的重算降到 O(L),整段生成从 O(L³) 降到 O(L²)。代价是显存:

```
KV bytes = 2 × n_layers × n_kv_heads × head_dim × seq_len × batch × dtype_bytes
             ↑ K和V各一份
```

MQA/GQA/MLA 优化的都是这个公式里的第三、四项:**MQA** 把 n_kv_heads 压到 1(省最狠,质量掉得也明显);**GQA** 压到 g 组(当前主流折中);**MLA** 换了思路——不减头数,而是把 K/V 低秩压缩成一个共享 latent 向量再缓存,压缩比更高且质量损失更小。

**深入版**:

**一、为什么必须有它**。没有 KV Cache,生成第 t 个 token 要对前 t 个位置重算全部 K/V,单步 O(t²·d),整段 Σ = O(L³);有 cache 后单步只算 1 个 token 的 K/V(O(d²))加上对 t 个缓存位置做一次注意力(O(t·d)),整段 O(L²)。**这不是优化,是自回归推理可行性的前提。**

**二、算一遍**(70B 级 GQA 模型的典型配置:n_layers=80、n_heads=64、n_kv_heads=8、head_dim=128、FP16):

```
每层每 token = 2 × 8 × 128 × 2 B = 4,096 B  = 4 KiB
每 token     = 4 KiB × 80 层             = 320 KiB
32K 上下文,batch=1 = 320 KiB × 32,768    = 10 GiB
```

**同一个模型若用 MHA(n_kv_heads=64)则是 80 GiB**——一整张 80GB 卡塞不下一个请求的 KV。这个对比就是 GQA 存在的全部理由。

7B 级(32 层、n_kv=8、head_dim=128、FP16)则是 **128 KiB/token**;batch=32、8K 上下文时 KV 占 **32 GiB**——权重才 14 GiB,**KV 比模型还大**。这是"并发上不去"的最常见原因。

**三、三种注意力变体优化了什么**:

| 变体 | 机制 | 缓存量(相对 MHA) | 代价 |
|---|---|---|---|
| MHA | 每个 query 头配独立 K/V 头 | 1× | 基线 |
| MQA | 所有 query 头共享**一组** K/V | 1/h | 质量下降明显、训练易不稳;as-of 2026 前沿模型基本不用,只在极端延迟敏感场景出现 |
| GQA | query 头分 g 组,组内共享 K/V | g/h(如 8/64 = 1/8) | 质量损失很小,**当前事实标准** |
| MLA | 把 K/V 低秩投影成共享 latent `c_t`(维度 d_c),只缓存 c_t + 一小段解耦的 RoPE key | 更高压缩比(DeepSeek 报告约 70 KB/token,对比 GQA 系模型 192–328 KB/token,as-of 2026,口径以原论文为准) | 需要在注意力时"解压";工程上靠把上投影矩阵**吸收**进 W_Q/W_O 来避免真的解压,kernel 实现复杂度高 |

要点:MQA/GQA 减的是**头数**(公式第三项),MLA 减的是**每头的表示维度**(第三×第四项一起换成一个 d_c)。MLA 本质是"KV 的低秩性可以被显式利用"——和 LoRA 用的是同一个直觉(Q7),只是一个用在权重更新上,一个用在激活缓存上。

**四、正交的两个手段**:① **KV cache 量化**(FP16→FP8/INT8,直接砍一半,质量代价通常远小于权重量化);② **prefix caching / KV 复用**——把系统提示、工具定义这段公共前缀的 KV 在请求间共享。**API 层看到的 "prompt caching",服务端就是这件事**。

**实例**(判断一张 80GB 卡能跑多少并发,这是最常见的现场计算题):

```
70B GQA、FP8 权重 = 70 GiB   →  留给 KV 的只剩 ~8 GiB(还要扣激活)
每 token 160 KiB(FP8 KV)   →  总容量 ≈ 8 GiB / 160 KiB ≈ 52K token
若每个 agent 会话平均 20K 上下文 →  并发上限 ≈ 2.6
结论:70B 想跑并发 agent,要么多卡,要么权重降到 4-bit(Q6),要么上 MLA/更激进的 KV 量化
```

**边界与误区**:
- 误区:公式里漏掉开头的 2(K 和 V 各一份)——最常见的口算错误。
- 误区:以为 GQA/MQA 是推理期的优化。它们是**架构选择,必须在预训练时定下**;已训好的 MHA 模型只能靠训练后转换(如 TransMLA 这类方法)迁移,不是配置开关。
- 边界:KV Cache 让 decode 从算力瓶颈彻底转为**带宽瓶颈**——每生成一个 token 都要把整个 KV 从 HBM 读一遍(见 Q4)。所以长上下文不只是费显存,还直接拖慢每 token 延迟。
- **与 agent 的关系(关键)**:agent 每一轮 loop 都把完整历史重发,KV 既是长上下文的成本主体,也是"prompt caching 能省 90% 输入费用"的物理基础。[08 生产化 Q3](08-production.md) 讲的缓存回本模型,回的就是这块显存的账。

**追问预判**:
- 追问:"上下文从 8K 涨到 128K,成本涨多少倍?" → 答:KV 显存线性涨 16×,但**并发数同比下降**,所以单请求摊到的固定成本上涨更多;再叠加 prefill 的 O(L²) 注意力项,端到端不是线性关系。答题要把"显存/带宽/prefill 算力"三笔账分开算。
- 追问:"KV cache 能不能丢一部分?" → 答:能,这是一整个研究方向(按注意力分数淘汰 token、滑窗+attention sink、层间共享)。工程判据是"丢掉的位置会不会在后续被回看"——对 agent 这类需要回溯早期工具结果的场景要格外谨慎。

**关联**:**本组 Q4 推理性能度量** · **本组 Q5 PagedAttention** · [interview/08-production.md](08-production.md) · [kb/01-context-engineering/overview.md](../kb/01-context-engineering/overview.md)

## Q3:Flash Attention 做了什么?为什么能又快又省显存?

**考察点**:能不能说出"它不改变 attention 的数学,改变的是数据在显存层级之间怎么搬"。答成"优化了 attention 算法"是标准的半懂。

**30 秒版**:Flash Attention 是一个 **IO-aware 的精确(exact)注意力实现**,输出与朴素实现在数学上完全等价——没有任何近似。它做了三件事:**分块(tiling)** 把 Q/K/V 切成能装进片上 SRAM 的小块;**在线 softmax(online softmax)** 让 softmax 可以流式增量地算,从而**永远不物化 `[L,L]` 的分数矩阵**;**kernel 融合**把 QKᵀ、mask、softmax、PV 合成一个 kernel。收益的来源不是少算了 FLOPs(反向传播里它甚至多算了),而是**把 HBM↔SRAM 之间的数据搬运从 O(L²) 降到了 O(L²d/M)**。attention 本来就是内存带宽受限的算子,省搬运就等于省时间。

**深入版**:

**一、先建立瓶颈模型**。GPU 显存是分层的:HBM 容量大(几十 GB)但带宽相对低(TB/s 量级);片上 SRAM/shared memory 容量极小(每 SM 百 KB 量级)但带宽高一到两个数量级。朴素 attention 的执行序列是:

```
1. 算 S = QKᵀ            → 把 [L,L] 写回 HBM
2. 从 HBM 读 S,算 softmax → 把 [L,L] 再写回 HBM
3. 从 HBM 读 P,算 PV     → 写回 O
```

三次 O(L²) 级别的 HBM 往返。而这些步骤本身的算术强度很低(尤其 softmax 是纯 element-wise)。**算子是 memory-bound 的,时间花在等数据,不在等算力。**

**二、在线 softmax 是能分块的关键**。softmax 需要全行的最大值和求和,看起来必须先看完整行——这正是"必须物化 L×L"的表面理由。在线 softmax 用一对运行时统计量(running max `m`、running sum `ℓ`)破掉它:每来一个新块,先合并最大值再**对已有结果做指数缩放校正**:

```
m' = max(m, m_new)
ℓ' = e^(m−m') · ℓ + e^(m_new−m') · ℓ_new
O' = e^(m−m') · O + e^(m_new−m') · O_new     ← 已累积的输出按新最大值重新缩放
```

因为始终减去运行最大值,数值上是稳定的;因为缩放因子是精确的指数比,结果是**精确的**而非近似。于是一个 `[B,h,L,L]` 的张量彻底从显存里消失了——**显存从 O(L²) 降到 O(L)**。

**三、反向传播用"重算换搬运"**。训练时反向需要 P,但 P 没被存。Flash Attention 的选择是**在反向时用保存下来的 m、ℓ 现场重算 P**——多花 FLOPs,但省掉了写入和读回 O(L²) 数据的 HBM 往返。**在 memory-bound 的算子上,重算比读回便宜**,这是全篇最反直觉也最值钱的一句。

**四、版本演进的方向(记方向不记数字)**:FA-1 确立 IO-aware + tiling + 在线 softmax;FA-2 改进 work partitioning、减少非 matmul FLOPs、增加沿序列维度的并行(短 batch 长序列场景显著受益);FA-3 面向新一代硬件做异步化(异步拷贝与异步矩阵指令重叠)与低精度支持。另有 **FlashDecoding** 一支:decode 阶段 query 长度只有 1,沿序列维度的并行度消失,于是改为**沿 KV 长度切分并行、最后归约**——这解释了为什么"prefill 用 FlashAttention、decode 用 FlashDecoding"是两套 kernel。

**实例**(把 Q1 的那个数字接下去):`[1, 32, 32768, 32768]` FP16 = 64 GiB 的分数矩阵,在 Flash Attention 下**从不存在**;实际驻留的是几个 `[block_size, d_h]` 的小块(几十 KB 级),加上 `[L]` 的 m/ℓ 统计量与 `[L, d]` 的输出累加器。显存占用与 L 成线性,这才让 32K/128K 上下文在单卡上变得可能。

**边界与误区**:
- 误区:"Flash Attention 是近似算法"。它是 exact 的,和线性注意力/稀疏注意力/低秩近似不是一类东西。这一条答错基本判失。
- 误区:"它减少了计算量"。FLOPs 没少,反向还更多。收益全部来自 IO。
- 边界:收益随序列长度增长而增长;L 很短时融合 kernel 的收益有限。
- 边界:它高度依赖硬件特性(SRAM 大小、异步指令),所以是**按 GPU 架构分别实现**的,新硬件上往往要等专门版本;非 NVIDIA 平台上的可用性与成熟度需要单独验证。
- 与 agent 的关系:Flash Attention 是"长上下文能便宜到可用"的底层前提,但它**只解决 prefill/训练侧的注意力开销,不解决 KV Cache 的显存占用**(Q2)——两者常被混为一谈。agent 的长上下文痛点主要在后者。

**追问预判**:
- 追问:"它和 PagedAttention 是一回事吗?" → 答:不是,而且是正交的两层。Flash Attention 管**单次注意力计算内部**的显存层级搬运;PagedAttention 管**KV Cache 在 HBM 里怎么分配和共享**。生产引擎里两者同时用。
- 追问:"如果我要支持 1M 上下文,光靠 Flash Attention 够吗?" → 答:不够。prefill 的注意力 FLOPs 仍是 O(L²),KV 显存仍是 O(L)。要再叠稀疏/滑窗注意力、KV 量化与淘汰、以及序列并行/上下文并行。

## Q4:推理性能怎么度量(TTFT / TPOT / 吞吐)?prefill 与 decode 两阶段有什么本质差异?

**考察点**:有没有真的部署过。区分点是能说出"prefill 是 compute-bound、decode 是 memory-bandwidth-bound",并能**用 roofline 算出单流 token/s 的理论上限**。

**30 秒版**:四个核心指标:**TTFT**(首 token 延迟,由 prefill 主导)、**TPOT/ITL**(每输出 token 时间,由 decode 主导)、**端到端延迟 = TTFT + TPOT × 输出长度**、**吞吐**(总 token/s 或 req/s;更严谨用 **goodput**——满足 SLO 的请求吞吐)。本质差异在于两阶段的**算术强度**完全不同:prefill 一次前向处理整个 prompt,所有位置并行,是大矩阵乘,**算力受限**;decode 每步只处理 1 个 token,是矩阵×向量,算术强度接近 1,**必须把全部权重和全部 KV 从 HBM 读一遍才产出一个 token,是带宽受限**。所以:batching 对 decode 收益巨大、对 prefill 几乎无效;TTFT 随 prompt 长度增长,TPOT 基本恒定(直到 KV 长到反过来吃带宽)。

**深入版**:

**一、指标定义与常见陷阱**:

| 指标 | 定义 | 陷阱 |
|---|---|---|
| TTFT | 请求发出 → 第一个 token 返回 | 包含排队时间。**高负载下 TTFT 上涨往往是排队而不是计算变慢**,不看队列长度会误诊 |
| TPOT / ITL | 相邻输出 token 的间隔 | 看分布不看均值。长 prefill 插队会造成 ITL 尖刺,均值完全掩盖 |
| 吞吐 | 系统总 output token/s | **和延迟是对立的**:加大 batch 提吞吐、同时抬高 TPOT。报吞吐不报延迟约束等于没报 |
| goodput | 满足 SLO 前提下的吞吐 | 唯一能同时约束两端的指标,选型时应以它为准 |

**二、roofline:decode 的硬上限可以直接算出来**。decode 每步必须从 HBM 读:全部权重 + 当前 batch 的全部 KV。忽略 KV 时:

```
TPOT 下界 ≈ 模型权重字节数 / HBM 带宽
例:70B 模型 FP8 = 70 GB,HBM 带宽 ≈ 3.3 TB/s(H100 SXM 量级)
    → 70 / 3300 ≈ 21 ms/token → 单流上限 ≈ 48 tokens/s
```

**这是物理上限,再多算力也无用**。它同时解释了三件事:为什么小模型吐字明显更快(读的字节少)、为什么权重量化能直接提速(Q6:字节数减半 → 上限翻倍)、为什么 batch=1 的部署浪费 GPU(算力单元大部分时间在等数据)。

**三、batching 为什么对 decode 是"免费午餐"**。权重读一次可以服务 batch 里的所有序列,于是每 token 摊到的权重读取降为 `21ms / B`;在算力饱和前吞吐近似线性增长。**但 KV 的读取是随 batch 线性增加的,不被摊薄**。交叉点可以算:

```
权重字节 70 GB  vs  KV 字节 = B × ctx × 320 KiB(Q2 的 70B 配置)
相等时 B × ctx ≈ 214K token
```

即:**当"batch 内 KV token 总数"超过约 20 万,decode 就从"读权重为主"变成"读 KV 为主"**。batch=8、上下文 32K 的 agent 场景已经越过这条线——这就是"长上下文 agent 吐字慢,且加 batch 也救不回来"的物理原因。

**四、两阶段互相干扰,这是延迟毛刺的头号来源**。同一个引擎里,一个 8K token 的 prefill 会占住 GPU 若干十毫秒,期间所有正在 decode 的请求全部卡住,表现为 ITL 尖刺。三种主流对策:
1. **chunked prefill**:把长 prefill 切块,和 decode 交错调度,牺牲一点 TTFT 换 TPOT 平稳;
2. **prefill/decode 分离(PD disaggregation)**:两阶段跑在不同的卡/节点上,各自按自己的瓶颈选硬件与并行策略,KV 通过高速互联传输(as-of 2026,这已是大规模服务的主流部署范式,vLLM / SGLang / Dynamo / llm-d 等均有实现;跨节点 KV 传输的事实标准是 NVIDIA NIXL——具体成熟度与适用规模需按自己场景核实);
3. **优先级调度**:把交互式请求与批处理请求分池。

**实例**(把指标翻译成用户体感与 agent 体感):

```
聊天场景:TTFT < 500ms 用户才觉得"秒回";TPOT < 50ms(20 tok/s)超过阅读速度即可
agent 场景:完全不同——用户不逐字读,关心的是"整轮多久做完"
           单轮耗时 ≈ Σ_i (TTFT_i + TPOT × 输出_i),i 遍历所有 loop 轮次
           agent 每轮输出通常很短(一次工具调用几十 token),历史却越来越长
           ⇒ 大头是 Σ TTFT,即 prefill;而 prefill 正是 prompt caching 能直接消掉的部分
```

这正好接上 [08 生产化 Q3](08-production.md) 的结论"agent 的延迟大头是轮次数 × 每轮 TTFT"——那是应用层的观察,这里是它的物理解释。

**边界与误区**:
- 误区:报"吞吐 X tokens/s"而不说 batch 与延迟约束。孤立的吞吐数字没有意义。
- 误区:用均值衡量 TPOT。必须看 p95/p99,尖刺才是用户投诉的来源。
- 误区:以为 prefill 也能靠 batching 提速。prefill 早已把算力打满,batch 更多只是排队。
- 边界:开启 prefix caching 后 TTFT 的分布会**双峰化**(命中 vs 未命中),此时均值毫无意义,必须分开统计并单独盯命中率。

**追问预判**:
- 追问:"TTFT 突然变差,怎么定位?" → 答:先分排队 vs 计算(看队列深度与 batch 占用),再看是否 prefix cache 命中率掉了(前缀被改动过),最后才看是否有超长 prompt 挤占。**顺序很重要**:前两项是最常见的原因。
- 追问:"speculative decoding 改善的是哪个指标?" → 答:主要是 TPOT/端到端延迟——用小模型一次猜多个 token、大模型一次前向并行验证,把"读一次权重出 1 个 token"变成"读一次权重出 k 个 token",本质是**提高 decode 的算术强度**。接受率低时反而变慢,且对吞吐不一定有利(高 batch 下算力已紧张)。

## Q5:continuous batching 与 PagedAttention 分别解决什么问题?

**考察点**:能不能一句话切开——**一个解决时间上的浪费,一个解决空间上的浪费**。混为一谈是常见失分点。

**30 秒版**:**continuous batching(又叫 iteration-level scheduling)解决时间浪费**:静态 batching 里一批请求必须等最长的那个跑完才整批退出,先完成的槽位空转,新请求也进不来;改成"每个 decode step 都重新调度",完成即离场、新请求即插入,GPU 不再空转。**PagedAttention 解决空间浪费**:传统做法为每个请求按 max_len 预留一段**连续**的 KV 显存,造成严重的内部碎片(预留 2048 实际只用 300)与外部碎片,且无法共享;PagedAttention 借操作系统虚拟内存的思路,把 KV 切成固定大小的 block,用 block table 做逻辑页→物理页映射,注意力 kernel 支持从不连续的块里取数。两者互补:**前者决定"能同时跑多少请求",后者决定"显存里能装下多少请求"**——而后者往往才是真正的约束。

**深入版**:

**一、continuous batching 的机制**。调度粒度从"请求"下沉到"迭代":

```
静态 batching:  [req A ████████████████████]  ← 输出 500 token
                [req B ███░░░░░░░░░░░░░░░░░]  ← 输出 50 token,之后 90% 时间在空转
                新请求必须等整批结束
连续 batching:  每个 step 后:已完成的出队 → 空出的槽位立刻被队列里的新请求填上
```

收益大小取决于**输出长度的方差**。方差越大(真实流量恰恰如此:有的请求 20 token、有的 2000 token),收益越大。这就是为什么它在真实负载上的提升远大于合成 benchmark。

**二、PagedAttention 的机制与三重收益**。KV 按固定 token 数(如 16)分块,每个序列维护一张 block table:

- **消除碎片**:浪费上限是"每个序列最后一个未填满的 block",与 max_len 无关;
- **按需增长**:序列变长时追加分配,不需要预知最终长度,也不需要连续地址;
- **共享(这是被低估的一条)**:多个序列的相同前缀可以**指向同一批物理 block**,写时复制。并行采样、beam search 自然受益,而对 agent 最重要的是——**共享 system prompt + 工具定义的前缀 KV 只存一份**。这就是 **prefix caching** 的实现基础,也是 API 层 "prompt caching" 的服务端真身。

**三、把收益算出来**(80GB 卡跑 13B MHA 模型:40 层、40 头、head_dim 128、FP16):

```
权重 26 GiB,留给 KV ≈ 50 GiB
每 token KV = 2×40×128×2 B ×40 层 = 800 KiB
KV 总容量 = 50 GiB / 800 KiB ≈ 65,536 token

静态预留 max_len=2048:  并发 = 65536 / 2048 = 32 个请求
  若平均实际只用 300 token → 有效利用率 300/2048 ≈ 15%,85% 显存被浪费
分页按需分配:          并发 ≈ 65536 / 300 ≈ 218 个请求   → 约 6.8×
```

**同一张卡、同一个模型、同样的算力,并发差 6.8 倍,全部来自内存管理**。这个数量级就是 PagedAttention 论文级影响力的来源,也是面试里最有说服力的一段现场计算。

**四、两者的关系**。continuous batching 让 batch 组成**每一步都在变**——这恰恰是静态连续显存分配最不擅长的模式。**没有分页式内存管理,连续 batching 的调度自由度就发挥不出来**;反过来,没有连续 batching,分页省下的显存也没有请求去填。它们是同一套设计的两半:一个是调度器,一个是内存分配器,合起来把 GPU 当成一台跑 LLM 的操作系统。

**实例**(as-of 2026 的引擎格局,只记定位不记分数):生产级开源服务框架已收敛到少数几家——vLLM 覆盖硬件最广、上手最快,通常作为默认选择;SGLang 在结构化生成、约束解码与复杂 agent 调度上更强;TensorRT-LLM 在 NVIDIA 硬件上做深度编译优化、峰值性能领先但工程门槛与迭代成本更高。**选型判据不是"谁最快",而是"我的负载像什么"**:高并发短请求看调度器质量,长上下文看 KV 管理与前缀复用,固定模型固定硬件的大规模部署才值得上编译式方案。(具体性能对比随版本变化很快,任何跨框架数字都必须自测,不要引用博客里的百分比。)

**边界与误区**:
- 误区:"continuous batching 就是 dynamic batching"。dynamic batching(传统推理服务里的攒批)仍是请求级的,只是攒批窗口可变;continuous batching 是**迭代级**的,量级不同。
- 误区:把 PagedAttention 当性能优化。它的直接收益是**显存利用率**,吞吐提升是"能装下更大 batch"的二阶结果。
- 边界:block 太小 → block table 与 kernel 间接寻址开销上升;太大 → 碎片回来。是个可调参数,不是免费的。
- 边界:前缀共享要求前缀**逐字节相同**。system prompt 里塞了时间戳、工具列表顺序不稳定、JSON 未排序,共享就静默失效——和 [08 生产化 Q3](08-production.md) 讲的缓存失效是同一件事的两面。
- **与 agent 的关系**:并发 agent 的瓶颈几乎总是 KV 显存而不是算力(每个 agent 都是长上下文、短输出的重 prefill 负载)。工程动作有三条:稳定前缀以吃满前缀共享、控制历史长度、KV 量化。

**追问预判**:
- 追问:"batch 越大越好吗?" → 答:不是。① 显存装不下;② TPOT 随 batch 上升,会击穿延迟 SLO;③ 越过 KV 带宽交叉点(Q4)后吞吐增速放缓。正确做法是**在延迟 SLO 约束下最大化 goodput**,而不是最大化 batch。
- 追问:"抢占(preemption)是怎么回事?" → 答:显存不够时引擎会把某些序列的 KV 换出(swap 到主存)或直接丢弃后重算(recompute),之后再恢复。这会造成 TPOT 长尾;线上看到无法解释的 ITL 尖刺,应优先查抢占次数。

## Q6:量化:INT8 / INT4 / FP8 的原理、精度损失来源与选型判据?

**考察点**:知不知道**权重量化(W4A16)与权重+激活量化(W8A8)加速的是完全不同的阶段**;知不知道精度损失的主因是**激活里的离群值**而不是"位数不够"。

**30 秒版**:量化是把高精度张量映射到低位宽表示:对称量化 `x ≈ s·q`(s = max|x| / (2^(b−1)−1)),非对称再加零点 `x ≈ s(q − z)`。粒度从 per-tensor → per-channel → per-group(如每 128 个元素一组)→ per-block(FP4 格式是 16 或 32 元素一块),越细越准、scale 开销越大。精度损失的主因是**激活里存在系统性的离群通道**(量级可达常规值的百倍),一个粗粒度 scale 会把其余数值压到只剩几个量化档位。选型判据不是"能压多小",而是**你的瓶颈在哪**:显存装不下 → 压权重;decode 带宽受限、batch 小 → 权重量化(W4A16)直接见效;prefill 算力受限、batch 大 → 必须用低精度 GEMM(FP8/FP4)才有加速;质量敏感(工具调用、结构化输出、长链推理)→ 停在 FP8。

**深入版**:

**一、权重量化 vs 权重+激活量化——最重要的一刀**:

| 方案 | 记法 | 加速 decode? | 加速 prefill? | 原因 |
|---|---|---|---|---|
| 权重量化 | W4A16 / W8A16 | **是** | **否**(甚至更慢) | decode 是带宽受限,权重字节减半 → 速度近似翻倍;但计算时必须反量化回 FP16 才能上 tensor core,大 batch 下这层反量化成了纯开销 |
| 权重+激活量化 | W8A8(INT8/FP8)、W4A4(NVFP4) | 是 | **是** | GEMM 本身在低精度 tensor core 上执行,算力吞吐直接翻倍 |
| KV 量化 | KV8 / KV4 | 是(长上下文尤其) | — | 正交维度,省的是 KV 显存与 KV 读带宽 |

这张表就是选型的骨架。**"我用了 INT4,为什么高并发下反而更慢"是高频线上问题,答案就在第一行的第二列。**

**二、精度损失从哪来**:
1. **激活离群值(主因)**。Transformer 的激活中存在少数固定通道的极端值,随规模增大而显性化。per-tensor scale 由离群值决定 → 其余 99% 的值被挤进极少的量化档位。三条主流对策思路各不相同:
   - **混合精度分解**(LLM.int8() 路线):把离群通道单独留在 FP16,其余走 INT8;
   - **难度迁移**(SmoothQuant 路线):按通道做 `X̂ = X/s, Ŵ = s·W`,数学上完全等价,但把激活的量化难度"搬"一部分到更好量化的权重上;
   - **重要性感知**(AWQ 路线):用激活量级识别约 1% 的显著权重通道并加以保护——注意它保护的是**权重**,依据却是**激活**统计,这是名字的由来。
   另有 **GPTQ** 路线:逐层用二阶(Hessian)信息做误差补偿,量化一列后把误差分摊到尚未量化的列上。
2. **误差沿深度累积**。单层看不出来,几十层叠加后偏差被放大;**长链推理与多轮 agent 轨迹是放大器**,这是 4-bit 在推理密集任务上仍不被视为 FP8 安全替代的原因(as-of 2026)。
3. **校准数据不匹配**。训练后量化要用一小批数据统计激活范围;校准集与线上分布不一致,离群范围就估错。**用你自己的真实流量做校准**,别用通用语料。

**三、INT8 / FP8 / FP4 的取舍**:
- **INT8**:均匀间隔、老硬件普遍支持;动态范围窄,对离群值最敏感,必须配 SmoothQuant/分解一类手段。
- **FP8**(E4M3 常用于权重与激活,E5M2 动态范围更大):同为 8 bit,但**间隔非均匀**——小值处密、大值处疏,天然更适配"多数值小、少数值极大"的激活分布。Hopper 起有原生 tensor core 支持。**as-of 2026,FP8 是现代 NVIDIA 硬件上生产部署的默认安全档**:接近无损、两端(权重+激活)都加速。
- **FP4**(as-of 2026):Blackwell 第五代 tensor core 原生支持 **NVFP4** 与 **MXFP4**,两者的元素都是 E2M1 四位浮点,差别在分块与 scale——NVFP4 用 16 元素块 + FP8(E4M3) scale,MXFP4 用 32 元素块 + E8M0(2 的幂)scale。**NVFP4 精度更好,MXFP4 胜在跨厂商可移植**(AMD 侧亦支持)。共同边界:推理密集/长链任务上 4-bit 的噪声会沿推理链累积,不能默认当作 FP8 的等价替代。

**实例**(70B 模型,显存账与部署形态的直接映射):

```
FP16   140 GB  → 至少 2 张 80GB 卡,KV 空间紧张
FP8     70 GB  → 勉强单卡,剩 ~8 GB 给 KV(见 Q2 的并发测算:并发只有个位数)
4-bit   35 GB  → 单卡剩 ~45 GB 给 KV → 并发提升近一个数量级
```

**注意最后一行的收益来源**:主要不是"模型跑得更快",而是**腾出来的显存变成了 KV 容量,从而变成了并发**。这是量化在服务端最大的一笔账,也是最常被忽略的一笔。

**边界与误区**:
- 误区:用 perplexity 验证量化质量。**perplexity 对 agent 关心的失败模式极不敏感**——JSON 结构合法性、工具选择准确率、长指令遵循度可能已经明显退化,而 ppl 只动了小数点后两位。必须用你自己的任务级评估集([kb/06-evals/agent-evals.md](../kb/06-evals/agent-evals.md))。
- 误区:"量化 = 压缩显存"。它同时改变速度、并发、质量三条曲线,而且方向不一致(见上表)。
- 误区:把 QAT(量化感知训练)与 PTQ(训练后量化)混为一谈。生产上 99% 是 PTQ(几分钟到几小时);QAT 要重训,只在极低位宽或专用硬件上才划算。
- 边界:MoE 模型的量化更微妙——专家权重占绝大部分显存,是量化的主要收益来源,但不同专家的敏感度差异大,均一位宽往往不是最优。
- **与 agent 的关系(关键)**:量化最先伤到的恰恰是 agent 最依赖的能力——**结构化输出的合法率与工具选择的准确率**,而这两项在通用榜单上几乎看不出来。判据:任何量化上线前,先跑一遍**工具调用轨迹回归集**,门槛是"不劣化",与 [08 生产化 Q5](08-production.md) 的 prompt 发布流程同一套。

**追问预判**:
- 追问:"KV cache 量化和权重量化哪个先做?" → 答:看瓶颈。长上下文、高并发场景 KV 往往比权重还大(Q2 的 7B 例子),此时 KV 量化收益更大,而且**质量代价通常比权重量化小**;短上下文场景反过来。
- 追问:"量化后要怎么验收?" → 答:三层——① 数值层(逐层激活相似度/余弦距离,定位是哪层崩了);② 任务层(自己的评估集,含结构化输出与工具调用);③ 服务层(实测 TTFT/TPOT/并发,验证加速真的发生在你的 batch 规模上)。

## Q7:微调:全参微调 vs LoRA / QLoRA 的机制与选型?为什么 LoRA 有效?

**考察点**:**"为什么 LoRA 有效"是这题的分水岭**——答"因为参数少所以省显存"是循环论证,要答到"权重更新的内在秩很低"这个假设,并能由它推出 LoRA 的能力边界。同时要能算显存与参数量。

**30 秒版**:全参微调更新全部权重,显存开销按 Adam 混合精度约 **16 字节/参数**(FP16 权重 2 + 梯度 2 + FP32 master 4 + Adam 一阶 4 + 二阶 4),7B 就要约 112 GB,单卡放不下。LoRA 冻结原权重 W,只训练一对低秩矩阵:`h = Wx + (α/r)·BAx`,`B ∈ R^{d_out×r}` 初始化为 0、`A ∈ R^{r×d_in}` 高斯初始化(B=0 保证训练起点的函数与预训练模型**完全一致**)。可训练参数每个矩阵仅 `r×(d_in+d_out)`。QLoRA 再把冻结的基座量化到 4-bit(NF4)+ 双重量化 + 分页优化器,把单卡门槛再降一个数量级。**LoRA 有效的核心假设是:把预训练模型适配到下游任务所需的权重更新 ΔW 具有很低的内在秩**——预训练已经学好了特征,适配主要是在一个低维子空间里重新加权,而不是学新特征。这个假设同时定义了它的边界:**擅长唤起与调整已有能力,不擅长注入大量新知识**。

**深入版**:

**一、把参数量算出来**(d=4096、d_ff=11008、32 层、6.7B 基座):

```
每个被适配矩阵的可训练参数 = r × (d_in + d_out)

方案 A:只挂 q_proj / v_proj,r=16
  单矩阵 16 × (4096+4096) = 131,072
  2 矩阵 × 32 层 = 64 个 → 8.4M 参数 = 基座的 0.125%

方案 B:挂全部线性层(q,k,v,o,gate,up,down),r=16
  q/k/v/o 各 131,072;gate/up/down 各 16×(4096+11008) = 241,664
  每层 4×131,072 + 3×241,664 = 1,249,280 → ×32 层 ≈ 40M 参数 = 0.6%
```

对应的优化器状态显存:全参 `6.7B × 16 B ≈ 107 GB`;LoRA(方案 B)`40M × 16 B ≈ 640 MB`。**三个数量级的差距**。

**二、LoRA 省的是什么、没省什么**(这是最常被答错的一层):

| 显存组成 | 全参微调 | LoRA | 说明 |
|---|---|---|---|
| 优化器状态 + 梯度 + master 权重 | 14 B/param | 仅适配器 | **省掉几乎全部** |
| 基座权重(前向必需) | 2 B/param(13.4 GB) | 仍需 2 B/param(QLoRA 降到约 0.5 B) | 只有 QLoRA 才省这块 |
| 激活值(反向传播必需) | 随 batch×seq×层数 | **基本不省** | 梯度仍要穿过全部冻结层才能到达适配器 |

由此得到两条实践结论:① **LoRA 的显存瓶颈很快会转移到激活值**,所以 gradient checkpointing 仍然要开;② **反向传播的计算量没省多少**——省的只是"算权重梯度"这一步,"算输入梯度"这一步一层都跳不掉。所以 LoRA 的每步耗时通常只比全参微调略低,它买的是**显存**,不是**速度**。

**三、QLoRA 的三件套**:
- **NF4(4-bit NormalFloat)**:量化档位按正态分布的分位点排布,而不是均匀排布——因为神经网络权重近似正态,这样每个档位承载的概率质量相等,信息论上更优;
- **双重量化**:把量化 scale 本身再量化一次,进一步压掉每参数零点几比特;
- **分页优化器**:借统一内存在显存尖峰时把优化器状态换出,防止偶发 OOM 直接中断长训练。
基座 6.7B 从 13.4 GB 降到约 3.5–4 GB;代价是前向要**实时反量化**,每步明显变慢(量级上是几成,具体视实现与硬件,需实测)。**QLoRA 是"用时间换单卡可行性"**,不是无损优化。

**四、为什么 LoRA 有效——第一性解释**。出发点是"内在维度"这一系列观察:预训练模型在下游任务上的适配,可以在一个远低于全参维度的随机子空间里完成;模型越大,所需内在维度反而越小。LoRA 把这个观察变成显式的结构约束——直接把 ΔW 参数化为秩 r 的乘积。进一步的分析显示,ΔW 的主要作用是**放大那些原本已存在于 W 中、但在预训练里被弱化的特征方向**,而不是创造新方向。

**从这个假设可以推出所有边界,这才是高分回答**:
- 任务只是改变**表达形式、风格、格式、语气、遵循某套工具 schema** → ΔW 天然低秩 → LoRA 极其有效,r 取 8–16 足够;
- 任务要注入**大量新知识、新语言、远离预训练分布的新领域** → 这本质需要高秩更新 → LoRA 会先饱和,应走全参微调或继续预训练;
- 副产品:低秩约束天然是**正则化**——灾难性遗忘更轻,但能力天花板也更低。这一利一弊同源。
- 经验上**挂哪些模块比 r 取多大更重要**:只挂 q/v 是老配方,挂全部线性层(尤其 FFN 三件)通常明显更好。

**实例**(选型判据表):

```
只要改输出格式/语气/遵循内部工具 schema  → LoRA,r=8~16,挂全线性层
中等领域适配(术语、文风、专有流程)      → LoRA,r=32~64,或 QLoRA(卡不够时)
新语言 / 大规模新知识                     → 全参微调 或 继续预训练;LoRA 会撞天花板
多租户(N 个客户共用一个基座)            → LoRA 完胜:适配器约 80 MB(40M × 2 B),
                                            可热插拔,multi-LoRA 服务在一个基座上同时挂 N 个
延迟极敏感的单一用途部署                  → LoRA 训完 merge 回基座(W ← W + (α/r)BA),
                                            推理零额外开销;但 merge 掉了多租户的好处
```

**边界与误区**:
- 误区:"LoRA 比全参微调训练更快"。省显存 ≠ 省时间,前向与大部分反向照做(见上表)。
- 误区:r 越大越好。r 增大到某个点后收益趋平,而且**过大的 r 会让低秩正则化消失**,重新出现过拟合与遗忘。
- 误区:merge 之后还能多适配器共存。merge 是把 ΔW 写死进 W,是不可逆的取舍。
- 边界:**做微调之前先确认提示工程/上下文工程/few-shot 已经无效**。微调把行为固化进权重,代价是每次基座升级都要重训——在基座模型迭代速度极快的当下,这是一笔持续的负债。
- **与 agent 的关系**:大多数"让 agent 输出符合我们工具规范/公司风格"的需求形态上是 LoRA 问题,但工程上第一选择仍是系统提示 + 工具描述 + few-shot——**因为它可以随时改、随时回滚、不锁模型版本**([08 生产化 Q5](08-production.md) 的发布工程只对提示成立,对权重就变成了重训成本)。微调应保留给"提示已经写到极限仍不达标"或"需要小模型逼近大模型行为以省成本"的场景。

**追问预判**:
- 追问:"α 是干什么的?" → 答:缩放因子,实际乘的是 α/r。它的作用是让**改变 r 时不必重调学习率**——常见做法是 α 固定为 r 的某个倍数;把 α/r 理解为"适配器输出的增益"最直观。
- 追问:"LoRA 训完质量不如全参,差在哪?" → 答:先查两件工程事而不是急着下结论——① 是否只挂了 q/v(挂全线性层往往就补回来了);② 学习率是否照搬全参的量级(LoRA 通常要高一个数量级)。工程因素排除后,若仍有差距,再判断是不是撞上了"任务需要高秩更新"的真实边界。

## Q8:对齐训练:RLHF 与 DPO 的机制差异?各自的工程代价?

**考察点**:能不能讲出 **DPO 的推导直觉**——"最优策略与奖励之间存在闭式关系,把它反解出来代进偏好损失,奖励模型就消失了"。只会说"DPO 更简单"是背结论。加分项:知道 as-of 2026 后训练已经模块化,可验证奖励(RLVR)是当前主线。

**30 秒版**:**RLHF** 是三阶段:① SFT 得到初始策略;② 用成对偏好数据训一个奖励模型(Bradley-Terry 损失 `−log σ(r(x,y_w) − r(x,y_l))`);③ 用 PPO 最大化 `E[r(x,y)] − β·KL(π_θ‖π_ref)`,KL 项防止跑偏与奖励黑客。**DPO** 的洞察是:上述 KL 约束优化问题的最优解有闭式形式 `π*(y|x) ∝ π_ref(y|x)·exp(r(x,y)/β)`,反解得到 `r = β·log(π/π_ref) + β·log Z(x)`;把它代回 Bradley-Terry 损失,配分函数 Z(x) 因为同一个 x 下对 y_w、y_l 相同而**直接抵消**,于是奖励模型被消掉了——**语言模型隐式地就是它自己的奖励模型**,训练退化成一个在偏好对上的监督分类损失。工程代价差一个数量级:PPO 要同时驻留 4 个模型(策略、参考、奖励、价值)且训练中在线采样;DPO 只要 2 个(策略 + 冻结参考)、离线数据、一个稳定的损失。

**深入版**:

**一、两条路径的机制对照**:

| 维度 | RLHF(PPO) | DPO |
|---|---|---|
| 阶段数 | SFT → RM → PPO(三段) | SFT → DPO(两段) |
| 驻留模型 | 4:策略(训)、参考(冻)、奖励(冻)、价值/critic(训) | 2:策略(训)、参考(冻) |
| 数据 | 在线 rollout,每步现采 | 离线偏好对,一次准备 |
| 主要超参 | β(KL 系数)、clip ε、GAE λ、优势归一化、策略与 critic 两套学习率 | β(隐式 KL 强度)、学习率 |
| 训练稳定性 | 差,以难调著称;需要分布式 rollout 基础设施 | 好,和 SFT 同一套训练栈 |
| 计算大头 | **采样(rollout)通常主导墙钟时间** | 一次前向两遍(策略/参考)× 两个回答 |

DPO 的损失写出来是:

```
L_DPO = −log σ( β·log[π_θ(y_w|x)/π_ref(y_w|x)] − β·log[π_θ(y_l|x)/π_ref(y_l|x)] )
```

读法:括号里是"策略相对参考模型,给优答加了多少对数概率" 减去 "给劣答加了多少"。**优化的是差值(margin),不是绝对概率**——这一句直接引出它的主要失效模式。

**二、DPO 的代价:便宜不是白来的**:
1. **离线/off-policy**。偏好数据由别的策略生成;随着 π_θ 训练中不断漂移,数据分布与当前策略越离越远,梯度信号质量下降。而奖励模型的价值恰恰在于**它能对没见过的新样本打分**——DPO 用固定数据集换掉了这份泛化能力。这是 DPO 与在线 RLHF 之间质量差距的主要来源。
2. **似然位移(likelihood displacement)**。因为只优化 margin,训练可能让 y_w 和 y_l 的概率**同时下降**,只要 y_l 掉得更快——概率质量被推到数据集之外的未建模区域,产出退化或啰嗦的输出。常见缓解:在损失里加一项对 y_w 的 SFT/NLL 正则;或改用**迭代式/在线 DPO**(每轮用当前策略重新采样、重新标注偏好),把 off-policy 的问题按轮次消掉。
3. **对 SFT 阶段依赖强**。若 y_w 本身对 π_ref 就是低概率的(不在分布内),优化会很别扭;标准做法是先在优答上做一遍 SFT 再 DPO。
4. **β 的两端**:太小 → 隐式 KL 约束过弱,退化与冗长;太大 → 几乎不动。

**三、as-of 2026 的实际格局**(重点在结构,不在名词):后训练已经**模块化**成三段栈——
```
SFT(学会遵循指令与格式)
  → 偏好优化(DPO / KTO / SimPO 等):调"品味"——风格、语气、有用性、拒答边界
  → RLVR(可验证奖励的 RL,以 GRPO / DAPO 一类算法为主):练"能力"——数学、代码、推理
```
**GRPO 的机制值得单独会讲**:它砍掉了 PPO 的价值网络——对同一个 prompt 采样一组 K 个回答,用**可验证的奖励函数**(测试是否通过、答案是否正确)给每个打分,优势直接用组内均值与标准差归一化得到。省掉 critic 就省掉了它的显存与"训练一个准确 critic"这个老大难。整体趋势是**从人工标注的奖励,转向自动验证与自我博弈**。

**实例**(选型判据):

```
有成对偏好数据、目标是风格/语气/有用性/安全边界   → DPO(先 SFT 再 DPO),性价比最高
有自动可验证的奖励(测试通过、答案匹配、编译成功) → GRPO/RLVR;这是能力增长最快的一条路
需要长程信用分配 + 已有成熟分布式 RL 基础设施     → PPO + 奖励模型仍是上限最高的选择
只有"好/坏"单点标注而非成对比较                   → KTO 一类只需二元反馈的方法
```

**边界与误区**:
- 误区:"DPO 全面取代了 RLHF"。DPO 取代的是**PPO 这个优化器**,没取代 RLHF 的**思想框架**(用人类偏好定义目标);而且在线 RLHF 在质量上限上通常仍占优。
- 误区:"DPO 里没有 KL 约束"。有,β 就是它,只是从显式惩罚项变成了损失函数结构里的隐式约束——这正是推导带来的。
- 误区:奖励模型分数高 = 模型更好。**奖励黑客**是这条路的固有风险:模型学会取悦奖励模型(变长、堆格式、过度自信),而非真的更有用。这也是必须保留 KL 项与独立留出评估的原因。
- 边界:**对齐训练会引入 agent 开发者随后要对抗的行为**——过度迎合(sycophancy)、过度拒答、倾向给出"看起来完整"的答案而非承认不知道。理解它的来源(奖励信号偏好"读起来更好的回答")能让你在提示层更有针对性地纠偏。
- **与 agent 的关系(最值钱的一条)**:当代模型的 agentic 能力,主要不是靠偏好对齐练出来的,而是靠 **在多轮工具使用轨迹上做可验证奖励的 RL**——奖励是"测试是否通过 / 任务是否真的完成"。这与应用层反复强调的"验证闭环"([10 编码代理](10-coding-agents.md))是同一个原理在训练侧与应用侧的两次出现:**可自动验证的信号,既是训练模型的最好奖励,也是评估 agent 的最好判据**。答出这条,基本就把底层与应用层打通了。

**追问预判**:
- 追问:"DPO 训练时参考模型每步都要前向,能省吗?" → 答:能。参考模型是冻结的,可以**预计算并缓存** `log π_ref(y|x)`(数据集固定,只需一遍),训练时直接读——显存与算力都省一半。这是很实在的工程点。
- 追问:"怎么判断对齐训练是否过头了?" → 答:看**能力回退**——留出一组与对齐目标无关的能力评估(代码、数学、长指令遵循),对齐前后对比;同时盯"拒答率"和"平均回答长度"两个廉价代理指标,它们通常最先异常。

## 本组事实基线(as-of 2026-08-19)

> 版本敏感断言集中于此,便于后续核对与更新。公式、推导与机制部分不随版本变化。
> 本组刻意**不写具体框架版本号与跨框架 benchmark 分数**——这类数字变化极快且口径不一,任何跨框架性能对比都必须在自己的负载上实测。

- **注意力变体**:GQA 是当前事实标准;MQA 在前沿模型上已基本退出,仅见于极端延迟敏感场景;MLA 由 DeepSeek 提出并在其模型上使用,压缩比显著高于 GQA(公开报告约 70 KB/token 对比 GQA 系模型的 192–328 KB/token,**口径需以原论文为准**);已有训练后把 GQA 模型转换为 MLA 的研究路线。
- **量化格式**:FP8 是现代 NVIDIA 硬件上的默认生产档。FP4 方面,Blackwell 第五代 tensor core 原生支持 NVFP4(16 元素块 + FP8 E4M3 scale)与 MXFP4(32 元素块 + E8M0 scale);NVFP4 精度更优,MXFP4 胜在跨厂商可移植。4-bit 在长链推理任务上仍不视为 FP8 的安全等价替代。
- **推理框架格局**:生产级开源方案已收敛为少数几家,定位分别是"最通用/最易上手"(vLLM)、"结构化生成与复杂调度更强"(SGLang)、"NVIDIA 硬件上深度编译优化"(TensorRT-LLM)。**具体排名与性能差异 as-of 需核实并自测。**
- **部署范式**:prefill/decode 分离(PD disaggregation)已成为大规模服务的主流部署形态,主流引擎均有实现;跨节点 KV 传输的常见方案为 NVIDIA NIXL(RDMA/TCP)。适用规模与成熟度 as-of 需核实。
- **后训练格局**:已模块化为 SFT → 偏好优化(DPO/KTO/SimPO)→ 可验证奖励 RL(GRPO/DAPO)三段栈;趋势是从人工标注奖励转向自动验证与自我博弈。PPO + 奖励模型在需要长程信用分配时仍是上限最高但成本最高的路径。
- **硬件量级参考**(用于估算,非精确规格):H100 SXM 的 HBM 带宽约 3.3 TB/s。做 roofline 估算时应以自己实际硬件的规格书为准。
