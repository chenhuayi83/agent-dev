# 面试题:08 生产化与可靠性

> 每题讲透五件套:本质 / 机制 / 实例 / 边界 / 检验(追问预判)。答案分 30 秒版 + 深入版。
> 本组的共同主线:**agent 的不确定性会渗进每一条运维假设**——重试不再是重放、成功不再是二值、发布不再有编译期。

## Q1:Agent 的重试与幂等怎么设计?为什么 agent 的重试比普通 RPC 复杂?

**考察点**:能否区分"传输层重试"与"语义层重试";有没有副作用治理的工程意识,而不是"加个 retry 装饰器"。

**30 秒版**:普通 RPC 重试只需保证"同一请求重放结果一致",幂等键 + 去重表就够。agent 的重试难在三层叠加:(a) **模型调用不确定**——同样输入可能走出不同轨迹,重试不是重放而是重掷骰子;(b) **工具有真实副作用**——发邮件、改文件、下单,最危险的失败点是"已执行未记录";(c) **失败位置不确定**——一次任务是几十轮 loop,重试粒度到底是整个任务、这一轮、还是这一次工具调用?所以答案是**分层**:传输层自动重试(无外部副作用)、工具层幂等键 + at-least-once、任务层 checkpoint 续跑(而不是从头重跑)。

**深入版**:

**1. 三层重试栈,每层失败语义不同**

| 层 | 典型失败 | 重试方式 | 幂等要求 |
|---|---|---|---|
| 传输层 | 429 / 5xx / 连接中断 / 超时 | SDK 自动重试 + 指数退避 | 天然幂等(纯模型调用无外部副作用) |
| 工具层 | 工具执行报错、下游 API 失败 | 优先"错误即数据"回传模型;harness 只对明确只读的工具静默重试 | 写操作必须幂等键去重 |
| 任务层 | 会话被杀 / 上下文爆 / 预算耗尽 | 从 checkpoint 续跑 | 阶段级"已完成"标记 |

**2. 传输层自动重试是个安静的陷阱**。Anthropic SDK 默认 `max_retries=2`,重试 408/409/429/5xx 与连接错误,`timeout` 默认 10 分钟(as-of 2026-08)。两个非直觉后果:**超时也在重试范围内**,最坏挂钟 = `timeout × (max_retries+1)`;而**超时 ≠ 没执行**——请求可能已在服务端完成,只是响应没回来。对纯模型调用无害(重来只是多花钱),但这一轮若触发了 server-side tool(代码执行、web fetch),重试语义就不再干净。相关坑:server tool 的错误**不抛异常**,而是 HTTP 200 里返回一个错误块——按异常来分类重试的代码会直接漏掉它。

**3. 幂等的两条路径**
- **幂等键**:`key = hash(tool_name, canonical(args), task_id, step_id)`,工具适配层先查已执行表,命中即返回上次结果。key 必须包含 task/step——否则同一任务里两次合法的"发同一封邮件"会被误去重。
- **可交换 / 可覆盖设计**:把"追加"改成"设置",把"发送"改成"upsert 到出件箱 + 独立投递器"。这是分布式系统的老办法:**能设计成幂等就别靠去重表**。

**4. agent 独有的第四难:重试会改变上下文**。失败的 tool_result 留在历史里,重试时模型看到"上次这么调失败了",可能换一条路。这既是自愈能力的来源,也是不可重放性的来源。于是有工程折中:**瞬时/传输错误由 harness 静默重试 ≤N 次;语义错误(参数错、权限拒、业务拒)一律回传模型;同一工具同一参数连续失败 K 次触发熔断,把"这条路走不通"作为显式信号注入**。全交给 harness 会浪费模型智能,全交给模型会陷入循环。

**5. 并行调用的重试细节**:一条 assistant 消息里的多个 `tool_use`,必须在**一条** user 消息里返回**全部** `tool_result`;失败的那个要带 `is_error: true` 回传,而不是丢掉——丢掉会破坏 tool_use/tool_result 配对,请求直接报错。实现重试时最容易踩的就是"重试成功的、丢掉失败的"。

**实例**(本仓库的任务层续跑,见 [meta/PROTOCOL.md](../meta/PROTOCOL.md)):

```
每阶段结束: git add -A && git commit   +   写回 state.json 的 pending
下次启动 P0: 读 meta/state.json
             pending 非空 → 先做完遗留阶段,再走当天流程
```

幂等来自两点:① 阶段边界是 git commit,重跑一个阶段最坏是"重做一次已提交的工作",不会留半成品;② 情报去重靠 `meta/seen.jsonl`——每条候选先用规范化 URL(去协议、去查询参数)`grep -F` 查已见表,命中即弃。**规范化 URL 就是幂等键**,jsonl 就是去重表,这是该模式的最小实现。同理,协议规定合并失败时"不做任何破坏性操作、保留分支、交给下次运行 P0 自愈"——把重试推迟到下一次运行,而不是当场 force。

工具层骨架:

```python
def call_tool(tool, args, task_id, step_id, attempt=0):
    key = sha256(f"{tool.name}|{canonical_json(args)}|{task_id}|{step_id}")
    if (prev := store.get(key)):            # 幂等命中,不重复执行
        return prev
    try:
        r = tool.run(args)
    except TransientError as e:
        if tool.read_only and attempt < N:  # 只读 + 瞬时 → harness 自己重试
            return call_tool(tool, args, task_id, step_id, attempt + 1)
        return ToolResult(error=str(e), is_error=True)   # 其余回传模型判断
    store.put(key, r)                       # 先执行后记录 = at-least-once
    return r
```

注意最后两行的顺序:**先执行后记录 = at-least-once(可能重复执行);先记录后执行 = at-most-once(可能丢)**。没有 exactly-once,只有"幂等的 at-least-once"看起来像 exactly-once。

**边界与误区**:
- 误区:"加个 retry 装饰器就行"——装饰器包得住函数调用,包不住"外部世界已经变了"。
- 误区:把 LLM 调用当幂等纯函数。即使采样参数固定,模型版本、路由、缓存状态的差异都可能给出不同轨迹;把"重试得到相同结果"写进假设的系统一定会出问题。
- 边界:高风险不可逆动作(转账、删除、对外发消息)不该有自动重试,应走人工确认或出件箱模式——agent 只写意图,投递交给独立可审计的组件。
- 边界:重试预算必须计入总预算。无界重试是成本失控最常见的来源之一。

**追问预判**:
- 追问:"agent 里能做到 exactly-once 吗?" → 答:不能,和分布式系统一样。能做的是幂等 at-least-once + 去重表;讲清 key 组成与"先执行后记录"的取舍。
- 追问:"模型重试和 harness 重试怎么分工?" → 答:按错误类型分——瞬时/传输给 harness,语义/业务给模型;加连续失败熔断防死循环。

## Q2:长时任务 agent 的部署形态有哪些?durable execution 解决什么问题?

**考察点**:是否理解"状态放在哪"决定了部署形态;对 durable execution 的**机制**理解,而不是背产品名。

**30 秒版**:按"谁持有状态 + 谁触发"分四种形态:①**同步请求内**(秒级,状态在内存,进程死=任务死);②**后台作业/队列**(状态在任务记录,worker 可重启,恢复逻辑自己写);③**durable execution**(状态在执行引擎的事件日志里,崩溃后重放日志恢复到断点);④**托管 agent 运行时**(harness + 沙箱 + 调度一起托管)。durable execution 解决一个非常具体的问题:**任务生命周期远长于进程生命周期**——机器会重启、部署会滚动、会话会被杀,而任务要跑几小时。它的手段是"每一步结果写进持久日志 + 崩溃后重放日志跳过已完成步骤",把进程内的调用栈变成可跨进程恢复的状态机。

**深入版**:

**选型的第一性判据**:任务时长 vs 进程寿命。任务 < 请求超时 → 同步;任务 > 进程寿命 → 状态必须外置,剩下的只是"外置到哪、谁负责恢复"。

| 形态 | 典型时长 | 状态位置 | 恢复方式 | 适用 |
|---|---|---|---|---|
| 同步 API | 秒 ~ 1 分钟 | 进程内存 | 不恢复,重来 | 对话式、单轮工具 |
| 后台作业 / 队列 | 分钟 ~ 小时 | DB / 队列记录 | 自己实现 checkpoint | 异步报告、批处理 |
| durable execution | 小时 ~ 天 | 引擎事件日志 | 自动重放到断点 | 多步长流程、需要严格副作用治理 |
| 托管 agent 运行时 | 分钟 ~ 天 | 平台托管 session | 平台负责 | 想少写基础设施 |

**durable execution 的机制**(讲透这块是加分点):
1. **workflow 必须确定性**。引擎恢复时会重新执行 workflow 函数体,靠"重放时不重复执行副作用"来跳过已完成部分。所以 `now()`、`random()`、直接的网络调用不能出现在 workflow 主体,必须包成 **activity/step**——activity 的结果写进事件日志,重放时不重新执行,直接取日志里的返回值。
2. **事件溯源**:日志是真相,内存状态只是日志的物化视图。恢复 = 从头重放日志到最新位置。
3. **由此得到三种能力**:崩溃恢复(换台机器继续)、超长等待(等人审批三天不占进程)、可审计重放(用同一份日志重建当时发生了什么)。
4. **代价**:确定性约束会传染到代码风格;**版本演进很麻烦**——改了 workflow 代码,运行中的老实例重放时可能走到不存在的分支,所以需要版本门(versioning gate)。

**把 agent 装进 durable execution 的正确切法**:workflow = 确定性的编排骨架(阶段顺序、审批点、补偿逻辑);activity = 每一次模型调用、每一次工具调用(不确定 + 有副作用,必须入日志)。"下一步由模型决定"与"workflow 必须确定性"看似矛盾,其实不矛盾:**决策一旦被记入日志就变成确定的**——重放时读日志里的决策,不再问模型。这就是"不确定的决策 + 确定的重放"。

**as-of 2026-08 的行业动向**:"managed agents / 托管 agent 运行时"是本季度明确升温的形态。LangChain 的 Harrison Chase 在 [2026-08-12 的观点文](https://www.langchain.com/blog/why-managed-agents-are-the-next-big-thing-in-agent-building)里把它定义为"跑在托管基础设施上的 agent harness",并列出托管层想一次性接管的东西:运行时(可靠执行与失败恢复)、事件流式 UX、沙箱、上下文/技能管理、评估、记忆、鉴权;文中也承认张力——托管带来的简化会与开发者要 custom middleware、以代码定义工具、程序化创建的诉求打架。同期 Anthropic 的 Managed Agents(beta)是同一形态的具体实现:agent 配置是**持久化、版本化的对象**,session 引用某个版本,每个 session 配一个容器做工具执行,支持定时触发的 deployment 与平台强制的 session 预算(as-of 2026-08)。判断力落点:**托管运行时买的是"少写基础设施",卖的是"控制权与可移植性"**——自建 harness + durable engine 仍是控制欲强、合规重的团队的选择。

**实例**(本仓库:最朴素的 durable execution,只用 git + 一个 JSON):

```
事件日志 = git commit 历史(brief: / deep-dive: / exp: / kb: / meta: / daily: 各一次 checkpoint)
断点指针 = meta/state.json 的 pending 字段
恢复动作 = P0 启动自检读 state.json,pending 非空则从该阶段继续
```

它没有引擎,却具备 durable execution 的核心三件:**持久日志、断点指针、启动即恢复**。这说明 durable execution 首先是一种设计,其次才是一个框架——判据是"进程随时被杀,下次能不能从断点继续",不是"用没用某个工作流引擎"。

**边界与误区**:
- 误区:"上了 durable 框架就可靠了"。框架保证编排可恢复,**不保证工具幂等**——副作用治理还得自己做(见 Q1)。
- 误区:把整个 agent loop 塞进 workflow 主体。模型调用不确定,必须是 activity。
- 边界:任务只有几分钟、失败重来成本低 → 不值得引入确定性约束的复杂度。
- 边界:托管运行时在数据出境、私有网络工具、自定义中间件三项上通常有硬约束,选型前先验这三条。

**追问预判**:
- 追问:"agent 的状态该存什么?" → 答:存"能重建现场的最小集"——目标/计划、已完成阶段、产出物指针、待办;不存完整对话(可重建、体积大、易过期)。
- 追问:"workflow 版本升级怎么办?" → 答:版本门 + 老实例跑完老版本;agent 场景还要额外考虑 prompt/协议版本的发布(见 Q5)。

## Q3:Agent 的成本与延迟优化手段有哪些?(缓存、模型路由、并行、预算护栏)各自的收益边界?

**考察点**:能不能算账。区分"降单价"与"减调用量";知道每种手段在什么条件下失效。

**30 秒版**:先立成本模型:`成本 ≈ Σ(轮次 × 上下文长度 × 单价)`。四类手段各打一个因子:**缓存**打重复前缀的单价(读约 0.1×,写 1.25×~2×);**模型路由**打单价;**并行**只打延迟不打成本(甚至更贵);**预算护栏**打轮次与失控尾部。收益边界:缓存要前缀稳定且复用够(5 分钟 TTL 下约 2 次回本);路由要有可靠的难度判别,否则误判返工比省下的更贵;并行只在真无依赖时有效;护栏省的是尾部而非均值——但 agent 成本是长尾分布,尾部往往就是大头。

**深入版**:

**先建模型**。一次 agent 任务的 token 大头不是输出,是**上下文被反复重发**:第 n 轮要把前 n-1 轮全部再发一遍,裸 loop 的输入 token 是 O(n²)。这一条解释了三件事:为什么 caching 对 agent 的收益远大于单轮问答;为什么"少一轮"比"每轮省一点"更有效;为什么上下文管理本身就是成本手段。

**1. Prompt caching**——降的是重复前缀的单价与 TTFT。
- 机制是**前缀匹配**:渲染顺序 `tools → system → messages`,前缀里任何一个字节变了,其后全部失效。所以稳定内容必须在前,易变内容(时间戳、请求 ID、本次问题)必须在最后一个断点之后。
- 经济学(两家旗舰 API 结构一致,as-of 2026-08):读约 0.1× 基础输入价(OpenAI 侧表述为 90% 折扣),写 1.25×(Anthropic 5 分钟 TTL;GPT-5.6 的显式缓存亦为 1.25×,最短缓存寿命 30 分钟);Anthropic 的 1 小时 TTL 写为 2×。**回本次数由此直接算出**:5 分钟档 `1.25 + 0.1 = 1.35 < 2`,两次请求即回本;1 小时档 `2 + 0.2 = 2.2 < 3`,需要三次。
- 失效条件:前缀短于最小可缓存长度(Anthropic 约 1024 token)**静默不缓存**;每请求都变的前缀(system 里塞 `now()`、未排序 JSON、随请求变的工具集)= 只付写费不产生读;断点数量有限(Anthropic 4 个)。
- 验证:看 `usage.cache_read_input_tokens`。长期为 0 就是有静默失效源。**"我开了缓存"不是证据,命中率才是。**

**2. 模型路由**——降单价,把成本风险换成了"判错风险"。
- 价差是真实的:Claude Opus 5 为 $5 / $25 每百万输入/输出 token,Haiku 4.5 为 $1 / $5(as-of 2026-08,以官方定价页为准)——同一 harness 里能差 5×。
- 三种粒度,工程可靠性排序是 **角色级 > 任务级 > 步骤级**:角色级(主 agent 决策用强模型,subagent 做检索/摘要用小模型)不需要难度判别器,只需要职责划分,收益/风险比最好;任务级需要一个分类器;步骤级最诱人也最脆。
- 边界:小模型在**长程规划与工具选择**上退化最快,而这恰是 agent 的关键路径。判据:让小模型干"上下文密集但决策简单"的活(读文件、抽取、格式化、摘要),决策留给强模型。误判的代价是返工——一次错误路由引发的多轮修复,常常抹掉几十次正确路由省下的钱。
- 同族但不同的杠杆:**effort / thinking 档位**——同一个强模型降档,往往比换小模型划算,因为保住了工具选择能力,只削思考深度;**批处理**(非实时任务走 batch,常见约 50% 折扣)则是不改模型、只改交付时效。

**3. 并行**——只买延迟,不买成本。
- 两个层次:工具级并行(一条 assistant 消息里多个 tool_use 并发执行,独立只读操作应当并行)与 agent 级并行(subagent 扇出)。
- 边界:① 有依赖的步骤并行 = 白做;② subagent 扇出会**增加**总 token(每个子上下文都要带一份指令),它买的是"主上下文不被污染"+ 墙钟时间;③ 并行度受下游速率限制约束,打满就退化成排队。
- 反直觉的一点:agent 的延迟大头常不是模型吐字,而是**轮次数 × 每轮 TTFT**。所以"减少一轮"优于"让这一轮更快"——这也正是缓存(降 TTFT)与好计划(降轮次)真正的价值。

**4. 预算护栏**——治长尾,不治均值。三种护栏语义完全不同,面试里最常混:

| 类型 | 模型知不知道 | 到点后发生什么 |
|---|---|---|
| `max_tokens` 这类硬上限 | **不知道** | 直接截断,答到一半没了,通常要重来 |
| 任务预算(告知式,如 Anthropic task budget,beta as-of 2026-08) | **知道**(服务端注入倒计时标记) | 模型自己收敛、优雅收尾 |
| 平台/宪法级硬闸(托管平台的 session 美元预算、本仓库的宪法 C5) | 不可协商 | 系统强制停止 |

设计原则:**告知式护栏放里层,硬闸放外层**。只有硬闸没有告知式,你得到的是"被砍断的半成品";只有告知式没有硬闸,你得到的是"模型觉得还能再试一次"的失控尾部。本仓库的例子:宪法 C5 规定网络操作 ≤40 次/运行、新增 ≤2500 行/运行,且**只可调低不可调高**;协议层的软预算(P1 ≤12、P2 ≤12、全局软 ≤30)在硬闸内自我调节。关键在于**硬闸不可被自动运行修改**——护栏若能被 agent 自己放宽,就不是护栏。

**实例**(按投入产出排序的优化顺序):

```
1. 量成本  →  按 task_id 聚合 input/output/cache_read/cache_write 与轮次(没有度量就别优化)
2. 稳前缀  →  system + tools 冻结在最前,动态内容后置,验证 cache_read > 0
3. 削轮次  →  更好的工具描述、只读并行、必要时先 plan(轮次是 O(n²) 的乘数)
4. 分角色  →  subagent / 检索 / 摘要换小模型或低 effort
5. 上护栏  →  告知式任务预算 + 外层硬闸 + 每任务成本告警
```

**边界与误区**:
- 误区:"换小模型是最大的省钱手段"。多数系统的第一大浪费是**上下文膨胀与无效轮次**,不是单价。
- 误区:把缓存当上下文管理。缓存**省钱不省注意力**——命中缓存的长上下文照样让模型变笨(见 01 组 Q5)。
- 误区:并行 = 省钱。并行省的是墙钟。
- 边界:**发布会击穿缓存**。改一个字的 system prompt,全量流量的前缀缓存立刻失效,成本与 TTFT 出现尖峰;灰度期间新旧两套前缀并存,两份缓存要各自攒够复用次数才回本——所以灰度窗口太长或桶切太碎,稳态之上还会多一笔账(接 Q5)。同理,任何"切换"都可能带缓存代价:换模型、换 speed 档位都会让已有缓存作废。

**追问预判**:
- 追问:"缓存命中率上不去怎么查?" → 答:按渲染顺序倒查静默失效源——动态时间戳、未排序 JSON、随请求变的工具集、工具描述里的随机 ID;逐项排除并盯 `cache_read_input_tokens` 变化。
- 追问:"怎么给 agent 设合理的成本上限?" → 答:先测分布不测均值(长尾),按 p95 设告知式预算、按远高于 p99 的水位设硬闸,并把超限当作可观测事件而不是异常。

## Q4:生产 agent 的 SLO 怎么定?失败了怎么降级?

**考察点**:能否把"模型系统"翻译成可运维的指标;有没有设计过降级链路。

**30 秒版**:agent 的 SLO 不能照抄"可用性 + p99 延迟",因为它的输出是**质量分布**而不是成功/失败二值。四类可用指标:**任务成功率**(必须挂在可自动判定的判据上)、**端到端时长分布**(p50/p95,不看均值)、**单位成本与轮次分布**、**人工干预率**。降级不是"返回 500",而是一条**逐级退让的链路**:同模型降档 → 换等价模型/供应商 → 缩小范围(部分完成 + 明确交接)→ 退回确定性 workflow → 转人工。核心原则:**降级要保住"可交接"——宁可交出半成品加清晰状态,不可交出看似完成的错误结果**。

**深入版**:

**为什么不能照抄传统 SLO**:传统 SLI 是二值的,而 agent 可能"HTTP 200、没报错、结果没用"。所以第一步是**定义什么叫成功**,并且它必须**可自动判定**——不可自动判定的成功率进不了 SLO,只能进人工抽检。

**四层 SLI**:
1. **可用性层(基础设施)**:能不能开工——模型 API 可达、工具/MCP 可达、沙箱可分配。这层照抄传统 SLO 没问题。
2. **完成层(任务)**:终止状态分布——`completed / partial / failed / timeout / budget_exceeded / needs_human`。务必把"预算耗尽"与"失败"分开统计,处置完全不同。
3. **质量层(结果)**:必须挂外部可验证信号,优先级从高到低:确定性判据(测试通过、schema 校验、编译通过)> 下游接受率(PR 被合并、工单被关闭、建议被采纳)> LLM-as-judge 抽样(有偏,只做趋势)> 人工抽检(金标准,采样)。**没有可验证信号的 agent 定不了质量 SLO**,只能退守到干预率。
4. **经济层**:单位任务成本 p95、轮次 p95。这层最常被漏掉,却是"系统在悄悄退化"的最早信号——质量下降往往先表现为"要跑更多轮才做完"。

**SLO 怎么落数**:别拍脑袋定 99.9%。先跑两周拿基线分布,取当前 p50/p95 附近作为初始 SLO,再逐季收紧;错误预算(error budget)用法与传统一致——**预算烧完就冻结变更**。这条对 agent 尤其重要,因为它的变更主要来自 prompt / 工具 / 模型,天然高频。

**降级链路**:沿"损失最小"的维度退,而不是简单失败。

```
L0 正常   强模型 + 完整工具集 + 完整预算
L1 降档   同模型降 effort / 缩短上下文             损失:结果深度
L2 换路   等价模型或另一供应商 / 关掉不稳定的工具   损失:能力细节(注意:换模型会让缓存作废)
L3 缩范围 只做能做的部分,产出"已完成/未完成/阻塞点" 损失:完整性,但保住可交接
L4 退化   走确定性兜底路径(模板、规则、旧流程)     损失:灵活性
L5 交人   明确失败并带上现场(日志、部分产出、下一步建议)
```

每一级都要满足同一个不变量:**状态必须落盘且可续跑**——降级不是终点,是把任务留在"下次能接着做"的位置(复用 Q1/Q2 的 checkpoint 机制)。

**平台已经提供的降级原语**(as-of 2026-08,举例是为说明机制):Anthropic API 对安全分类器拒答给出 `stop_reason: "refusal"` 并提供服务端 fallback 参数,可在拒答时按类别自动路由到备选模型——这是把 L2 做进协议层;fast mode 遇到自身速率限制时,标准做法是按 `retry-after` 重试或退回普通速度,而**换速度会让 prompt cache 失效**。后者正是"降级有代价"的具体形态:换来了可用性,付出了成本与 TTFT。设计预案时必须把这种耦合写进去,否则会出现"降级后系统更慢更贵"的雪上加霜。

**熔断与隔板**:单个工具/下游连续失败要熔断(否则每个任务都要在它上面白烧几轮);不同租户、不同任务类型要隔板(bulkhead),避免一个高消耗任务吃光并发与配额。

**实例**(本仓库的降级实践,见 [meta/CONSTITUTION.md](../meta/CONSTITUTION.md)):
- **C10 收尾优先**:预算或上下文吃紧时,**砍内容不砍收尾**——宁可当天少做,也必须完成"提交 + 合并 + 汇报"。这是标准的 L3:牺牲完整性,保住可交接与可续跑。
- **C3 收尾必达 + 失败不破坏**:合并失败时不 force、不 reset、不删未合并分支,给出手工命令并交给下次运行 P0 自愈——降级到"安全停机 + 留痕",而不是"强行成功"。
- **C7 诚实**:平静日就写"平静日"。**允许系统输出"没有",本身就是降级设计的一部分**——不允许说"没有"的系统,迟早会开始编。

**边界与误区**:
- 误区:用"没报错"当成功率。agent 最贵的失败是**顺利完成了错误的事**。
- 误区:把 LLM-as-judge 当 SLO 闸门。judge 有偏,且会随模型更新漂移,适合看趋势和触发告警,不适合当合同。
- 误区:降级 = 返回错误。对 agent 来说"部分完成 + 明确状态"几乎总优于"整体失败"。
- 边界:高风险域(资金、医疗、法务)不该有"自动降级到弱模型"这一级——那里的正确降级是**直接转人工**。

**追问预判**:
- 追问:"没有确定性判据的任务(比如'写篇周报')怎么定 SLO?" → 答:用代理指标——人工干预率、返工率、下游采纳率,配抽样人工评分看趋势;并明说这类任务只做趋势 SLO,不做硬 SLA。
- 追问:"供应商更新模型导致质量下降,SLO 怎么保护你?" → 答:锁模型版本 + 切换前跑回归集(见 Q5);而且经济层指标(轮次/成本 p95)通常比质量指标更早报警。

## Q5:Prompt / 系统提示 / 协议的变更怎么发布?灰度、回滚、防回归怎么做?

**考察点**:是否把 prompt 当代码来管;有没有真实的发布工程经验,而不是"改完看看效果"。

**30 秒版**:把 prompt / 系统提示 / agent 协议当**生产配置**发布,四件事缺一不可:①**版本化**(进版本库、版本号递增、每次改动独立 commit、附动机与回滚方式);②**防回归**(改动必须跑固定评估集,门槛是"不劣化"而不是"变好");③**灰度**(按任务/租户分桶,先小后大,同时盯质量、成本、轮次);④**回滚**(一条命令退回上一版,且回滚路径演练过——`git revert` 单个 commit 是最朴素也最可靠的形式)。两个特有的坑:prompt 改动**没有编译期**,语法永远正确、错误只在行为上出现;而且改一个字就击穿全量 prompt cache。

**深入版**:

**为什么 prompt 发布比代码发布难**:
1. **没有类型系统**:改错不报错,只是行为变差,可能几天后才被发现。
2. **效果非局部**:系统提示改一句话,可能影响完全无关的任务类型——因为它进的是**每一次请求的前缀**,爆炸半径比多数代码大。
3. **评估贵、慢、带噪**:一次全量回归要跑真实任务,成本与时间以小时计,且结果本身有方差——单次通过不等于没退化。
4. **耦合缓存与成本**:前缀变了 = 缓存全失效(见 Q3);灰度期间新旧前缀并存,两份缓存各自都要攒够复用次数才回本。
5. **上游也会变**:供应商更新模型,本身就是一次"你没发起的发布"。所以必须锁模型版本,并把模型升级当作与 prompt 改动同级的发布事件。

**一套可落地的流程**:

```
变更提案(改什么 / 为什么 / 预期效果与检验方式 / 回滚方式)
  ↓
离线回归:固定评估集(含历史 bug 用例)+ 成本与轮次对比;门槛 = 不劣化
  ↓
灰度:先 1-5% 或先内部租户,保留对照组
  ↓
观察窗:质量指标 + 经济指标(轮次/成本 p95)+ 干预率,至少覆盖一个完整业务周期
  ↓
全量  或  回滚(回滚不需要审批——回滚是默认权利)
  ↓
记录:进化日志(改动 / 动机 / 预期检验 / 回滚方式 / 幅度)
```

关键设计点:**一次一变**(同时改 prompt 和工具集就无法归因,这条比任何工具都重要);**改动独立成 commit**(混在功能提交里的 prompt 改动无法单独 revert);**回归集包含历史 bug 用例**(每修一个线上问题就加一条,这是防回归的复利来源);**预期检验写在发布前**(事后找解释是最常见的自欺);**允许"不改"**(为改而改是 prompt 工程最主要的熵增来源)。

**当被发布的对象是"agent 自己遵守的协议"**,还多出一个安全问题:**谁有权改**。答案必须是分层——一层可自我修改(策略、参数、措辞),一层不可自我修改(硬预算、安全边界、以及"修改权限"本身)。缺了后者,系统会缓慢地把约束改宽,而每一步看起来都合理,这就是自我扩权/漂移。

**实例**(本仓库自身就是一套完整的 agent 发布工程):
- **分层权限**:[meta/CONSTITUTION.md](../meta/CONSTITUTION.md) 规定自动运行**永远不得修改宪法与 CLAUDE.md**(C1),要改只能写 `meta/PROPOSALS.md` 等人工批准;而 [meta/PROTOCOL.md](../meta/PROTOCOL.md) 可由 agent 在宪法边界内自我修改。可自我修改层 / 不可自我修改层,落到了两个文件上。
- **变更速率限制**:C4 规定协议每次运行**至多 1 处实质改动**、版本号递增、**独立 commit**、进化日志必须记录动机/预期检验/回滚方式。一次一变 + 独立 commit ⇒ 回滚就是 `git revert <该 commit>`。
- **不可自我放宽的硬闸**:C5「硬预算只可调低,不可调高」,直接堵死"agent 通过改协议给自己扩权"的路径。
- **验收闭环**:P5 周元复盘会**验收近一周协议改动是否兑现了当初写下的"预期检验",未兑现则 `git revert` 回滚**——把"观察窗 + 条件回滚"写进了流程,而不是靠人记得。
- **版本记录**:[meta/EVOLUTION.md](../meta/EVOLUTION.md) 只追加,记录 v1.0 → v1.1 的改动、动机、预期检验、回滚方式与幅度(小/中/大);大改必须走提案,不得直接执行。
- 诚实地对照上面的流程表,这套系统缺的一环是**离线回归集**:它靠"下次运行的实际表现 + 周复盘"做在线验收,代价是问题要一整个周期才暴露。这也是这类系统最典型的下一步——补一个小而稳的回归用例集。

**发布形态的工程细节**(as-of 2026-08,重点在机制):无头/自动化运行(`claude -p` 这类无头模式配合 `--allowedTools` 收窄权限、CI 集成、云端定时 routines)让 agent 的发布真正变成 CI/CD 问题——提示与协议进仓库、改动走 PR、评估作为 CI 门禁、权限白名单随版本一起发布。托管 agent 平台则把这层做成一等公民:agent 配置是版本化的持久对象,session 启动时**钉住某个版本**,于是"灰度"变成"让一部分 session 钉旧版本、一部分钉新版本",回滚变成"把默认版本指回去"。机制上与传统配置发布同构,只是被发布的东西从代码变成了行为规范。

**边界与误区**:
- 误区:"prompt 不是代码,不用走发布流程"。它是进入每一次请求前缀的**全局配置**。
- 误区:改完看一两个 case 就上线。agent 输出有方差,单次样本区分不了"改好了"和"这次运气好"。
- 误区:只做灰度不做回滚演练。**没被验证过的回滚路径等于没有回滚**。
- 边界:小团队/低风险场景全套流程过重——但**版本化 + 一次一变 + 可回滚**这三条,是任何规模都该有的最小集。
- 边界:评估集会过拟合。定期加新用例、退休失去区分度的老用例,否则"回归全绿"会变成安慰剂。

**追问预判**:
- 追问:"prompt 的 A/B 怎么做才有统计意义?" → 答:**任务级**随机分桶(不是请求级,避免同一任务跨版本)、按效应量估样本量、主指标优先用确定性判据、同时看成本与轮次这类低方差代理指标。
- 追问:"模型升级和 prompt 升级怎么排期?" → 答:绝不同时——两者都动就无法归因。先锁 prompt 升模型跑回归,再在新模型上调 prompt;并注意为旧模型调优的 prompt 在新模型上常常"过度指令化",需要做减法。
