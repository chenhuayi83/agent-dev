# 上下文工程总览

上下文是 agent 最稀缺的资源:预算分配(系统提示/工具/历史/检索)、注意力衰减、just-in-time 加载、"上下文即产品"的工程观。

## 原理(稳定)

### prompt 工程 ⊂ 上下文工程(以及为什么重心转移了)

一个可量化的理由:单轮对话里,**你亲手写的提示词就是上下文的 100%**;而在一个跑了 30 轮的 agent 会话里,它只占百分之几——其余全是工具输出、文件内容、历史消息。你能控制的那部分份额缩小了一个数量级,所以工作重心必然从"怎么措辞"转向"**哪些信息该进上下文、何时进、以什么形式进**"。

### 判断一个提示技巧是否过时的单一测试

问:这个技巧是在**骗出模型已有的能力**,还是在**给出模型不可能知道的信息**?

- 前者(如"请一步步思考"、角色扮演式咒语、强行 CoT 提示)——随着模型原生具备推理能力而失效,属于历史技巧;
- 后者(项目约定、输出契约、边界情况样例、明确的负向约束)——**永不过时**,因为模型再强也猜不到你的私有约定。

### few-shot 为什么比"描述输出格式"更有效

这是机制差异,不是经验偏好:**示例是分布内的强约束**(模型做的是模式续写,几乎无翻译损耗);**描述是分布外的弱约束**(需要把规格翻译成行为,有损,且自然语言难以表达边界情况)。推论:样例应当**优先覆盖边界情况**,并保持多样与规范——而不是堆砌一长串同质例子。
